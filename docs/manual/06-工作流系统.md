# 第 6 章 工作流系统

## 6.1 先从一个场景说起

你对 coara 说：

> 帮我做一个工作流：先调研今天的 AI 新闻，再写成一份简报，发之前找个人把关，不合格就打回重写

接下来大致会发生这些事：

1. Root 激活 `workflow` 技能，学会工作流图的写法；
2. 它用 `orchestrator` 工具把流程登记成一张图：调研节点 → 写作节点 → 评审节点，评审不通过就回指写作节点（打回重写），通过才到发布节点；
3. 你在 Web 编辑器里看到这张图——节点和连线，连线上标着"成功"还是"失败"；
4. 你说"跑吧"，Root 先把图固化成定稿文本，再交给后台引擎运行；
5. 每个节点都是一个智能体在干活：调研的查资料、写作的写简报、评审的挑毛病；评审说"不行"，写作节点就被再次激活，重写一遍；
6. 全部节点跑完，结果摘要出现在对话里，工作空间动态里也多了一条「AI 日报 · 完成」。

这一章就沿着这条链，把每个环节讲清楚。

## 6.2 工作流是什么：一张节点加连线的图

**工作流（workflow）** 是 coara 处理"步骤多、有依赖、要反复跑"的任务的正式机制。遇到以下情况就适合用它：步骤之间有先后或分支；要不同能力的节点分工；要定时或由事件触发；要跑很久、中途能停能续。

工作流的核心是一张**图**：**节点**是干活的人，**边**是节点之间的先后关系。

- **节点 = 智能体**。图里只有一种节点：智能体节点。每个节点有自己的名字（id）和任务指令（task），运行时是一个完整的智能体在自主思考、调用工具、产出结果。并行、汇聚、分支、循环、重试都不是节点的种类，而是**图的形状**：
  - 并行 = 一个节点扇出给多个下游；
  - 汇聚 = 多个上游汇到一个节点（等齐再动）；
  - 分支 = 节点声明 `routes: one`，每次只挑一条路走；
  - 循环 = 下游画一条边指回上游（回边）；
  - 重试 = 画一条 `on: error` 的边指回自己或指向上游。
- **边 = 唯一拓扑**。边表示"谁跑完轮到谁"，还带着触发条件 `on`：`success`（正常完成就投递，缺省）或 `error`（失败时投递，用来做重试/兜底路由）。

这份图用一段叫 **WDL**（Workflow Description Language，工作流描述语言）的 YAML 文本保存。三方看的是同一份文本：

| 角色 | 对 WDL 做什么 |
|------|---------------|
| Root | 按技能指引写出 WDL，用 `orchestrator` 保存、提交 |
| 工作流引擎 | 解析 WDL，按节点和边执行，回传进度 |
| Web 编辑器 | 把 WDL 画成画布上的节点和连线，编辑后再转回 WDL |

WDL 文本**不是独立语言**，它是这张图的规范序列化（canonical 投影）：图长什么样，文本就是什么样，固定键序、省略默认值，同一张图生成的文本永远逐字节相同。权威格式规范是 `WORKFLOW_SPEC.md`。

**节点即智能体**：工作流里没有写死的脚本节点，每一个节点都是一个完整的智能体——有自己的身份、任务说明，会自主思考、调用工具、产出结果。所以工作流更像"一组分好工的智能体按图施工"，而不是一条自动化脚本流水线。详见 [`docs/节点即智能体.md`](../节点即智能体.md)。

## 6.3 怎么让它帮你设计

你不需要自己学 WDL。流程是这样的：

1. **你说目标**（"做一个每日巡检工作流"）；
2. Root 激活 `workflow` 技能，技能里包含 WDL 写法和常见模式；
3. Root 用 `orchestrator` 工具把流程登记成图：`spawn` 逐个登记节点（填节点名、任务指令、依赖谁、路由给谁），节点默认停车不跑，你在对话里就能看到一张待启动的图；
4. 确认结构后 `run` 点火，节点按依赖自动级联推进；
5. 跑通了用 `save(flow=…)` 把会话内图自动投影成 WDL 定稿并存成草案，长期复用、交给后台引擎无人值守执行（无需单独 export，也不必手写 definition）。

`orchestrator` 工具一共十二个动作（激活 `workflow` 技能后注册）：

| 动作 | 干什么 |
|------|--------|
| `spawn` | 登记一个 flow 节点（节点名 + 任务指令 + 依赖/路由），默认停车 |
| `run` | 点火 flow（`flow=…`），或把已定稿的 WDL 提交后台引擎（`draft_id=…` 或 `wdl=…`） |
| `wait` | 等整个 flow 收尾 |
| `status` | 查看 flow 各节点状态与输出 |
| `save` | 把会话内图自动投影为 WDL 并落盘（`save(flow=…)`；也可贴 `definition=`） |
| `load` | 从落盘文件恢复 flow（结构与结果） |
| `result` | 按 `instance_id` 查看结构化运行结果（摘要/输出/节点） |
| `delete` | 删除草案 |
| `update` | 运行中改节点任务指令或路由模式（下次激活生效） |
| `edge` | 运行中加/删边（`frm`/`to`/`on`，`remove: true` 删边） |
| `remove` | 删未运行节点（已跑的是实录，不可删） |

草案存放在 `<coara_home>/users/default/workflows/drafts/`；运行实例记录在旁边的 SQLite 里。改草案不影响已经在跑的实例。

工作流是**全局资产**，不属于某个工作空间；但每一次**运行**都在一个具体的执行工作空间里进行（文件读写、`@` 路径都落在那里）：你在哪个空间提交就默认在哪个空间跑，事件源触发的运行在事件源所属空间跑。所谓把工作流「部署」到某空间，就是给它的 `schedule` 配一个该空间的事件源（`kind: event` + `event_id`）——建立的是触发绑定，不会复制任何文件。改草案后触发器自动用新版，不会跑旧快照。

## 6.4 WDL 长什么样

一个最小工作流（两步顺序执行）：

```yaml
name: 示例
description: 一句话目标
schedule:
  kind: manual
nodes:
  调研:
    task: 调研内核设计
  写作:
    task: 写简报
    input: "{{steps.调研.text}}"
edges:
  - { from: 调研, to: 写作 }
```

- 顶层字段：`name` 必填；`description`、`schedule`（启动策略，默认 `kind: manual`）、`max_activations`（全局激活上限，默认 100）可选。**没有图级 `inputs`**——输入归每个节点：节点 `input` 字段即输入接口（`{{steps.y.text}}` 引用上游或字面量种子），外部运行传参直接编辑节点配置。
- **`nodes`**：一张映射，键是节点名，值是该节点。节点字段只有四个——`task`（任务指令）、`input`（数据进模板）、`routes`（路由模式，`all` 缺省 / `one`）、`max_activations`（节点级激活上限）。
- **`edges`**：列表，每条边 `from` / `to` / `on`。`on` 缺省 `success`；`on: error` 表示失败兜底路由。

一个带分支、循环、重试的完整例子（评审流水线）：

```yaml
name: 评审流水线
nodes:
  调研:
    task: 调研内核设计
    routes: one
  写作:
    task: 写初稿
    input: "{{steps.调研.text}}"
  评审:
    task: 审阅并选择后继
    routes: one
  发布:
    task: 发布
    max_activations: 5
edges:
  - { from: 调研, to: 写作 }
  - { from: 写作, to: 评审 }
  - { from: 评审, to: 发布 }
  - { from: 评审, to: 写作 }        # 回边：打回重写（循环）
  - { from: 调研, to: 评审, on: error }  # 失败兜底路由
```

注意：`on` 是 YAML 1.1 的裸词，会被解析成布尔值 `True`（系统已做兼容还原），但手写时建议给含 `on` 的边加引号：`{ from: a, to: b, 'on': error }`。

**数据靠模板传**：节点之间不靠边传数据，而是在 `input` 里写模板引用，运行时自动渲染。只有一种写法：

| 写法 | 含义 |
|------|------|
| `{{steps.节点名.text}}` | 某个节点的最终输出文本（模板引用即隐式依赖） |

节点 `input` 字段除了模板引用，也可写**字面量种子**——每个节点自带输入接口，没有图级 `inputs` 声明。

模板引用会自动成为隐式依赖（校验时推导），所以就算忘了画边，数据流也能追到上游。

## 6.5 跑起来之后：引擎与结果

工作流可以在两处跑，语义完全一致，差别只在"谁在照看"：

- **会话内编排（FlowCoordinator）**：节点直接在当前会话里跑，`spawn` 登记、`run` 点火、`wait` 收尾，跑的过程你在对话里实时看得见，适合边聊边调；
- **后台引擎（KernelGraphRunner）**：把 WDL 定稿文本提交给独立引擎进程，无人值守执行，状态落 SQLite、崩溃可恢复，适合固化复用的正式流程。

日常路径：先在会话里 `spawn` + `run` 把流程跑通，`save(flow=…)` 自动投影并存草案，之后要正式执行时 `orchestrator(action="run", draft_id=…)` 提交后台引擎，立刻返回任务编号，不用干等。**工作流是独立子系统，状态不进 CLI 对话**：无论谁发起，进度与结果都只在 Web UI /workflow 和工作空间动态里看；需要时用 `orchestrator(action="result", instance_id=…)` 主动拉取。

查看结果：

- `orchestrator(action="status", flow=…)` —— 会话内 flow 各节点输出；
- `orchestrator(action="result", instance_id=…)` —— 后台实例的结构化结果（摘要/输出/节点）；
- Web UI（内核托管 Web 服务 → /workflow）—— 草案列表、实例列表、运行状态与结果、编辑器，以及节点模型设置。

**中断恢复**：引擎进程万一异常退出，重启时会把还在 running 状态的实例标记为 `interrupted`。这些实例不会自动续跑，等你在网页上点"恢复"才继续。

### 节点模型：工作流自己的 provider

工作流节点有自己的模型选择，**与主会话的 `/model` 切换互不影响**。解析顺序（先到先得）：

- 图级覆盖：投影顶层写 `provider: xxx` / `model: yyy`，本图节点优先用它（省略则不写入，序列化字节不变）；
- 全局默认：providers.yaml 的 `llm_profiles.workflow.node`——在 Web UI /workflow 页右上「节点模型」里选择并保存即写入此处，保存后当前进程与后台引擎都会热生效，无需重启；
- 兜底：以上都缺时用引擎内置默认（minimax / MiniMax-M3）。

## 6.6 节点怎么被激活：路由、循环、重试与上限

- **首激活**：每个节点要等它所有"必需等待"的上游都到达才动。源节点（谁都不依赖）一开工就能跑。
- **再激活**：图里可以有回边——评审说不行，就沿回边把写作节点**再次激活**重写。回边和 `on: error` 边是"机会性触发"：上游完成就投递，节点收到就会再跑一轮。
- **分支（routes: one）**：节点声明 `routes: one` 后，每次激活只选一条出边走。会话内编排由节点自己用 `deliver(message=…, next=后继)` 挑；后台引擎按静态顺序取第一条。
- **重试（on: error）**：节点失败时，`on: error` 的出边会把失败信息投递过去——可以指回自己（失败重来）、指向上游（打回重做），也可以指向一个兜底节点。节点**没有失败兜底边**时失败会一路冒泡，整个工作流判失败。
- **激活上限**：每个节点每轮激活都计数，受上限约束——全局 `max_activations`（默认 100），节点可写自己的 `max_activations` 覆盖。触顶即失败终态。**图允许任意回边，循环会不会卡死由上限兜底**：循环边界显式、确定、可终止。

## 6.7 除了手动运行：文档级 schedule

用顶层 `schedule` 声明整图如何启动（细节见 `WDL_SPEC.md` §2 文档结构）：

| schedule.kind | 说明 |
|---------------|------|
| `manual` | 默认。你（或 Root 按你意思）明确运行 |
| `event` | 绑定事件源 `event_id`，事件到达自动开跑 |
| `webhook` | 外部系统推 webhook（`event_id` 或 `webhook_path`）自动开跑 |
| `cron` / `interval` | 按时间表 / 间隔；定时执行 = cron 事件源（`kind: cron`）到点发 `cron.tick`，再经 trigger 注册表直启本工作流 |

`kind` 为 `event`/`webhook` 且 `enabled` 不为 `false` 时：保存草案会登记到事件启动注册表，事件到了由引擎自动启动实例。事件源怎么配，见 [第 9 章 事件源与工作空间动态](./09-事件源与工作空间动态.md)。

## 6.8 边界与限制

- 图里只有一种节点（智能体），没有 if/for/while/parallel/wait/merge 之类"形状节点"——分支靠 `routes: one`，循环靠回边，重试靠 `on: error` 边；
- 没有独立的数据边，数据只靠节点 `input` 的 `{{steps.y.text}}` 模板或字面量种子传；
- 节点没有内置人工审批挂起点（审批是人话层的机制，不进工作流图；需要把关就设一个"评审"智能体节点）；
- 模板引用只能指向存在的节点，写错会在保存/运行的校验阶段报出来，不会带病执行；
- 修改草案不影响已创建的实例；
- 会话内 flow 与后台引擎跑同一套激活语义；`routes: one` 在后台引擎按静态顺序取第一条（交互式才由节点自己挑）。

## 6.9 本章小结

- 工作流是一张图：节点 + 边；节点是智能体，边是拓扑，控制流全是图的形状；WDL 是图的规范序列化，权威规范在 `WORKFLOW_SPEC.md`；
- 使用路径：说目标 → `tool(activate, name=orchestrator)` → spawn 登记节点 → run 点火 → save(flow) 固化落盘 → 正式跑提交后台引擎；
- `orchestrator` 十二个动作覆盖登记、点火、收尾、固化、草案 CRUD 与运行中调整（update/edge/remove）；
- 并行=扇出、汇聚=扇入、分支=one 路由、循环=回边、重试=error 边；激活上限保证循环终止；
- 双宿主：会话内 FlowCoordinator 交互编排，后台 KernelGraphRunner 无人值守；同一张图、同一套语义；
- 除手动外还支持 event / webhook / cron 触发，结果按来源进对话或工作空间动态。
