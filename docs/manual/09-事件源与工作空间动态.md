# 第 9 章 事件源与工作空间动态

## 9.1 先从一个场景说起

你的商店 App 上线了，用户会在手机上提交反馈。你希望：反馈一到，coara 知道；但你不想正在聊别的事情时被打断。

你配了一个事件源：监听商店空间的 `feedback/inbox/` 目录，新文件落地就产生一条事件。效果是这样的——

- 反馈落地 → 一条消息进商店空间的"动态流"；
- 手机 App 上商店空间亮起红点，显示"1 条未读"；
- 你方便的时候说"看看商店有什么新动态"，Root 列出未读，你决定怎么批示——或让管家 janitor 先过目。

另一种玩法是反馈一到就让管家先看一眼——把配置里的 `handle` 从默认的 `park` 改成 `janitor` 即可：janitor 勾掉噪音、把要你拍板的呈阅上来、能自己处理的直接处理，处置理由都写进消息轨迹。

这一章讲两件事：**事件源**（coara 感知外部变化与定时点的传感器）和**工作空间动态**（这些变化按工作空间归档后的消息流）。

## 9.2 事件源：四种传感器

事件源（event source）把外部变化变成系统内部统一的事件对象。目前有四种：

| 类型 | 感知方式 | 典型场景 |
|------|----------|----------|
| `file_watch` | 监听文件系统变化 | 反馈 JSON 落进空间的 `feedback/inbox/` |
| `interval_poll` | 定时扫一遍目录 | 文件系统通知不可靠的环境、兜底补漏 |
| `webhook` | 接收 HTTP POST | App 后端、第三方服务主动推送 |
| `cron` | cron 表达式到点触发（Asia/Shanghai） | 每天 8 点巡检、每工作日拉行情（停机错过不补发） |

每个事件源是一份 YAML，放在 `<workspace>/.coara/matters/definitions/*.yaml`，主要字段：

| 字段 | 含义 |
|------|------|
| `id` | 事件源编号 |
| `kind` | 上面四种之一 |
| `workspace` | 归属的工作空间短名 |
| `salience` | 显著性：`low` / `normal`（默认）/ `high`；`high` 的内容会进跨空间前台待处理视图（见 9.3） |
| `handle` | 内容谁来处置（见 9.3），默认 `park` |
| `ttl_seconds` | 消息保质期（秒）：落箱超时未读被纯规则自动勾掉（低价值事件建议配） |
| `enabled` | 是否启用 |
| `watch_path` / `watch_pattern` / `watch_events` | file_watch / poll 的监听路径、文件名模式、关心的事件（默认只关心"新建"） |
| `interval_seconds` | poll 的扫描间隔 |
| `cron` | cron 表达式（`kind: cron` 必填） |
| `webhook_secret` | webhook 的校验密钥 |
| `cooldown_seconds` | 同一事件的去重冷却，默认 30 秒 |
| `message_template` | 事件渲染成文本的模板 |
| `suggested_delegate` | 建议后续派哪类分身处理 |

webhook 统一挂在 coara 内嵌的接收服务上，默认端口 `8765`（可在 `config.yaml` 的 `events.webhook_port` 改），外部请求路径是 `/webhook/<事件源 id>`。

## 9.3 事件来了往哪儿送：salience 与 handle

消息内容体系下，**任何事件都先无条件写进所属空间的动态流**（动态流就是该空间的收件箱），然后由两个字段决定曝光与处置：

| 字段 | 取值 | 含义 |
|------|------|------|
| `salience` | `low` / `normal`（默认）/ `high` | 显著性。`high` 的内容上浮到跨空间的"前台待处理视图"（`review(action=pending)`），其余只有收件箱红点 |
| `handle` | `park`（默认）/ `janitor` | 处理模式。`park` = 挂住等用户来看；`janitor` = 事件落箱后叫醒管家 janitor 过目（勾掉 / 呈阅 / 自处理，理由写进处置轨迹） |

什么时候用：

| 配置 | 行为 | 什么时候用 |
|------|------|-----------|
| `handle: park`（默认） | 只进动态流，不打扰任何人 | 绝大多数情况：先进动态流，你看了再处理 |
| `handle: janitor` | 进动态流 + 叫醒管家 janitor 过目 | 需要"有人先看一眼"的，如"反馈一到就先筛选一遍" |
| `ttl_seconds` | 消息带保质期，过期未读自动勾掉 | 低价值通知，不怕漏 |
| （经工作流触发） | 事件源还可以触发工作流：文档级 `schedule.kind: event` + `event_id` 指向该事件源 | 反馈要进一条正式流水线时 |

> 旧版 `trigger_mode` 字段已废弃并被忽略（处置缺省 `handle: park`）：不再有「事件自动叫醒主会话跑回合」。

事件到达后的完整路径：

```text
外部变化 / cron 到点 → 事件源感知 → 构造事件对象 → 去重检查
  → 无条件写入动态流（按 salience 曝光，+ 手机红点推送）
  → handle=janitor 时 → 叫醒管家 janitor 过目（勾掉/呈阅/自处理，写处置轨迹）
  → 工作流 trigger 命中 → 直启 WDL
```

**去重与冷却**：每条事件算出一个去重键，同一键在 `cooldown_seconds` 内不重复处理。去重状态持久化在 `<coara_home>/users/default/matters/.state/` 下，重启不丢。这样文件反复抖动、webhook 重试都不会刷出重复动态。

**改完配置不用重启**：聊天里输入 `/events reload` 即可热重载所有事件源配置；`/events` 单独用是查看各源状态。

## 9.4 工作空间动态：每个空间的动态流

工作空间动态（updates）是按工作空间归档的消息内容流，存在 `<workspace>/.coara/inbox/`，一条一个 JSON 文件。写入方不只事件源：工作流的终态和待审批、提醒到点，都会变成动态。凡是"需要你知道的内容"，都会落进所属空间的收件箱——事件源这类外部感知标记为 `external_sensor`，系统内部自报（工作流完成、提醒到点）标记为 `internal_report`。（后台任务完成结果只回发起会话历史，不再落收件箱。）

每条动态的主要字段：编号（`upd-` 开头）、所属空间、来源、标题、正文、原始载荷、去重键、状态，外加消息内容信封的字段：

- `salience`：显著性（`low` / `normal` / `high`）。`high` 的未读内容会进跨空间的"前台待处理视图"；
- `handle_mode`：处理模式（`park` / `janitor`）；
- `source_kind`：来源族（`external_sensor` / `internal_report`）；
- `disposition`：处置轨迹（`pending` 待过目 / `elevated` 呈阅 / `resolved` 已处置 / `dismissed` 已勾掉）+ 过目人 / 时间 / 备注（`reviewed_by` / `reviewed_at` / `review_note`）+ 保质期（`expires_at`）。

内部自报的显著性是定好的：提醒到点恒为 `high`（落当前活跃空间）；工作流完成/失败/取消等终态 `normal`。

**状态与处置**：

```text
状态：unread（未读） → read（已读） → archived（归档）
处置（正交于状态）：pending → elevated / resolved / dismissed
```

- 你在 Web 或手机上的**批示** = `resolved`（备注为批示摘要）；
- 你或 janitor **勾掉** = `dismissed`（不再占红点，条目保留可回查）；
- janitor **呈阅** = `elevated`（上浮前台待处理视图，无论显著性）；
- 纯规则过目（janitor watcher 每拍执行，不经 LLM）：过保质期 / `low` 超龄（默认 7 天）的未读 pending 自动 `dismissed`；已呈阅的条目不受规则触碰。

**红点是怎么算的**：系统为每个空间记一条"已读水位线"（最近一次"全部标为已读"的时间），水位线之后、且未被勾掉/处置的条目就是未读数——这就是手机 App 上红点数字的来源。读完把水位线推上去，红点就清零。

容量上限每空间 500 条：超出时先清理已归档的，再清理最旧的已读，**未读的永远不会被挤掉**。

## 9.5 怎么看动态、怎么处理

**聊天命令**（不经 LLM，直接出结果）：

```text
/ws updates                    " 当前空间的未读动态
/ws updates pending            " 跨空间高显著未读 + 已呈阅（前台待处理视图）
/ws updates stats              " 各空间动态统计
/ws updates list <空间名>       " 指定空间
/ws updates read <动态编号>     " 读全文（顺带标为已读）
/ws updates dismiss <动态编号>  " 勾掉（留处置轨迹）
/ws updates elevate <动态编号>  " 呈阅（上浮待处理视图）
/ws updates resolve <动态编号>  " 标记已处置
/ws updates archive <动态编号>  " 归档
/ws updates mark_read <空间名>  " 全部标为已读（红点清零）
```

**对话里 janitor 的批复工具**：`review(action=board / list / pending / stats / read / dismiss / elevate / resolve / archive / salience / mark_read)`，语义与上述命令相同；dismiss/elevate/resolve 可带 `note` 写处置理由；`salience` 调优先级（low/normal/high），轨迹写回消息。

**主会话不带动态工具**：动态的查看与处置归 janitor（`review`）与用户（Web UI / `/ws updates` 命令）；主会话经工作空间消息注入了解动态，要动手时派 coaras 锁定空间处理，或配工作流直启。

看完动态如果要动手（比如处理那条反馈），让 Root 派 coaras 锁定到那个空间处理，或配工作流直启；常规事件源 `handle: janitor` 已让管家先过过目。

**手机端**：PC 上每写入一条动态，系统会往 Matrix 房间发一条 `[COARA_UPDATES]` 隐藏消息，里面带着各空间的未读数和这条动态的摘要。手机 App 收到后更新本地角标，不在聊天界面显示——所以你不在电脑前也能知道"商店空间有新反馈"。

## 9.6 webhook 为什么需要一条隧道

如果 coara 跑在你家里的 PC 上，而 App 后端在公网服务器，后端没法直接访问你本机的 `127.0.0.1:8765`——中间需要一条从公网回传本机的隧道。

注意这和 Matrix 用的隧道是**两条**：Matrix 那条指向本机的 GoMatrix（`:8008`），负责聊天同步；webhook 这条指向本机 `127.0.0.1:8765`，负责事件推送。仓库里 `scripts/tunnels/Start-AllTunnels.ps1` 负责把这类隧道拉起来；临时隧道重启后域名会变，脚本会同步更新后端配置。

数据流：

```text
手机 App → 后端 → POST https://<webhook 隧道>/webhook/<事件源 id>
  → 本机 127.0.0.1:8765 → 事件源接收 → 写入动态流 → Matrix 隐藏消息推给手机
```

## 9.7 边界与常见误解

- `file_watch` 依赖操作系统通知，某些网络盘不稳定，可以用 `interval_poll` 兜底；
- 事件源配置里的 `workspace` 指向已删除的空间时，事件无处可去；
- `webhook_secret` 不匹配的 POST 会被拒绝；
- cron 事件源在进程停机期间错过的触发不补发，重启后从当前时间重算下一次；
- 误解一："事件到了 Root 会立刻处理"——默认 `handle: park`，只进动态流；
- 误解二："挂住（park）的内容手机收不到通知"——红点照常推送，只是不弹对话；
- 误解三："事件源和提醒是一回事"——事件源面向工作空间（可驱动工作流、叫醒管家），提醒面向你本人（到点响一下）。

## 9.8 本章小结

- 事件源是四种传感器：file_watch / interval_poll / webhook / cron（webhook 默认端口 8765）；
- 一切先进动态流（收件箱）；`salience` 决定曝光（`high` 进前台待处理视图），`handle` 决定处置：`park`（默认，挂住等用户）、`janitor`（叫醒管家过目）；`ttl_seconds` 给低价值消息保质期；旧 `trigger_mode` 五档已废弃并被忽略（处置缺省 `park`）；工作流也可经 event 触发器消费同一事件源；
- 动态是每个空间的动态流：unread / read / archived 三态 + disposition 处置轨迹（pending/elevated/resolved/dismissed），已读水位线决定红点，每空间上限 500 条且永不挤掉未读；
- 查看入口：`/ws updates …`（含 `pending` 跨空间高显著未读 + 已呈阅）或 Web UI；janitor 用 `review` 工具过目处置；处理交给 coaras；
- 去重靠去重键 + 冷却，状态持久化；`/events reload` 热重载配置；
- 手机红点经 `[COARA_UPDATES]` 隐藏消息同步。
