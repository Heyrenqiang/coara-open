# 第 13 章 上下文窗口与压缩

## 13.1 为什么它有"记忆上限"

你跟 coara 聊的每一句、它调用的每个工具、工具返回的每段内容，都会追加进**消息历史**。每次请求大模型时，这段历史要完整发给模型——这就是它的"记忆"。

但模型一次能接收的输入有硬上限，叫**上下文窗口**（context window），按 token 计量。超出上限，请求直接失败。可以把窗口理解成一张固定长度的纸：系统提示词、消息历史、工具定义、动态提醒都写在这张纸上，写满就发不出去了。

一次复杂任务很容易把纸写满：多轮工具循环、大段文件内容、网页抓取结果、技能正文……几轮下来历史就可能从几千 token 膨胀到十几万。coara 的对策是：**快写满时，自动把旧内容摘要成一小段，腾出位置继续写**——这就是上下文压缩。

## 13.2 压缩什么时候发生

每次调用模型前，系统先估算当前输入占了多少 token，对比窗口大小：

- **没到窗口的 80%** → 正常调用，什么都不做
- **达到 80%** → 触发压缩
- 例外：消息总数不足 6 条时不压（太短没有摘要价值）；要压掉的部分占总历史不足 5% 时也跳过（避免为压而压）

窗口大小按优先级确定：模型自报的窗口（`provider.get_context_window()`）→ 默认 200,000 token。

## 13.3 压掉了什么，留下了什么

压缩时，历史被切成两段：

- **旧的前半段**：交给一个专门的摘要模型（`context.compression` 档案），压成一段密集的 `<state_snapshot>` 摘要，替换原来的几十上百条消息
- **新的后半段**：原样保留。默认保留最近 2 条消息，并按"配对安全"向前扩展（见进阶一节）

如果摘要调用失败、超时，或者摘要居然比原文还长，就退而求其次：**直接截断**，丢掉旧历史。这是可靠的兜底，但会彻底忘掉早期内容。

压缩完成后，系统还会补两条"备忘"，防止模型忘记正在飞的事情：

- **后台任务快照**：仍在运行的 bash 后台任务和后台子智能体清单
- **待办快照**：当前会话未完成的待办项

所以压缩之后，coara 依然知道自己该干什么——只是细节（比如某段文件的具体内容、某次讨论的原话）可能丢了。如果后面还需要，它会重新读文件、重新查证。

## 13.4 对你使用的影响

日常使用中你几乎察觉不到压缩，但有几点值得知道：

- **极长对话会丢早期细节**。如果任务的关键前提是很久以前口头交代的，压缩后它可能只剩摘要里的一句话。重要约定值得落到文件里（让它写进 README 或待办），而不是只存在于对话中
- **超长任务建议拆开**。需要读几百个文件、跑几十轮的活，更适合用工作流或子智能体分段完成——每个分身有自己的上下文，互不挤占
- **撞墙有提示**。压缩后仍超过窗口 90% 时，本轮会被硬阻断并提示上下文超限。这时候 `/new` 开新会话是最干净的解法
- **`/new` 是合法的清场方式**。它会清空整个消息历史和会话状态（顺带给宝箱上锁），重新开始。反过来，**没有**"删掉历史中某一条"的操作——历史前缀一旦参与过请求就不再改动，这是提示词缓存设计的一部分（详见 [第 14 章 提示词系统](./14-提示词系统.md)）
- **压缩不动磁盘**。它只改模型可见的上下文，已经执行的写文件、跑命令等副作用不受影响

## 13.5 进阶：估算、切点与配置

这一节给想深入了解机制的读者。

**Token 怎么估**

优先用模型接口返回的真实用量（含 cache）。工具栏的 context 占比也只看实报。

压缩触发与 guard 在热路径上只用廉价字符启发式做预算（不再跑离线 DeepSeek tokenizer 扫全文）；没有实报时也走启发式。若模型仍因上下文过长拒绝，会强制压缩一次再重试。图片不按 base64 文本算，每张开上限估 10,000 token。

**切点怎么找（split 安全）**

工具调用是成对的：assistant 发起的 tool_call 必须有对应的 TOOL_RESULT。如果保留下来的尾段里有一条 TOOL_RESULT，而它的 tool_call 被压进了摘要，模型服务商会拒绝请求。所以默认的"保留最近 2 条"只是起点：系统会检查保留段里有没有"孤儿"工具结果，有就把切点继续向前扩，直到所有工具调用都成对。比例模式（保留最近 30%）同理，从后往前维护一个未配对集合，只在集合为空处下刀。

**压缩后的水位线**

压缩完成后再评估一次：用量降到 75% 以下正常；≥75% 记一条 `context_warning` 警告事件；≥90% 记 `context_blocked` 并阻断本轮。这两个水位是内置常量，不可配置。

**可配置项**

`config.yaml` 的 `context_compression` 段：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `threshold` | 0.80 | 触发压缩的使用率阈值 |
| `preserve_ratio` | 0.30 | 比例模式下保留最近历史的比例 |
| `min_compressible_fraction` | 0.05 | 可压缩部分占比下限，低于则跳过 |

注意默认生效的是**条数策略**（保留最近 2 条，内部常量 `PRESERVE_LAST_N = 2`），`preserve_ratio` 只在代码里显式关闭条数策略后才生效。压缩前后还会运行 PreCompact / PostCompact 钩子（保存与恢复快照状态）。

## 13.6 本章小结

- 上下文窗口是模型单次输入的硬上限；coara 在每次请求前估算占用，80% 触发压缩
- 压缩 = 旧历史由摘要模型压成 `<state_snapshot>`，最近消息原样保留；失败则直接截断
- 压缩后注入后台任务与待办快照，进行中的工作不会丢
- 默认按条数保留（最近 2 条 + 配对安全扩展），比例 30% 是备选；split 安全保证工具调用不被拆散
- 日常使用：重要约定落盘、超长任务拆工作流、撞 90% 红线就 `/new`
- `context_compression` 配置段可调阈值与保留策略；警告 75%、阻断 90% 为内置常量
