# 第 19 章 配置系统

## 19.1 第一次启动要准备什么

把 coara 跑起来，最少要准备两个文件：

1. **`providers.yaml`**——告诉它去哪调大模型（服务商地址、API Key 的环境变量名、可用模型）
2. **`.env`**——放 API Key 本体

这两个文件放在 **`<coara_home>/system/`** 下。一键安装会自动播种 `providers.yaml`；`.env` 无需手动创建——首次启动 coara 时若没有任何可用 Key，会进入交互向导，粘贴 Key 回车即自动写入。第三个文件 `config.yaml`（全局行为配置）可选，不配也有默认值。

为什么要分两类文件？因为**秘密和行为分开管**：`.env` 里是 Key 和密码，永远不该进 git；YAML 里是行为参数，可读、可改、可以放心备份。

## 19.1a 改配置的推荐方式：配置助手对话

从 08-23 起，Web 配置页的全部 11 个 section 和 Android 配置页的全部卡片已**只读化**——纯展示，每 5 秒轮询刷新，不再提供编辑表单。改配置的推荐路径是配置页右下角的**配置助手**（浮动对话窗）：用自然语言告诉它你要改什么（"把默认模型换成 kimi k3"、"关掉遥测"），它会读取当前配置概况、理解意图后直接写入配置文件并生效。

配置助手每轮对话都会收到一份**配置概况注入**（从 config_manager 现算，含当前各 section 的实际值），sha1 指纹变更才注入，保证它看到的永远是最新状态。

文件直改（手动编辑 YAML）仍是底层路径，完全有效，但不再是推荐交互方式——配置助手能帮你校验值合法性、提示可用选项、避免语法错误。

## 19.2 coara Home：一切配置的起点

`coara_home` 是 coara 运行时数据的根目录（详见 [第 20 章 存储布局](./20-存储布局.md)），配置文件也到它下面找。系统按这个顺序确定它：

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | 已合并配置里的 `coara_home` 字段 | `config.yaml` 中写 `coara_home: "D:/coara"` |
| 2 | 仅开发机：仓根存在 `providers.yaml` | 从源码仓库运行时 home 落到仓根（见 [DEV_VS_USER.md](../DEV_VS_USER.md)） |
| 3 | 环境变量 `COARA_HOME` | Windows 上还会额外读注册表里的用户级/机器级设置 |
| 4 | 都不存在 | 用 `<当前目录>/.coara`——单工作空间试用模式 |

这里有个"鸡生蛋"问题：配置文件里可能写着 `coara_home`，但读配置文件得先知道 coara Home 在哪。系统的解法是两轮解析：先用环境变量做引导，读出一版初步配置；如果里面有 `coara_home` 字段，再以它为准重新确定路径。另外，若 `COARA_HOME` 指向多个候选（比如注册表里还有一个），系统优先选**下面已经有 `providers.yaml`** 的那个。

## 19.3 好几个配置文件，谁说了算

确定 coara Home 后，系统按固定顺序加载 YAML，**后加载的覆盖先加载的**：

```text
1. <coara_home>/system/providers.yaml
2. <coara_home>/system/config.yaml
3. <coara_home>/users/default/config.yaml     ← 用户级覆盖（可选）
4. <源码仓库根目录>/providers.yaml、config.yaml  ← 仅开发仓库存在，盖过 COARA_HOME 各层
5. llm_preferences.yaml                       ← /model --global 写入的全局默认，最后加载，对 agent.main 优先级最高
```

第 4 条只在你从源码仓库运行时存在：仓库根目录的配置盖过 COARA_HOME 各层，方便开发者携带自己的默认值；但 `llm_preferences.yaml` 仍在它之后加载。普通用户用安装包时没有第 4 层。

**覆盖不是整文件替换，而是深度合并**：同名的字典键递归合并，非字典值才是后者盖前者。举例：

```text
system/config.yaml:              users/default/config.yaml:
  matrix:                          matrix:
    homeserver: "http://a:8008"      user: "@bot:local"
    user: "@old:local"

合并结果:
  matrix:
    homeserver: "http://a:8008"   ← 来自 system/，用户级没碰它
    user: "@bot:local"            ← 用户级覆盖
```

所以用户级覆盖文件里**只写你想改的那几行**就够了，不用复制整份配置。

`.env` 的加载顺序类似：先 `<coara_home>/system/.env`，后仓库根目录 `.env`（后者覆盖同名变量）。

## 19.4 模型是怎么选出来的

`providers.yaml` 分三块：`providers`（服务商）、`llm_profiles`（场景档案）、`default_*`（默认值）。

**provider** 定义一个模型服务商怎么连：

```yaml
providers:
  minimax:
    driver: anthropic                 # 协议驱动：anthropic、openai 或 responses（DeepSeek V4）
    base_url: "https://api.minimaxi.com/anthropic"
    api_key_env: "ANTHROPIC_API_KEY"  # Key 从这个环境变量读，不写在文件里
    default_model: "MiniMax-M3"
    models:
      available:
        - id: "MiniMax-M3"
          function_calling: true      # 支不支持工具调用，很关键
          max_tokens: 131072
```

注意 API Key 不落盘在 YAML 里，只有一个环境变量名——Key 本体在 `.env`。

**Agnes**（OpenAI 兼容）Endpoint：

| 站点 | Base URL | Key |
|------|----------|-----|
| 国际站（默认） | `https://apihub.agnes-ai.cn/v1` | 国际站 Key |
| 国际站（备选） | `https://apihub.agnes-ai.com/v1` | 同一把国际站 Key |
| 国内站 | `https://api.agnes-ai.cn/v1` | 国内站 Key（与国际站不互通） |

**LLM profile** 是"场景 → 模型"的路由表。系统不同部位各用各的档案：

| profile | 谁在用 |
|---------|--------|
| `agent.main` | 主对话（Root 和分身默认） |
| `agent.xiaomi` / `agent.minimax` 等 | 备选服务商档案 |
| `agent.web_search` | 网页搜索摘要 |
| `context.compression` | 上下文压缩摘要 |
| `workflow.node` | 工作流节点 |

profile 支持 `inherit` 继承：`context.compression` 可以写成"继承 `agent.main`，只把 `max_tokens` 改成 2048、`temperature` 改成 0.2"。这样换主模型时所有场景跟着走，不用逐个改。

**默认值**：`default_provider` / `default_model` / `default_profile` 决定没指定时用谁。如果只配了一个 provider，系统自动选中它。

## 19.5 /model 切换到底改了什么

**切换权在端，生效面是空间。** 同一工作空间会话只有一份生效模型；共看该空间的
各端 chrome 立刻同步。聊天里 `/model` 的写入分两种：

- `/model <选择>`（不跟 `--global`）：改**当前工作空间**的 last-run 模型，
  写 `registry/workspaces.yaml` 该条目 `provider`/`model`，并切换该空间会话。
  每次正常对话还会自动把实际使用的模型回写为 last-run——这是空间的内核默认
  模型，重启加载与 janitor 触发都用它（见 [第 7 章](./07-工作空间与多工作空间.md)）。
- `/model --global <选择>`：改**全局默认**，写 `llm_preferences.yaml`（位置优先取
  `<当前目录>/.coara/llm_preferences.yaml`，不存在则用
  `<coara_home>/users/default/llm_preferences.yaml`），新/未对话空间跟随。

两个要点：

- 它只影响 `agent.main` 一个档案——上下文压缩、QC 等其他 profile 不跟着换
- 它不改 `providers.yaml`，删掉 llm_preferences.yaml 就回到 providers.yaml 的默认

不同端可看不同工作空间（视图独立）；**同一空间**共看时模型显示与执行一致，
不再支持「同空间各端各用各模型」。

## 19.7 环境变量

`.env` 在 `<coara_home>/system/.env` 和仓库根目录各加载一次（后者覆盖前者）。常用变量：

| 变量 | 用途 |
|------|------|
| `ANTHROPIC_API_KEY` | Anthropic 兼容服务商的 Key（MiniMax 走这里） |
| `OPENAI_API_KEY` | OpenAI 兼容服务商的 Key |
| `XIAOMIMIMO_API_KEY` | 小米 MiMo 的 Key |
| `AGNES_API_KEY` | Agnes Key（国际站 / 国内站不互通） |
| `AGNES_BASE_URL` | 可选；默认跟 `providers.yaml`（`https://apihub.agnes-ai.cn/v1`） |
| `COARA_HOME` | 全局数据根目录 |
| `COARA_MATRIX_HOMESERVER` / `COARA_MATRIX_USER` / `COARA_MATRIX_PASSWORD` | Matrix 连接三件套，优先于 `config.yaml` 的 `matrix:` 段 |
| `COARA_MATRIX_NOTIFY_ROOM` | 事件推送房间 ID |
| `COARA_VAULT_PASSWORD` | 宝箱主密码，用于可信环境自动解锁 |
| `COARA_WEB_PORT` | Web UI 端口（默认 8080） |
| `COARA_WAKE_SCAN_INTERVAL` | 工作流唤醒扫描间隔秒数（默认 5） |

## 19.8 哪些改动立即生效，哪些要重启

**不用重启的**：

| 操作 | 写到哪 | 生效范围 |
|------|--------|----------|
| `/model` | 当前空间 `registry/workspaces.yaml` 条目（last-run）；`/model --global` 写 `llm_preferences.yaml` | 该空间当前及以后会话的主模型 / 全局默认 |
| `/sandbox`、`/thinking` | 内存 | 仅本会话 |
| Web 仪表盘设置页 | 可写的 `config.yaml` / `providers.yaml` + 内存同步 | 立即 + 重启后保持 |
| WebUI 自动化/工作空间组（事项、事件源、提醒、工作空间增删启停） | 各域 store（走活 service） | 立即 |
| `/events reload` | 重读事件源定义 | 立即 |

**要重启的**：`config.yaml` 里大部分段落（`security`、`context_compression`、`matrix` 等）改了都要重启 coara。

系统要写回 `config.yaml` 或 `providers.yaml` 时（比如仪表盘保存设置），按这个顺序挑一个已存在的文件：`<coara_home>/system/` → 仓库根 → `<当前目录>/.coara/`（兜底，自动创建）。挑的都是下次启动一定会读到的路径，不会出现"写了但没生效"的死信（providers 写回位置在 2026-08 修复前曾落在读取链外）。

## 19.9 踩坑与误解

| 误解 | 实际 |
|------|------|
| 改了 `config.yaml` 立刻生效 | 大部分段落要重启；热改项见上一节 |
| `/model` 会改 `providers.yaml` | 不改 providers.yaml；空间 `/model` 写 registry 条目（last-run），`/model --global` 写 `llm_preferences.yaml` |
| `/model` 换了模型，压缩/QC 也跟着换 | 只影响 `agent.main` |
| 配置可以从 `<coara_home>/config/` 读 | 旧目录不再参与加载，只放 `system/`（`config/` 仅在从多个 `COARA_HOME` 候选中挑家目录时被参考） |
| 仪表盘上能看到 API Key 明文 | 不能，字段名含 password / api_key / token / secret 等的一律掩码成 `***` |
| 一个 provider 配错了整个系统起不来 | 单个条目校验失败只跳过该条并记警告；但一个可用 provider 都没有会直接拒绝启动并提示复制模板 |
| 环境变量和 YAML 各管各的 | Matrix 三件套等环境变量优先于 YAML 同名字段 |

## 19.10 进阶：加载流程与容错

完整加载顺序（供排查配置不生效时参考）：

```text
1. 加载 .env（system/.env → 仓库根 .env，后者覆盖）
2. 两轮解析确定 coara_home（先用空配置引导，再用合并后配置确认）
3. 按 §19.3 顺序逐个读 YAML，深度合并成一个原始字典
4. 硬性检查：system/ 或仓库根必须存在 providers.yaml，否则拒绝启动
5. 最后叠加 llm_preferences.yaml
6. 解析 providers / llm_profiles（单条校验失败记警告并跳过）
7. 确定 default_provider / default_model（只有一个 provider 时自动选中）
8. 组装成类型化的 CoaraConfig，并据此配置上下文压缩参数和执行沙箱
```

类型校验由 Pydantic 模型把关：字段类型不对、值越界的条目在加载时被跳过并记警告，不会带病启动。Web API 返回配置内容时，字段名含 `password`、`api_key`、`token`、`secret`、`auth` 等关键词的值统一替换为 `***`。

## 19.11 本章小结

- 最少两个文件：`system/providers.yaml`（模型从哪来）+ `system/.env`（Key 本体）；`config.yaml` 可选
- coara Home 按"配置字段 → `COARA_HOME` → `<当前目录>/.coara`"确定
- YAML 加载顺序：`system/` → 用户级覆盖 → 仓库根（最高）→ `llm_preferences.yaml`（最后），深度合并
- profile 是"场景 → 模型"的路由表，支持继承；`/model` 只改 `agent.main`
- 热改项只有少数（`/model`、几个聊天开关、仪表盘设置、`/events reload`），其余重启生效
- 敏感字段在 API 输出中自动掩码；配置条目出错跳过而非带病启动；完全没有 provider 则拒绝启动
