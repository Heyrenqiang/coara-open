# 三端收发机制梳理（内核 × CLI / Web / Matrix）

> 2026-09-09 依据磁盘代码（src/）梳理。目的：把「内核怎么收三端信息、怎么分发给三端」讲成一张清晰地图，并逐条判定问题真伪与优化路径。
> 相关现象：① 运行中 Ctrl+C 会退出 CLI（稳定复现）；② 子智能体结果显示在 CLI（疑似异常）；③ 子智能体运行时无法接续输入（重启后消失）。本文第 5 节逐条裁决。
>
> **现状（2026-09-11 更新）**：本文是 09-09 的快照。下列条目**本轮已解决**——输出帧带归属（`workspace_dir` / `session_id` / `turn_id` / `channel_id`；命中判据 `EndRegistry.deliver()` 的 `RouteResult.hit`，不再用 sender 返回值反推）、连接级兜底通道（全局槽只注册不注销；无在飞回合时帧经 standby 流落带 + 广播，不再无序号直推）、审批三端统一（三端同一套帧，`ApprovalCenter` + 定向 channel）、Ctrl+C 忙闲判定（本地回合流权威化：发 chat 即建流、收到服务端 `turn_end` 才 done）、B 类会话配置确认门（复用审批原语，fail-closed）、分隔线口径（只有 `/new` 与他端模型切换落帧，切空间一律不落；见 §7.5）。
> **仍开放**（按 §7 优先级处理）：忙闲权威帧（`busy_state`，§5.5 R1 只部分收敛）、事件白名单单点化（R2）、模块正文并入 EndRegistry（R3）、正文三表达定边界（R4）、UnifiedScheduler 空转与双 CLI 客户端清理（P5/P6）、P2/P4 的 UX 残留。未标注「已解决」的条目一律按本文原结论处理。

## 1. 总体架构一句话

**一个内核进程（tray 常驻），三种端（CLI attach / Web / Matrix）平等接入；端只是渲染器，不持状态。**

```
                    ┌──────────────────────────────────────┐
                    │  内核进程（单 asyncio event loop）      │
                    │  RootCoara ── 每工作空间一个 session    │
                    │  ┌────────────────────────────────┐   │
                    │  │ 回合执行器 turn loop             │   │
                    │  │  每迭代头 drain 接续队列 → 注入 → LLM │   │
                    │  └────────────────────────────────┘   │
                    └───────┬───────────────────┬───────────┘
        process_message /  │                   │  EndRegistry 输出帧 / trace 广播
        submit_continuation │                   │  (正文 chunk + 工具 diff → 端 sender)
        ┌───────────────────┴───────┐    ┌──────┴──────────────────┐
        │ CLI attach（WS /ws/attach） │    │ Web（WS /ws + REST）      │
        │ Matrix（nio /sync → 房间）  │    │（均为独立进程/浏览器）      │
        └─────────────────────────────┘    └─────────────────────────┘
```

关键推论：
- 端退出 ≠ 回合取消。端断连只是 sender 注销，内核里的回合照跑，重连可回放（web/attach 有 ring buffer；matrix 房间即历史）。
- 端不直接调 LLM、不建状态。一切经 `process_message` / `submit_continuation_input` 两个内核入口。
- janitor / daily 是内核内维护协程，不经任何端，与端存活无关。

## 2. 入站：信息怎么进内核

### 2.1 只有两个统一入口

| 入口 | 用途 | 位置 |
|---|---|---|
| `process_message(content, source=…)` | 空闲时开新回合；async generator，边跑边产 chunk | src/coara/base.py:389，Root 代理 root.py:609 |
| `submit_continuation_input(text, source=…)` | 忙时跟话，入 `_continuation_inputs` 缓冲队列 | src/coara/base.py:1036，Root 代理 root.py:631 |

**各端拿到用户输入后的唯一决策：内核忙不忙？** 空闲 → process_message；忙 → submit_continuation_input。这个「忙闲判定」是本架构的命门，问题①②③都从它派生（见 §4、§5）。

### 2.2 入站消息分类

| 种类 | 三端路径 | 忙时处置 | 进 LLM 回合 |
|---|---|---|---|
| 用户文本 | attach chat 帧 / web chat / matrix 房间消息 | 入接续队列 | 是 |
| 图片/媒体 | matrix 先经 1.5s 去抖聚合（media_batch） | 带 image_blocks 入同一队列 | 是 |
| slash 命令 | 各端命令层 | 命令层直接执行 | 否 |
| 审批答复 | approval_reply 帧 / 自定义 msgtype | ApprovalCenter.resolve 推 Future，工具继续 | 否（旁路） |
| 后台任务完成 | EventBus 订阅（root.py:1206） | 忙→入队注入；闲→唤醒新回合 source=background | 是 |
| 子智能体主动消息 | interact 工具 | 入队（`<子智能体消息>`） | 下迭代注入 |
| 提醒 / 事件源 | 落工作空间收件箱 + push | 不占回合 | 否 |

### 2.3 常被误会的 UnifiedScheduler

`src/coara/scheduler.py` 的 FIFO 队列与消费循环仍在，但消费端 `inbound_router.py` 只 debug 忽略一切——WDL 执行层剥离后已无生产者。**它是空转死代码，不是入站通道**。真正入站只有 §2.1 两个入口。

## 3. 出站：内核怎么分发

### 3.1 输出帧（正文 + 工具 diff）——唯一事实源

内核输出统一成帧：`{"kind":"chunk","text":…}` / `{"kind":"diff",…}`，经 **EndRegistry** 按 `(source, session_id, channel_id)` 路由到端注册的 sender。

- 注册：各端在回合启动时注册本回合的显示通道（sender 闭包捕获连接/房间）；attach 多连接靠 `_end_channel_id` 精确归位。
- 归属：帧上带「最近注入段」的 source——回合开头开 seg0，每次 mid-turn 跟话开新段并换归属端。所以**正文回给最后说话的那个端**。
- 无通道时静默丢弃；后台唤醒回合无端通道时靠 `session_origin` 兜底。
- **已解决（2026-09-11）**：帧一律带归属（`workspace_dir` / `session_id` / `turn_id`，attach 另带 `channel_id`），端侧按归属做边界守卫，不再靠「猜是哪条线」；命中判据与执行结果分离（`deliver()` 返回 `RouteResult.hit`，同步 sender 返回 `None` 也算命中），未命中记 WARNING 带查找键与现有键。

### 3.2 并行辅助通道

| 通道 | 管什么 | 消费端 |
|---|---|---|
| EndRegistry 输出帧 | 正文 chunk + 工具 diff | attach / web / matrix |
| TurnStream | 端内回合流：ring buffer（≤200 帧）→ 落带（分配 `view_seq`）→ 广播；断连重连 replay | attach / web |
| standby 流 | 无在飞回合流时的帧出口（按 `(session, workspace)` 复用，上限 8）——落带与广播同源同序，帧上带 `view_seq` 与归属 | web |
| trace 广播 | spinner / 活动树 / 工具行 / 排队等生命周期事件（100ms 微批） | web / attach（matrix 不经此） |
| matrix room 直投 | notify / diff 信封 / 子代理结果直推 | matrix |
| conversation_message | 仅进 trace 与录像带，**不推 attach** | 无显示端 |

| 阶段 | 形态 | 通道 |
|---|---|---|
| 运行期 | 活动树（◌/✓✗ 动态行） | trace 广播 subagent_* 事件 → 各端消费 |

## 4. 忙闲判定与接续输入（核心机制）

### 4.1 串行裁决（内核真实忙）

- 每会话一把 `_process_lock`（FIFO 锁）+ TurnQueue 记账。
- 回合进行中来了新 process_message → 排队等锁（不是接续）。
- 回合内跟话 → 入 `_continuation_inputs`，turn loop **每迭代头 drain**（turn_orchestrator.py:305），注入历史并开 mid_turn 新段。
- LLM 已收尾但队列有剩 → 发起端宿主 drain 后按项 source 开新回合补发（continuation_leftover），不丢。

### 4.2 端侧忙闲镜像（问题之源）

内核真实忙 = `_process_lock` 被占。但**端不能直接读内核内存**（CLI/Web 是独立进程），它维护一份本地镜像 `has_active_turn()`：

- attach 镜像 = 本地乐观位（发 chat 置 True）+ 事件推断（收到 turn_start/turn_end/trace 置位清位）。
- 镜像与内核真实状态**没有强一致校验**。

一切端侧决策都压在这个镜像上：Ctrl+C 是中断还是退出、输入走接续还是排队。镜像失真 → 决策错。

## 6. 优化方案

### 方案 A（P1 根治）：Ctrl+C 语义改为「先中断，后退出」

现状：空闲 Ctrl+C → 直接退 CLI。
改为：Ctrl+C 一律先发 interrupt 帧到内核（本地无回合也让内核裁决）→ 内核回「无活跃回合」时提示「再按一次 Ctrl+C 或 /exit 退出」。退出需要两次 Ctrl+C（或保留 Ctrl+D / /exit）。

- 改动点：cli/session.py `_handle_ctrl_c`/`_resolve_running_sigint_action`（531-540）、attached_chat_runner.py `_interrupt_current_turn_nowait`（259-281）改为发帧后等内核回执而非本地判空闲即 break；attach_ws.py interrupt 处理（323-330）补「无活跃回合」回执帧。
- 附带收益：想中断「它端正在跑的回合」时不再误退 CLI（当前会退）。
- 代价：空闲 Ctrl+C 不再一步退出，需适应；已有 /exit、Ctrl+D 出口。

### 方案 B（P1/P4 根因）：忙闲判定改内核权威推送

让镜像不再靠事件拼凑：attach 握手时内核下发当前真实 busy 状态，之后内核在回合边界（turn 真正开始/结束、队列变化）主动推送 `busy_state` 帧；镜像只信内核帧，本地乐观位仅作断连期兜底。

- 改动点：attach_ws.py 回合生命周期处加 busy_state 帧；root_shim.py 镜像维护（35-45、661-703）改为帧驱动；handshake 补全量状态。
- 收益：Ctrl+C 语义、接续/新回合分流、排队提示全部基于真实状态，三类失真场景同时消除。
- 风险：时序敏感（断连/重连、帧乱序），需与 TurnStream replay 对齐；改动面中等。

### 方案 C（P4）：排队可见化

turn_queued 事件补 `position`/`queue_depth`（内核 turn_queue_depth 已有，base.py:1123）；CLI 排队行显示「第 N 位」；接续被转新回合时显式提示而非静默。

- 改动点：attach_ws.py:582 事件载荷补深度；CLI 显示层（session.py 排队行）。

### 方案 D（P5-P8）：清理冗余

## 7.5 端行为语义（用户 2026-09-09 裁决）

端上所有触达内核的行为分六类，语义如下（裁决人：用户）。

**A 回合控制**
- Ctrl+C（CLI）判定链：输入区有内容 → 先清内容；无内容 → 本端有进行中的对话 → 打断；无对话 → 退出 CLI。三端打断只作用于各自所在的端（web/手机只在运行中有打断按钮，点击即打断当前会话）。/stop 命令**移除**（Ctrl+C 已覆盖，无独立价值）。
- 输入对话 / 接续 / 图片 / 文件发送：任何端随时可发 = 抢归属（开新段），维持现状。
- 审批答复 / vault 解锁 / plan 批准：与输入对话/接续同性质（回合内挂起交互），维持现状。

**B 会话配置（/new /model /thinking /tools /sandbox /stream /compact）**
- 其他端占着内核时执行 → **先提醒，用户确认后才执行**（不能静默改共享会话）。空闲/本端归属时直接执行。
- 待实现：会话配置类操作的确认门（端侧弹确认 or 排队提示）。

**C 视图与空间（/ws switch、attach pin、web 切视图）**
- 与会话无关，随意操作。

**D 只读查询（/status /help /log /usage /report /message /events /vault list /qrcode /login）**
- 不影响任何状态，随意操作。
- `/workflow list` 清掉（工作流已外移 WDL）；工作流命令/工具去留见调研结论（编排工具保留）。

**E 生命周期（/restart /exit）**
- 两个都**移除**（内核不自拉起不重启；退出 CLI 由 Ctrl+C 空闲路径承担）。

**F 显示偏好（/theme）**
- 与会话无关，随意操作。

> 本质规则：回合内状态 → 归属端独占（A）；会话级状态 → 归属端即时动、非归属端确认后动（B）；端自身/只读 → 随时（C/D/F）。

**分隔线口径（2026-09-11 裁决落地）**：只有两个显式动作落分隔帧——新会话（`/new`）与他端模型切换（`llm_switched` 事件路径）；切空间一律不落（服务端不落，端上也不自插：自插的线会被下一次 hydrate 冲掉并污染该空间缓存）。按时间间隔自动出的线**尚缺**。
