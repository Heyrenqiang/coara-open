# 出站通道收敛设计（草案）

> **本文是设计与迁移方案，不是现行规范**。现行口径见 [消息渲染契约.md](./消息渲染契约.md)（Web 显示唯一权威）· [三端运行显示出站.md](./三端运行显示出站.md)（Ⅰ/Ⅱ/Ⅲ 分类与两把尺）· [架构契约.md](./架构契约.md)（内核不变量）。
> 状态：2026-09-25 起草。落地前需逐条评审；每一步都是可独立交付、可单独回退的。

## 一、现状：一帧内容要走几条路

内核产出的一帧内容（正文 chunk / 工具行 / diff / 子智能体结果 / 命令结果…），今天可能经由以下任意组合抵达端上：

| # | 通道 | 谁在用 | 载体 |
|---|------|--------|------|
| 1 | **EndRegistry 定向投递** | 三端主路径 | 按 `(source, session_id[, channel_id])` 查 sender |
| 2 | **TurnStream 实时帧** | web 聊天区、CLI attach 的跟话流 | 微批 16ms → 先落带（分配 `view_seq`）后广播 |
| 3 | **trace 广播** | Web 侧栏/看板、CLI 活动区 | EventBus → TraceStore → WS，按 `payload.source` 门控 |
| 4 | **Matrix 房间直投** | 手机 | `dispatch_matrix_end_frame` 封 `[COARA_*]` 信封发房间 |
| 5 | **落带** | 全部（存档与刷新回放） | `view_recorder.record_view_frame` → `WebViewStore.append_event` |
| 6 | **读端归集** | web hydrate / 手机端解析 | `subagent_texts`、三张折叠映射、房间消息历史 |

**设计意图是对的**：每条通道服务一种端形态（浏览器要可刷新、手机要房间历史、CLI 要 scrollback），且「端独立」是内核不变量。
**代价**：同一件事——**这帧归谁、长什么样、要不要落带**——在每条通道都实现了一遍。

## 二、问题不是"通道多"，而是"规则被复制"

通道数量本身不是病；病在**归属判定与帧形状在每条通道各写一份**。已发生的事故都是同一类：

| 事故 | 根因 | 状态 |
|------|------|------|
| 子智能体正文漏进 web 主消息流（09-25） | 跟话通道抄了主通道的映射，抄漏了 kind 分派与父标识折叠 | 已修（出口唯一化） |
| 手机跟话通道漏子智能体分支（09-24） | 同上，手机侧复制时漏 | 已修 |
| web 视图带曾对 `subagent_chunk` 豁免落带（09-25） | 落带规则在写入侧另写一份 | 已修 |
| 注入信封漏成气泡（09-24） | 三端出口各自实现拦法，写端拦了、出口没拦 | 已修（出口统一按 `is_preformatted_injection`） |
| 手机 `[COARA_DIRTREE]` 未知信封漏成气泡（09-10） | 两端信封常量各写各的 | 已修（信封真源 + 生成） |
| 隐藏工具行清单三端各写（09-25） | 显示口径没有真源 | 已修（display_rules 下沉） |
| 跟话通道守卫三端各写（09-25） | 通道类型判定没有真源 | 已修（注册表 `kind` / `is_followup`） |

前六条的共同结构：**同一份规则，N 份实现，改一处漏一处**。三条已经收敛（信封、显示口径、通道类型），**剩下的最大一块是"帧的形状与落带口径"**。

## 三、仍然存在的形状差（真实清单）

契约 §十一「已知限制」里拖着三条，本质都是"实时路与落带路不同构"：

1. `divider` 帧**只落带不广播**——实时看不到，刷新后凭空多一条
2. 实时 `file` 帧**不带 `view_seq`**，且 kind 名与落带的 `files` 不一致——刷新后形态变一次
3. `command_result` 实时**无序号**，落带被投影成 `turn_start + chunk`——同一件事两种形态

另有两条通道级差异：

4. **CLI attach 不读落带**：它靠自己的 TurnStream + ring buffer 回放；断连重连的能力与 web 不等价
5. **trace 广播兼了两职**：既做观测（看板/调试），又在若干场景实际承担内容投递（侧栏工具详情、活动树）。观测通道承担内容投递，就会出现"某端独家少一次"的问题

还有两处兜底路径值得登记（它们是必要的，但要可观测）：

6. `standby` 流：没有在飞回合时的帧出口（上限 8 条）
7. `EndRegistry._tape_orphan`：无通道时兜底落带（"没人看 ≠ 不该记"）

## 四、目标模型：落带是唯一事实，实时帧只是加速器

一句话定调：

> **端上看到的每一条内容，都必须能从落带形状完整重建；实时帧只是把同一条内容提前送到端上的加速器。**

推论（作为后续判据）：

- **R1 形状同源**：实时帧与落带帧必须由**同一个构造函数**产出，不允许两条路各自拼字段。
- **R2 覆盖完整**：任何会出现在端上的内容，都必须有落带（进带 ≠ 上屏，但上屏必须可回放）。
- **R3 差异只允许是时间差**：实时先到、落带后到可以；形状不同、字段缺失不行。
- **R4 观测与内容分家**：trace 通道只服务观测；内容投递一律走通道 1/2/4。
- **R5 兜底可观测**：standby / orphan 落带必须计数可查，不许静默。

## 五、迁移步骤（每步独立可交付、可回退）

**S1 帧工厂（形状同源）**
把每条通道的帧构造收敛到一个模块（例如 `src/coara/output_frames.py`）：`chunk_frame(...)` / `tool_frame(...)` / `diff_frame(...)` / `subagent_chunk_frame(...)` / `divider_frame(...)` / `files_frame(...)` …
实时路与落带路都调它。**行为不变**（字段逐字对齐现状），只把"拼字段"从 N 处变成一处。
判据：新增回归——同一事件经实时路与落带路产出的帧，除 `view_seq`/时间戳外逐字段相等。

**S2 补齐三处形状差**
`divider` 补广播；实时 `file` 帧带 `view_seq` 并与落带 `files` 同名同形；`command_result` 实时帧带 `view_seq`（由落带回填），不再"实时一张卡、刷新一段正文"。
判据：契约 §十一 的那三条从清单里划掉；前端 selftest 增加"刷新前后同形"断言。

**S3 CLI 读落带（或同源投影）**
让 CLI attach 的回放走与 web 同一份权威（读落带或读同一构造的投影），断连重连的行为与 web 对齐。
风险：CLI 现有 ring buffer 与滚动区语义要保住（它是端内 UI 态），只换"内容来源"。
判据：断连重连用例（跨回合、跨空间）+ 与 web 的对照目检。

**S4 trace 通道降级为纯观测**
把仍在承担内容投递的几个点（侧栏工具详情、活动树补给行）改为消费"落带形状"，trace 只留观测字段。
风险：前端侧栏与活动树是主要消费方，需要逐页确认；这两处本就有 REST 兜底（`/api/v1/tool-call`）。
判据：把 WS trace 订阅临时关掉，端上内容仍完整（只有观测信息缺失）。

**S5 兜底收敛与可观测**
`standby` 流与 orphan 落带合并成一个"无主线兜底"，并暴露计数（沿用现有 `/status` 或日志）。
判据：持续压测下兜底次数可查、为 0 时可确认无静默丢弃。

## 六、边界：什么不做

- 不取消端独立，不取消按段归属（这是内核不变量，不是冗余）
- 不让 web 依赖手机的房间，也不让手机依赖 web 的视图带（各端仍是自己的投影）
- 不为省事把三端合并成一个端抽象（形态差异是真实的：刷新回放 / 房间历史 / scrollback）
- 不在这一批顺手动"归属载体"（那是另一批的事，见第五节之外）

## 七、与其它批次的关系

- **依赖**：本批 S1 是"帧形状"的收敛，与"显示口径下沉"（已完成）同源思路；都属"把复制品收拢成真源"。
- **不依赖**：S2–S5 各自独立，可以只做 S1+S2 就停。
- **与归属载体收敛（另一批）的关系**：那一批动"谁该收到这帧"；本批动"这帧长什么样、要不要落带"。两者正交，可分别推进；但若两批都做，**先做本批**——形状稳定后，归属改造的回归面会小很多。

## 八、验收总判据

1. 任一时刻，端上内容都能由落带形状完整重建（关掉实时帧仍能看到全部内容）
2. 同一事件经实时路与落带路产出的帧，除序号与时间戳外逐字段相等
3. trace 通道关闭时，端上内容不缺（只缺观测信息）
4. 兜底路径（standby / orphan）计数可查，长期为 0
5. 三端主路径目检：刷新、切空间、断连重连、跨回合跟话、子智能体折叠三组，行为与改造前一致
