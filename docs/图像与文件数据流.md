# 图像与文件数据流（三端）与工作流数据流

> **一句话总览**：不管用户从 CLI、Web 还是手机发图发文件，内核都把它们落到工作空间唯一的 `uploads/` 目录，图片压缩成 base64 视觉块随消息喂给模型、文件按类型内联成文本或只给绝对路径；反过来模型产出的文件经 `send_file` 工具按「当前说话的端」路由回 Web 或手机。工作流则是另一张数据流：会话里用 `orchestrator` 编一张内存图（flow），写穿投影成 WDL 草案，真正的执行由独立 wdl 软件承担，内核不再跑工作流实例。

---

## 一、总览：三端入口 → 统一落盘 → 处理 → 喂模型 → 出站

- **三端入口**
  - CLI：`Alt+V` 贴剪贴板图 / 拖入图片路径（`src/cli/image_paste.py`、`src/utils/clipboard_image.py`）
  - Web：输入区粘贴/拖拽/选择 → 先经 `POST /api/upload` 落盘，发送时 WS 帧带 `image_refs` / `file_refs`（`src/ui/handlers/files.py`）
  - 手机（Matrix）：`m.image` / `m.file` 事件到 GoMatrix 房间，内核经 nio 下载 mxc（`src/matrix_client/media_inbound.py`）
- **统一落盘**：`<工作空间>/uploads/`，目录名唯一真源 `src/core/workspace_layout.py` 的 `UPLOAD_DIR_NAME = "uploads"`；文件名净化（只取末段、Windows 保留名、重名 `_N`）
- **处理**
  - 图片：视觉门控（`src/llm/vision.py`）→ Pillow 压缩缩放（`src/utils/image_processor.py`，detail=high，2048px / 2500 个 32px patch 预算）→ base64 视觉块
  - 文件：按扩展名分类——文本照常内联、Office/PDF 提取成文本内联、纯二进制只给绝对路径（`src/ui/handlers/files.py::_append_text_file_refs`）
- **喂模型**：文本 + 图片块组装成一条多模态 user 消息进 `message_history`，base64 驻留历史；压缩时剥图占位、trace 里瘦身占位
- **出站**：`send_file` 工具 → `OutboundFileRouter` 按当前回合端路由 → Web 桥（复制到投递目录 + WS 推送）或 Matrix 桥（mxc 上传 + 房间消息）

## 二、图像链细节

### 2.1 视觉门控（三端同尺）

- 判定真源：`src/llm/vision.py`。
- 输入侧（发送前提示）用 `model_vision_explicit`：**只认显式证据**——providers.yaml `models.available[]` 里 `vision: true` / `input_modalities` 含 image 才判支持，`vision: false` 或模态不含 image 才拦；拿不到证据（None）一律放行，交后端转换层处理。三端行为一致：**丢图留文**——图片被省略，文字（caption/正文）照常发送（见 `src/matrix_client/media_inbound.py` 的门控分支与提示文案「图片已省略，文字内容照常发送」）。
- 后端转换层用 `model_supports_vision`：fail-closed，判不支持时图片块被替换为占位文案 `[图片内容：当前模型不支持图像输入，已省略]`（常量 `IMAGE_OMITTED_PLACEHOLDER`），避免非视觉模型收到图片被服务端 400。
- 白名单只剩通用 marker（型号名含 `vision`），具体视觉模型一律由配置显式声明。

### 2.2 压缩参数（detail=high 三端归一）

真源 `src/utils/image_processor.py`：

| 参数 | 值 | 代码位置 |
|------|-----|----------|
| detail=high 尺寸上限 | 2048px 边长、2500 个 32px patch | `_HIGH_LIMITS = (2048, 2_500)` |
| detail=low / original | 1024px / 1000 patch、6000px / 10000 patch | `_LOW_LIMITS` / `_ORIGINAL_LIMITS` |
| base64 大小上限 | 5MB（API limit） | `MAX_IMAGE_BASE64_SIZE = 5 * 1024 * 1024` |
| 无 detail 旧兜底 | 2000px thumbnail | `MAX_IMAGE_DIMENSION = 2000` |
| JPEG 质量 | 85 起，最低 30，每次降 15；仍超限按 0.75/0.5/0.25 缩放重试 | `_encode_and_compress` |
| Pillow 缺失 | 不压缩、原样 base64 放行 + warning（宁可大图慢也不丢用户内容） | `process_image_for_api` / `process_image_bytes_for_api` |

三端统一用 `detail="high"`：Matrix 侧 `src/matrix_client/remote_vision.py::image_block_from_bytes` 调 `process_image_bytes_for_api(data, detail="high")`；Web 侧 `src/ui/handlers/files.py::_resolve_image_refs` 调 `image_bytes_blocks_with_notice(raw, "high")`；CLI 经 `src/cli/image_paste.py` 走同一套。Pillow 解码失败的图：Web 端小图（≤5MB，`_FALLBACK_RAW_IMAGE_MAX_BYTES`）回退原始 base64 不丢图，大图放弃并记 warning。

### 2.3 张数上限：9 张，三端共享

- 常量：`MAX_IMAGE_BATCH_COUNT = 9`，定义在 `src/matrix_client/remote_vision.py`。
- 三处消费：Matrix 聚合批（`media_batch.py::MAX_BATCH_IMAGES`）、Web（`web_server.py` 收到 `image_refs` 超长即截断并提示「一次最多发送 9 张图片」）、CLI（`src/cli/session.py::_gate_cli_images` 同款截断提示）。
- Matrix 侧还有一层**批量聚合**（`src/matrix_client/media_batch.py`）：手机连拍/多选是「每张图一条 Matrix 消息」，聚合器按房间在去抖窗口（默认 1.5 秒，最后一张到达后计时，可经 `COARA_MATRIX_MEDIA_BATCH_MS` 调）内合并，满 9 张立即投递；合并成**一条** user 消息（文本 + 图1 + 图2…），文本消息到达前会先 `flush_now` 保序。

### 2.4 base64 驻留三处与瘦身

图片块的 base64 形态 `{type: "image", source: {type: "base64", media_type, data}}`（`src/utils/multimodal_content.py::image_block_from_base64`）随 user 消息进 `message_history`，base64 本体**永久驻留历史**。为控制它的代价，有两处瘦身：

1. **压缩剥图**（`src/context/window.py::_strip_images_for_compression`）：上下文超限自动压缩时，压缩 LLM 的**输入**里 image 块原位替换为 `[图片]` 文本占位，`message_history` 本体不动（模型回看仍能看到原图）。
2. **trace 瘦身**（`src/utils/message_content.py::message_content_to_text`）：trace/dashboard 展示时图片块渲染为 `[图片: media_type, NKB]`（N 按 base64 长度折算原始字节，永不回显 base64），避免整块 base64 被 `json.dumps` 放大进 trace。

### 2.5 原图落盘（Matrix 侧）

视觉块是压缩产物，落盘必须留原图：`remote_vision.build_image_blocks_from_matrix_upload` 的 `originals` 参数按块同序保留原始字节，`media_inbound._save_uploads` 在**回调入口**就把原图写进 `uploads/`（文件名优先端上声明名，缺省按 mime 补扩展名），投递文本注入绝对路径（「发送了图片（用户附件，已存入工作空间 uploads/）: <绝对路径>」），模型可一步 `read` 读原图。web /api/upload 上传的原文件本就落盘，天然同形态。落盘同时记「最近文件」索引（`src/records/recent_files.py`，origin=inbound）。

## 三、文件链细节（按 kind 分类）

Web 端文件附件（`file_refs`）走 `src/ui/handlers/files.py::_append_text_file_refs`，与 read 工具的文本提取能力对齐：

| 类别 | 扩展名 | 处理方式 |
|------|--------|----------|
| Office | `.docx` `.xlsx` `.pptx` | 复用文档读取器（word/excel/pptx reader）提取成 Markdown-ish 文本内联进消息 |
| PDF | `.pdf` | `read_pdf_document` 提取文本内联 |
| 纯二进制 | `.zip` `.exe` `.mp4` `.mp3` `.db` 等（`BINARY_SUFFIXES`） | 无可提取文本，只给绝对路径提示：「（二进制文件，位于 …，可用 read/shell 工具处理）」 |
| 其余按文本 | 一切不在上述两类的 | UTF-8 解码；含 NUL 字节或大量替换符判二进制走路径提示 |

内联文本单附件上限 `_MAX_TEXT_FILE_CHARS = 100_000` 字符（`web_server.py`），超出截断并标注「附件已截断」。磁盘读 + 解码跑 worker 线程（`asyncio.to_thread`）不阻塞事件循环。

Matrix 侧 `m.file`（`media_inbound.process_matrix_media_inbound`）：**不内联内容**，下载 → 20MB 上限校验（`MAX_MATRIX_UPLOAD_BYTES`，与 GoMatrix 服务端 `MaxRequestSize` 对齐）→ 落盘 `uploads/` → 注入文本「发送了文件（用户附件，已存入工作空间 uploads/）: <绝对路径>」+ 附言（caption）。端上无附言时 body 回落成文件名，那不算正文。模型拿到绝对路径后自己 `read`。

各端上传上限汇总：

| 端 | 上限 | 代码 |
|----|------|------|
| Web `/api/upload` | 单文件 50MB（流式写盘，超限 413 删半成品） | `src/ui/web_upload_limits.py::MAX_UPLOAD_FILE_BYTES` |
| Matrix m.file / m.image | 20MB（对齐 gomatrix 服务端） | `media_inbound.MAX_MATRIX_UPLOAD_BYTES`；mxc 下载另设 30s 超时 + 20MB 上限（`remote_vision._DOWNLOAD_*`） |
| 手机出站 send_file | 20MB 拒绝并明确提示「不要改发 Web 端」 | `src/matrix_client/file_bridge.py` |
| Web 出站 | 200MB 软上限（防一次调用填满磁盘） | `src/ui/web_file_bridge.py::_MAX_OUTBOUND_BYTES` |

## 四、各端差异表

| 维度 | CLI | Web | 手机（Matrix） |
|------|-----|-----|----------------|
| 图片入口 | `Alt+V` 读剪贴板（PowerShell/osascript/xclip，见 `src/utils/clipboard_image.py`）+ 图片路径识别；输入框显示 `[图片N]` 占位符，破坏占位符即撤回 | 粘贴/拖拽/选择 → `POST /api/upload` 落盘 → WS chat 帧带 `image_refs` | App 发 `m.image`（批量聚合 1.5s 去抖合并成一条） |
| 文件入口 | 无专用附件通道（直接用绝对路径对话） | 同上，`file_refs` | App 发 `m.file`，文字附言随文件走 |
| 单文件上限 | —（剪贴板图无独立上限，压缩到 5MB base64） | 50MB | 20MB |
| 张数上限 | 9 张（共享常量） | 9 张（共享常量） | 9 张（共享常量，满即投） |
| 发送前预览 | 占位符文字 | 输入区 blob URL 即刻缩略图（`ChatInput.tsx` 的 `previewUrl`），发送后气泡内联渲染（attachments `is_image`） | 输入区草稿图预览 `LocalImagePreviewScreen`（直读 Uri），发送后气泡内缩略图 |
| 文件预览 | 终端点 Markdown 链接（`local_open` 查 uploads/） | `/file` 预览页（渲染态：图片/HTML sandbox iframe/PDF/Office 文本），`uploadRawUrl` 取原字节 | 五层架构：FileRef → FileKind（classifyFile 单点分类：图片/HTML/文本/Markdown/PDF/Office/APK…）→ FileRoute → FilePreviewTopBar（恒定占位顶栏）→ FileLocalCopy；PDF 用系统 PdfRenderer 逐页渲染，视频 Media3 ExoPlayer |
| 门控提示 | `[yellow]` 提示丢图留文 | 错误帧提示 | 房间内文字提示 |

工具输出另有一层与附件无关但同类的体量控制：模型侧工具结果超 `spill_threshold_bytes`（默认 25,000 字节）即 spill 落盘、批次合计预算 `batch_budget_bytes`（默认 200,000 字节），见 `src/core/types.py::ToolOutputStoreConfig` 与 `src/runtime/spill_policy.py`。

## 五、出站链（模型 → 用户）

- 工具：`send_file`（`src/tools/builtin/integration/send_file.py`），**仅 web / matrix 回合可用**（`_ALLOWED_SOURCES`），CLI/后台/事件回合直接报错「当前端不支持」。路径必须是绝对路径。
- 路由：`OutboundFileRouter`（`outbound_file.py`）注册 Matrix 桥与 Web 桥互不干扰；`target=auto` 选**恰好一个**目的地——显式 room_id → Matrix；当前是 Web 回合 → Web；Matrix 远端回合 → Matrix；CLI/本地无端 → 不投递。绝不双发。
- 归属：`OutboundOwner`（workspace_dir / session_id / turn_id）由 executor 经 `bind_runtime_context` 注入调用当时快照，投递可能异步完成（视频几分钟），**绝不能**用「完成那一刻的端视图」推归属——那是「nx 请求的视频落到 v8 线」的根因修复点。
- Web 桥（`src/ui/web_file_bridge.py`）：复制文件到投递目录（200MB 软上限）→ 生成不透明 file_id → WS 推 `{type: "file", ...}` 帧 → 端上经 `/api/outbound-files/{file_id}`（token 校验）取件；可选 `persist` 写会话事件带，刷新/切页后附件仍在。
- Matrix 桥（`src/matrix_client/file_bridge.py`）：20MB 上限校验（超限明确报错并禁止改发他端）→ `_matrix/media/v3/upload`（r0 兜底）拿 mxc → 按是否图片发 `m.image` / `m.file` 房间消息。

## 六、工作流数据流（flow / orchestrator / WDL）

WDL **执行**在独立软件（仓库 `wdl/`）。内核做两件事：会话内编排内存图（flow）、生产与托管 WDL 草案。工作流终态由 wdl 软件自管（`inbound_router` 不消费终态回投）。

链路分四段：

1. **会话编排（内存图）**
   - 挂起工具 `orchestrator`（`src/tools/builtin/orchestrator/orchestrator.py`，平时不占工具面，`tool(activate)` 揭示）提供 spawn/run/wait/status/save/load 等 action。
   - 一组 `spawn` 调用在 `FlowCoordinator`（`src/coara/flow_coordinator.py`）里唯一确定一张 `FlowGraph`：节点只有一种（智能体，id 即名字、task 即完整任务指令），边是唯一拓扑（depends_on / routes_to 都是边的只读视图）。没有 if/for/while 节点——并行=扇出、汇聚=扇入、分支=源节点 `routes="one"` 运行时只挑一条（`NodeState.next_hint`）、循环=回边、重试=`on=error` 兜底边。
   - 图模型真源是 `src/workflow/core/`（自持副本，与 wdl-engine `wdl/src/wdl/core/` 同源；分叉声明在 `model.py` 文件头），`FlowCoordinator` 只做构建子智能体、渲染输入、投递到达、级联启动；就绪判定与激活上限（默认每节点 100 次，`DEFAULT_MAX_ACTIVATIONS`）归 `ActivationEngine`。

2. **数据沿边流动（run）**
   - `run(flow=…)` 点火：无入边的起始节点 spawn 成停车 coaras 子智能体开跑；节点完成后结果文本沿边自动投递下游——wait 边（不成环且 on=success）要求**每条**上游都交活到齐才开跑，kick 边（回边/error 边）不参与就绪、只送一次到达让节点再跑一轮。
   - 下游输入：上游结果自动以「来自 xx」段落注入下游 prompt；节点 input 可写 `{{steps.上游.text}}` 显式引用（模板引用即隐式依赖）。上游先完成、下游未 spawn 时到达进引擎队列（悬空边），下游 spawn 后自动消化。
   - 循环终止由激活上限硬兜底，图允许任意回边。

3. **写穿投影（草案）**
   - **编排即写穿**：每个改图动作（spawn/update/edge/remove）自动把图经 `emit_graph` 投影成 WDL 文本落盘到绑定草案（`src/workflow/draft_store.py`，存系统级 `<coara_home>/users/default/workflows/drafts/`，与工作空间无关），并推送 WebUI 画布实时显示；`save` 仅作幂等确认。
   - 草案是**唯一活模型**，内存图是执行缓存：会话编排与 WebUI 编辑器读写同一份存储；UI 侧改过的 flow 标 `_stale`，下次 run/wait 前从草案重建（`rebuild_from_projection`）。
   - 序列化规则固定（键序固定、默认值省略、节点按 id 排、边按 (from,to,on) 排），同一张图输出逐字节相同。WDL 格式权威是 `docs/WORKFLOW_SPEC.md`。

4. **执行（独立 wdl 软件）**
   - 跑通后的草案交给独立 wdl 引擎执行（`wdl/`，`wdl run` / `wdl serve`，KernelGraphRunner、持久化、画布工作台全在 wdl 侧）。触发方式有两类：人经画布/CLI 直启；事件源 `kind: cron` 等定义里的工作流 trigger 命中直启（见 `docs/工作空间与事项制度.md`）。
   - 内核与 wdl 零 import；`src/workflow/core/` 副本的语义漂移有哨兵（`tests/test_workflow/test_core_fork_parity.py`、`scripts/dev/check_core_fork.py`），改图语义必须明确判断是否两边都改。
   - 终态：由 wdl 软件自管与展示；内核 `inbound_router` 对调度终态消息 debug 忽略
