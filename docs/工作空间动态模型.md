## 1. 概念模型

每个工作空间有一条**动态流（updates）**：工作空间发生的外部事件与运行结果，按时间排成一条 typed entry 流，类似未读消息。消息内容体系下，每条动态就是一条**消息内容信封**：内容**无条件**落所属空间的收件箱，`salience` / `handle_mode` / `source_kind` 三个字段决定曝光与处置（见 §2）。

- **写入方（生产者）**分两族：外部感知（`external_sensor`：事件源 file_watch / interval_poll / webhook / cron）；内部自报（`internal_report`：工作流引擎事件、提醒到点）
- **读取方（消费者）**：janitor 的 `review` 工具（过目单 + 处置）、`/ws updates` 聊天命令、Web UI、手机 App 红点（Matrix 推送）
- **设计意图**：不再有「事件自动叫醒主会话跑回合」——内容默认 `handle_mode: park`（挂住等用户来看）；事件源配 `handle: janitor` 时叫醒管家 janitor 过目（勾掉/呈阅/自处理，处置轨迹写回消息）；用户决定处理后由 Root `delegate(coaras, workspace=…)` 去办。`salience: high` 的未读内容上浮到跨空间「前台待处理视图」（`review(action=pending)`）

## 2. 动态条目字段

每条动态是一个 JSON 文件，对应 `WorkspaceUpdate`（`src/workspace/updates/types.py`）：

| 字段 | 说明 |
|------|------|
| `message_id` | 动态编号，格式 `upd-{12 位 hex}` |
| `workspace` | 归属工作空间名 |
| `source_id` | 来源 id（事件源 id、`workflow-engine`） |
| `event_type` | 事件类型（如 `webhook.received`、`cron.tick`、`workflow_completed`） |
| `type` | 条目类型，见 §3（缺省 `note`） |
| `payload_ref` | 详情引用：文件路径 / run_id / 工作流实例 task_id / 事件 id（可空） |
| `status` | `unread` / `read` / `archived` |
| `dedupe_key` | 去重键（§6） |
| `title` | 一句话标题（优先取 payload 的 content/title/summary/subject，截 120 字符） |
| `text` | 完整正文（事件源为渲染后的 `message_template`） |
| `display_text` | 展示用正文（经 `display.py` 格式化） |
| `salience` | 显著性 `low` / `normal`（默认）/ `high`；`high` 的未读条目进跨空间前台待处理视图（`review(action=pending)`） |
| `handle_mode` | 处理模式 `park`（默认，挂住等用户）/ `janitor`（叫醒管家 janitor 过目）；janitor 处置产出的结果内容恒为 `park`，防止自激环 |
| `source_kind` | 来源族 `external_sensor`（外部感知：事件源）/ `internal_report`（内部自报：事项/工作流/提醒） |
| `disposition` | 处置轨迹，与 status 正交：`pending`（待过目，默认）/ `elevated`（呈阅用户）/ `resolved`（已处置）/ `dismissed`（已勾掉，留轨迹不再上浮） |
| `review_history` | 完整处置轨迹数组，每项 `{by, at, action, note}`——谁、何时、做了什么、备注，一次处置追加一条 |
| `reviewed_by` / `reviewed_at` / `review_note` | 最近一次处置的快捷字段（与 `review_history` 末条一致，旧条目兼容解析） |
| `salience_by` / `salience_at` | 优先级最近一次被修改的过目人与时间（`review(action=salience)` / `/ws updates salience`） |
| `expires_at` | 消息保质期（ISO，可空）：事件源声明 `ttl_seconds` 时写入；过期未读被纯规则过目勾掉 |
| `payload` | 原始 event + routing 元数据 |
| `created_at` / `read_at` / `archived_at` | ISO 时间戳 |

**处置轨迹规则**（规则常量在 `src/workspace/updates/rules.py`，随 `updates_board` 下发，与本文档同源）：

- 用户批示（Web / Matrix 批复入口）→ `resolved`，`reviewed_by=user`，备注为批示摘要（截 200 字符）
- 用户或 janitor 勾掉 → `dismissed`；勾掉时顺带置为已读（不再占红点），条目保留可回查
- janitor 处置（dismiss/elevate/resolve）**必须写 note**（处置理由），≤200 字；`high` 显著条目禁止 dismiss，必须呈阅或处置
- 每次处置追加一条 `review_history` 轨迹（by/at/action/note），显示端展示完整审批链
- 待处理视图（`review(action=pending)`）＝未读且未被勾掉/处置的 **high** 条目 ∪ 被呈阅（`elevated`）的条目（无论显著性）
- 纯规则过目（sweep，`WorkspaceUpdatesStore.sweep`，挂在 janitor watcher 每拍执行，不经 LLM）：① 过保质期（`expires_at`）的未读 pending → `dismissed`「已过保质期 自动忽略」；② `low` 显著超龄（默认 7 天）未读 pending → `dismissed`「低显著消息超龄 自动忽略」。`elevated` 条目不受规则触碰 |

## 3. 条目类型 type

`type` 字段目前实际产生的共 4 种（常量 `UPDATE_TYPES` 已随清理删除，以生产写入方为准）：

| type | 来源 |
|------|------|
| `file_change` | file_watch / interval_poll 事件源 |
| `webhook` | webhook 事件源 |
| `workflow` | 工作流终态事件（完成/失败/取消；内核已无待审批挂起态） |
| `reminder` | 提醒到点（恒 `salience: high`，落当前活跃工作空间） |
| `note` | 其它（缺省值） |

历史兼容（只读，不再产生）：旧日程执行完成条目、`background_task`（结果只回发起会话历史，不再落收件箱）。

## 4. 存储布局

`WorkspaceUpdatesStore`（`src/workspace/updates/store.py`）：

```text
<workspace_dir>/.coara/                    # 工作空间目录（空间自治布局，2026-08 起）
  ws.md                                    # 空间概况
  inbox/
    upd-abc123def456.json                  # 每条动态一个 JSON 文件
    upd-….
    read_marker.json                       # 已读水位线（inbox 目录内）
```

> 动态跟随工作空间：空间移动/删除时数据一起走；rename 只改别名不动目录。
> 兼容：无 registry 时回退旧集中布局 `{coara_home}/users/default/inbox/{name}/`（启动 best-effort 迁移到空间布局）。

## 5. 已读水位线与红点

- 已读水位线持久化于 `<workspace>/.coara/inbox/read_marker.json`（空间自治布局），内容为含 `marker` ISO 时间戳的 JSON。
- **未读数（红点）= 未归档且 `created_at` 晚于水位线的条目数**。
- `review(action=mark_read)` / `/ws updates mark_read <name>` 把水位线推进到该工作空间最新条目的时间 → 红点清零；PC 侧推进后会再推送一次 Matrix 状态让 App 同步清零。
- 手机 App 端则是**进入该工作空间即本地清零**（微信式，不做逐条已读），不写回 PC。
- 单条 `review(action=read)` 只把该条置为 `read`，不影响水位线。

## 6. 去重与裁剪

**去重**（`append()`）：

- 写入前按 `dedupe_key` 查找同工作空间的既有条目；**存在未归档**同键条目则跳过写入。
- 已归档的同键条目不挡新写入（同一来源可再次产生动态）。
- 事件源侧另有冷却去重（`cooldown_seconds` 默认 30 秒，状态存 `matters/.state/`），在动态写入之前生效。

**裁剪**（每工作空间 **500 条**上限）：

1. 先删**已归档**的（最旧优先）；
2. 仍超额再删最旧的**已读**条目；
3. **永不删未读**——删未读等于静默丢事件。

## 7. 生产者

三个写入点，全部是 best-effort（失败只记日志，不影响主流程）：

| 生产者 | 代码位置 | 产出 type | 说明 |
|--------|----------|-----------|------|
| 事件源落盘 | `EventSourceManager._handle_event()`（所有事件无条件落收件箱） | `webhook` / `file_change` / `note`（cron） | `salience`/`handle_mode` 取自事件源定义的 `salience`/`handle`；`source_kind=external_sensor`；`expires_at` 由 `ttl_seconds` 算出；`payload` 含原始 event 与 routing（domain、suggested_delegate）；`payload_ref` 取首个文件路径，否则事件 id/feedback_id |
| 工作流事件 | `WorkflowBridge._emit_update()` → `RootCoara._record_workflow_update()` | `workflow` | 覆盖 `workflow_completed` / `workflow_failed` / `workflow_cancelled`；`source_kind=internal_report`；均 `normal`（含失败）；工作空间归属见 §10；`dedupe_key = workflow:{task_id}:{event_type}` |
| 提醒到点 | `src/coara/root_lifecycle.py` `_on_reminder_fire()` | `reminder` | 恒 `salience: high`、`source_kind=internal_report`；落当前活跃工作空间；**不自动跑回合**，挂前台待处理 |

写入成功后统一回调 `RootCoara._on_update_stored()` → 推送 Matrix 红点（§9）。

## 8. 查看与管理入口

**动态动作与用户批示**（动作实现 `src/tools/builtin/ws/updates_ops.py`，由 `/ws updates` 命令驱动；用户批示路由 `src/workspace/updates/review.py`）：

| action | 参数 | 说明 |
|--------|------|------|
| `board` | `name`（工作空间名，缺省全部）、`limit` | **过目单**：处理规则 + 待处理条目 + 已处置轨迹，janitor 过目一次拿全 |
| `list` | `name`、`status`（unread/read/archived/all，默认 unread）、`limit`（默认 30） | 列动态 |
| `pending` | `limit`（默认 30） | 跨空间高显著未读（前台待处理视图，`salience: high`） |
| `stats` | — | 按工作空间统计 未读/已读/归档/合计（只统计已登记工作空间） |
| `read` | `message_id` | 读全文并标记该条已读 |
| `archive` | `message_id` | 归档 |
| `dismiss` / `elevate` / `resolve` | `message_id` + `note` | 处置三选一（勾掉/呈阅/已处置），**note 必填**（处置理由），留完整 review_history 轨迹 |
| `mark_read` | `name` | 全部标为已读（推进水位线 + 推送 Matrix 状态） |

> janitor 专属的 `review` 工具已移除（janitor 不再挂动态工具）；用户批示经 `src/workspace/updates/review.py` 路由回内容所属空间的会话。动态查看靠工作空间消息注入、Web UI、`/ws updates` 与直接读 inbox JSON。

**聊天命令**（无需 LLM）：`/ws updates [list|pending|read|archive|dismiss|mark_read|stats] [工作空间名]`

- 工作空间名可带 `@`（如 `/ws updates list @xuan`）；省略动作默认 `list`（未读）
- `read` / `archive` 的第一个参数是**动态编号**：`/ws updates read upd-abc123def456`

**手机 App**：工作空间菜单红点 + 本地缓存列表（§9）。

Web UI 目前没有动态相关的 REST 端点。

## 9. Matrix 同步（PC → App）

App 是 Matrix 客户端，不直连 coara HTTP——同步走 Matrix 房间里的**隐藏负载**（聊天界面过滤不显示）：

```text
[COARA_UPDATES]
{"type":"workspace_updates",
 "workspaces":[{"workspace_id":"…","name":"暄","summary":"…","path":"…",
                "unread":2,
                "latest":{"type":"webhook","title":"反馈 #28","created_at":"…"}}],
 "message":{"message_id":"upd-…","workspace":"暄","type":"webhook",
            "title":"…","display_text":"…","created_at":"…", …}}
[/COARA_UPDATES]
```

- **状态 + 新动态推送**：动态落盘时推送（含 `message` 字段）；已读水位推进后推送（仅 `workspaces` 状态）。
- 负载构造：`format_updates_payload()`（`src/coara/updates_matrix_sync.py`）+ `build_updates_workspaces_payload()`（`src/workspace/updates/catalog.py`，按 registry 的 active 工作空间逐个统计未读数与最新条目）。
- **App 侧**（`android-app/`）：`UpdatesSyncParser.kt` 解析 → 与本地目录合并 → `updates_state.json` 缓存 + 红点；进入工作空间本地清零；打开菜单只读本地缓存，**不向房间发消息**。
- PC 收到误发的 `[COARA_UPDATES]` 入站消息时在 Matrix 层直接丢弃（`is_updates_control_message`），不进 Root LLM。

## 10. 工作流与工作空间的关系

四种关系分开看，不要混为一谈：

- **定义（WDL）**：全局独立资产，不属于任何工作空间——草案、触发器、实例库存储均为全局（`users/default/workflows/`）。在某个工作空间里创建工作流只是作者的上下文，不构成所有权；也**不存在**「把 WDL 拷进工作空间」的概念（拷贝必分叉）。
- **运行上下文**：每次**运行**必须有一个执行工作空间（文件工具落点、`@` 路径解析、权限边界）。这是运行参数而非资产属性：提交时 `workspace` 别名经 `WorkflowBridge._resolve_execution_workspace_dir` 解析为路径，随 `start_workflow` 命令传给引擎（`workspace_dir` 字段，并写入 `origin_json` 供跨重启 resume 恢复）；引擎按任务执行（`_task_workspaces`），代理池按 空间+能力契约 隔离。未给别名时取当前前台空间；别名无法解析时回退前台并告警。
- **触发绑定（「部署」的准确含义）**：把全局工作流挂到某空间的事件源上——`triggers.json` 里一条绑定记录（workflow + event_id）。事件源本身按空间分（`defn.workspace`），触发时该空间别名成为运行上下文。触发器存 WDL 快照 + `draft_id`；点火时草稿的当前 WDL 优先于快照（`resolve_trigger_wdl`），改草案不会留下跑旧版的触发器。
- **结果**：运行记录/状态是运营数据，全局 `instances.db` + `workspace` 标签过滤；产物（工作流写出的文件）落在运行上下文空间——产物跟运行走，不跟定义走。

动态归属（`WorkflowBridge._emit_update()`）：优先事件 payload 的 `workspace`；其次提交时记录的别名 / `origin.workspace`（内存 `_submit_workspaces` + 持久化 `origin_json`/`workspace` 列）。都拿不到则**跳过**该条动态。
进程重启后仅内存映射会丢；已写入 `origin_json`/`workspace` 的实例仍可从 DB 恢复归属（旧实例无列数据时动态可能仍缺省）。
