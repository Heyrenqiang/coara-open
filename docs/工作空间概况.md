# 工作空间概况（Agentic Workspace Overview）

> **概念 + 实现对照**：定义智能体进入工作空间时，如何快速、全面、省 token 地掌握干活所必要的知识。
> 面向「工作空间 + LLM + View」三模型架构中的 View 层与 LLM 的接口，与 [`工作空间与目录.md`](./工作空间与目录.md) 的物理布局定义互补。
> §1–§7 讲机制；**§8 严格对齐当前代码**（`environment_injector` / `workspace_protocol` / `root` idle watcher / `janitor`）。维护写作规范见 [`工作空间概况维护规范.md`](./工作空间概况维护规范.md)。

---

## 1. 目标与三个问题

工作空间是异构容器：可能是代码仓库、数据目录、绑定了一组工作流的自动化环境，也可能只是一个挂着动态流的文件夹。智能体进入一个空间，只需要回答三个问题：

| 问题 | 本质 | 回答者 |
|------|------|--------|
| 关键东西在哪 | 认知 | 概况 `# 目录文件`；深读 README / AGENTS.md |
| 用户在空间里说过做过什么 | 对齐 | 概况 `# 用户行为`（情境·用户输入·现状） |
| 具体怎么做 | 行动 | AGENTS.md / 工具探索 + 按需 read |

token 效率：概况 = **目录 + 用户行为 + 可选其它**（软目标 ≤12KB）；长文仍归 `AGENTS.md`。

---

## 2. 概况是什么

工作空间概况是一套机制，统一就叫这一个名字。它管三件事：

| 层面 | 管什么 |
|------|--------|
| 内容 | 概况正文里写什么：五个问题（§5） |
| 组织 | 正文怎么链接到细节：分层 + 链接 + 触发条件（§6） |
| 时机 | 何时注入、何时更新：进入空间即注入、会话边界由智能体维护（§7） |

载体是 `<工作空间目录>/.coara/ws.md`，磁盘上的完整概况就是它。唯一文件名，不做 `AGENTS.md` / `CLAUDE.md` 兼容。

概况 = **目录 + 用户行为 + 可选其它**（janitor 在会话边界维护），不是技术 changelog。静态架构归 `AGENTS.md`；技术变动与过程细节归 `record` 与对话历史。

## 3. 核心模型：空间 + 资源

模型分两层，这是整个概况机制的地基。

### 3.1 三层实体

| 实体 | 是什么 | 归属 |
|------|--------|------|
| 工作空间 workspace | 容器：数据、文件、状态、动态的承载 | 用户创建，独立存在 |
| 专家 expert | 公共能力资源：自然语言定义的智能体描述词，可被发现、被任务按需创建调用 | 公共池，不属于任何空间 |
| 工作流 workflow | 公共流程资源：WDL 描述的流程，可被空间绑定，也可独立运行 | 公共池，可绑定到空间 |

### 3.2 关系规则

- 工作空间独立存在，不依赖绑定关系。一个空间可以一个工作流都不绑，也可以绑多个。
- 空间与工作流之间是显式绑定关系，不是包含关系。绑定表示「这个工作流住在该空间，为它工作，动向经该空间动态反馈」。
- 工作流不必须绑定空间。未绑定的工作流是公共池里的工具，用户需要时运行一次（工具调用或 UI 运行），结果按调用方约定返回，不进任何空间动态。
- 专家不绑定空间。任何空间的智能体都可以发现并调用公共专家。
- 工作流与专家同为公共资源：统一存放、统一目录、被 coara 管理。

### 3.3 为什么这样分层

统一的是「壳」——空间、专家、工作流都有统一的身份、发现方式、生命周期管理。不统一的是「内容」——空间里装的是域数据，专家是能力描述，工作流是流程描述。智能体面对三者使用同一套发现协议，但读取的内容格式各不相同。

## 4. 空间内容域模型

空间里装什么，固定为六种域。任何空间都是这些域的子集——可以是空 files 域（没有目录的空间），也可以是只挂 activity 域的纯动态空间。

| 域 | 内容 | 典型视图（索引） |
|----|------|------------------|
| files 文件域 | 源码、文档、资产、任意文件 | 目录树、语言分布、文件类型统计 |
| data 数据域 | 结构化数据、表、数据库、知识库 | 单元清单、schema、规模 |
| flows 流程域 | 绑定到本空间的工作流引用 | 工作流列表、触发方式、最近运行 |
| triggers 触发域 | 定时器、事件源 | 触发清单、状态、最近触发时间 |
| activity 动态域 | 工作空间动态、外部事件、运行结果 | 最近动态列表、未读摘要 |
| state 状态域 | 当前运行状态 | 运行中的任务、待处理事项、异常告警 |

域清单是空间自带文档描述空间类型的骨架：智能体看 README / AGENTS.md 就知道该空间是什么类型、从哪里下手；概况正文不重复罗列。

## 5. 概况正文设计（核心）

概况正文让智能体把握该空间：目录在哪、用户说过做过什么。

### 5.1 内容骨架

| 块 | 回答 | 内容 |
|----|------|------|
| 目录文件 | 从哪下手 | 空间物理样子；有 AGENTS 时短地图并指向它 |
| 用户行为 | 用户说过做过什么 | 情境·用户输入·现状；无可只留标题 |
| 其它 | 悬置等 | 无可整块省略 |

### 5.2 ws.md 正文模板示意

```text
# 目录文件
AGENTS.md  src/  docs/  tests/

# 用户行为
- 09-04 情境 … → 用户输入 … → 现状 …

上面是该工作空间的一些情况，仅供参考
```

### 5.3 组织原则

- **正文不写格式说明**（规则在 janitor 提示词）。
- 用户行为宁缺毋滥；没有值得记的就只留标题。
- 目录无变化保留上一版；细节进 `record`；长文进 `AGENTS.md`。
- AGENTS 与 ws 重复时：能放概况的放进 ws.md 并去重。

## 6. 用户行为条目中的路径

用户行为条目可顺带相对路径（如「优先改 src/ui/web_views」）；不设独立链接区。

## 7. 注入与更新机制

### 7.1 进入空间即注入（环境种子）

新开会话（含切入后开新会话、`/new`、空闲 renew）时，系统必须把概况正文注入智能体。

**实现位置**（非 system prompt 后缀）：`context_modules.build_prefix_seed_messages`（经 `environment_injector.build_environment_seed_messages` 入口）按配置构造**多条**伪造 USER 消息（包在 `<系统消息>` / 用户规则用 `<系统提醒>`），挂在 `message_history` 最前，从而保持 system prompt 静态、利于缓存。默认顺序：

1. `用户规则：` + `<coara_home>/system/user_rules.md`（无文件则跳过；`<系统提醒>`）
2. `环境上下文：`（日期、地点、OS、工作目录；可选 git）
3. `AGENTS.md：` + 工作空间根 `AGENTS.md`（无文件则跳过；与 Cursor 惯例同名）
4. `工作空间概况：` + `.coara/ws.md` 全文（≤32KB）；文件缺失或空白时写占位句「本空间工作空间概况生成中…」

对话之后还可 ephemeral 注入 `<情境>` 包裹的 `情境：` + `situation.md`（每轮 LLM 调用末尾，不冻进历史头，与一次性参考 `<系统消息>` 区分）。模块开关与顺序见 `<coara_home>/system/context_modules.yaml`（devtools「上下文模块」页可改）。

概况消息含 `工作空间概况：` 前缀（环境消息含 `环境上下文：`），故 `workspace_session_has_conversation` 等「是否真实对话」判定会跳过它们（见 §8.4）。

### 7.2 会话级快照：前缀冻结原则

概况是会话级快照：一次 new 会话注入一次，会话内绝对冻结，绝不修改前缀。送入 LLM 的内容必须增量式、前缀不可变——概况一旦进 history，就随会话固定，直到 new 会话才允许刷新。配套规则：会话内磁盘上的 `ws.md` 也不被运行时改写（含 janitor）；**唯一写入时机是会话边界**（过期维护或手动 `/new` 前）。

**唯一例外：janitor 完成后的种子替换**。janitor 写盘完成时，若该空间还有存活会话，系统在下一个 turn 边界把历史中带 `工作空间概况：` 的种子消息替换为最新内容（独立概况消息整条替换；旧版「环境+概况」合种则只换概况段），并经 persist 边界写回事件日志。内容未变则跳过；会话超过 40 条消息则跳过。这条例外让 `/new` 后立刻开始干活的会话也能在一两分钟内拿到刚总结好的概况，而不必清空对话。

理由有两条，互为因果：

- 会话内智能体自己造成的空间变化，都在对话历史里自然体现，LLM 知道，概况不必变。
- new 会话后对话历史清空，此前积累的空间变化必须进概况，否则 LLM 对空间失去认知。new 会话本就是前缀重建的时刻，此时刷新概况没有额外缓存代价。

### 7.3 外部变化的时机处理：不走前缀，走对话流与落盘

概况冻结期间，空间的一切变化必须通过对话流让 LLM 知道，而不是回头改概况。处理按「变化发生时该空间有没有对话流可注入」分四种时机：

| 外部变化发生时 | 处理 |
|----------------|------|
| 该空间有活跃前台会话 | 落盘 activity 域 + 下一轮 LLM 调用时以系统消息注入对话流 |
| 智能体未进入该空间（无会话或空间挂起） | 只落盘 activity，无人可注入，落盘即全部 |
| 进入空间时 new 会话 | janitor 从快照更新「用户行为」与目录（若有变） |
| 进入空间时恢复旧会话 | 旧概况冻结；挂起期间的未读动态以系统消息补偿注入对话流，注入后标记已读防重复 |

统一原则：**外部变化永远先落盘进 activity 域（保底），有活跃会话则同时推一份进对话流（加速）**。恢复旧会话的补偿注入最容易被遗漏——旧概况和旧对话历史都不含挂起期间的变化，必须补上，LLM 的认知才完整。

过滤原则：并非一切外部变化都注入。只注入与该空间相关且达到关注阈值的变化（工作流终态、告警、用户反馈落地），高频低价值事件（普通文件改动）只落盘不推送，避免对话流被噪音刷屏。

智能体自己造成的变化不需要任何通道——都在对话历史里自然体现。智能体怀疑状态过时时，调用刷新工具重新拉取，结果进对话流。

### 7.4 结构与块排序

**结构（与 janitor 一致，不可调换）**：

```text
# 目录文件 → # 用户行为 →（可选 # 其它）→ 结尾参考句
```

会话边界 janitor 维护各块；用户行为宁缺毋滥；目录无变可保留。

### 7.5 会话间维护：过期触发，janitor 执行

维护是会话的终结仪式：一个会话一生只被维护一次（同一 activity epoch 不重复派发），默认挂在「最后会话活动 + `session.idle_timeout_seconds`（默认 2h）」边界上——最后会话活动指三端真实用户消息或回合结束（最后一轮 LLM 调用），取近者，因此超长自治回合结束后不会立刻触发维护。执行者是内核固化维护流程 **janitor**（非子智能体、不经 delegate、系统内部、非 user_facing；提示词见 [`工作空间概况维护规范.md`](./工作空间概况维护规范.md) 与 `src/coara/prompts/injections/janitor.md`）。双任务：① 更新 `ws.md`；② 用 `record` 记下用户做事与工作空间状态变化（全局 `users/default/records/agent/`；用户收藏只能人手点，不能 `origin=user` 代写）。

**触发规则（按空间独立计时）**：

| 空间状态 | 动作 |
|----------|------|
| 歇着（本会话周期无真实对话） | 不维护、不 renew |
| 有真实对话且空闲超时 | 后台 janitor 写 `ws.md` → pending 结束后若 activity epoch 未变 → `start_new_session`；非前台空间同样触发 |
| 手动 `/new` 且有真实对话 | 后台 janitor（不等待）→ 立刻开新会话并注入当时磁盘版；janitor 写盘后把新概况**替换**进存活会话的种子（7.2 例外） |
| 进程重启后磁盘已过期且 history 有真实对话 | 启动补扫：后台 janitor **只刷盘**，不入 pending、不在此处 renew（切入时磁盘恢复会开新会话） |

**频率限制（冷却防抖）**：每工作空间两次真实派发间隔不得小于 `session.janitor_min_interval_seconds`（默认 600，0 = 关闭）。窗口内的触发**只推迟不丢弃**：每次触发都先拍历史快照（保证刚结束会话的内容不丢），然后挂一个延迟定时器（同空间只有一个，后到触发只刷新负载不顺延），到点用最新快照跑一次。配合单飞（在飞期间触发只标 dirty），任何冷却窗口内每空间最多一次 janitor LLM 调用，且运行永远使用最新快照。

**跨重启去重**：已维护的 activity epoch 持久化到 `<coara_home>/workspaces/<ws_id>/janitor_activity.json`；启动补扫与 idle 扫描都先查它——一个会话一生只被维护一次，反复重启不会对同一会话重复派发。**标记在 janitor 完成时才落盘**（完成钩子写入；失败/取消不写）：派发时只记内存单飞标记，进程在维护中途被杀不会留下磁盘标记，重启 catch-up 会重派该 epoch，维护不再永久丢失。

**失败退避重试**：janitor 失败/取消时除不写磁盘标记外，还在进程内记一条失败记录（epoch + 失败时刻）；idle 扫描对同 epoch 在退避窗口（10 分钟，`JANITOR_RETRY_BACKOFF_SECONDS`）到期后放行补派一次，重派仍走单飞/冷却/在飞合并闸门。每 epoch 进程内最多补派一次（名额消费后不再记录失败），防失败循环；成功路径行为不变。

**边界规则**：

- **竞态**：维护进行中用户发消息或回合结束 → `record_user_activity` / `record_turn_activity` 刷新 `_workspace_activity_at` → finalize 时 epoch 不一致 → **保留磁盘上新写的 `ws.md`，取消 renew**，会话复活。
- **歇着空间的外部变化**：不触发维护；变化落盘 activity；待该空间有会话并过期后，janitor 从快照提炼用户行为（若有）。
- **任务类型**：磁盘上无 `ws.md` →「首次生成」；已有 →「会话间维护」（`resolve_janitor_task_type`）。
- **快照接力**：历史快照只有一份；中间会话的用户行为靠 janitor 写盘接力——后一轮先 read 现有 ws.md 再读快照。快照经临时文件 + 改名写入，janitor 不会读到半截文件。

与会话内冻结不冲突：维护改的是磁盘文件，当前会话 history 里已注入的概况前缀不动。

护栏：用户行为宁缺毋滥；目录文件无明确变化不擅自改。`/new` 不等待 janitor；新会话注入当时磁盘上的 `ws.md`（或「生成中」），janitor 写盘后再把新概况替换进种子（7.2 例外）。

### 7.6 用户行为的维护

| 内容 | 维护者 | 更新时机 |
|------|--------|----------|
| 用户行为 | janitor 维护 `ws.md` | 会话边界（7.5）；宁缺毋滥 |

注入内容 = `ws.md` 全文。会话边界维护，频率低。

### 7.7 分层披露

概况：**目录文件** + **用户行为** + 可选**其它**。`AGENTS.md` 是 Canonical 长文；`ws.md` 是进入会话时的对齐视图。进入空间开销 ≈ 概况（软目标 ≤12KB）+ 按需 read。

### 7.8 增量维持

智能体常驻后，会话内新信息靠对话流增量进入；概况前缀冻结不回写。用户行为在会话边界由 janitor 从快照刷新。

## 8. 逻辑框架 · 工作流 · 数据流（与代码对齐）

> 一句话：`ws.md` 是**磁盘上的空间说明书**；新会话注入一次后**前缀冻结**；会话边界由系统 **janitor** 维护管道写盘；写盘既服务下一次注入，也经「概况替换」服务当前存活会话。

### 8.1 逻辑框架

两个角色，读写分离：

- 主会话 Root（用户可见）
  - 读：环境种子里的「工作空间概况：」+ ws.md（进 history 后冻结）
  - 写概况：不负责；会话中变化靠对话 / updates / 工具查询
  - 例外：janitor 写盘后，种子里的概况段被替换为最新版（turn 边界）
  - 看不到、也不能主动 delegate janitor
- janitor：系统维护管道（`janitor_maintenance.py`，静默），由会话边界系统派发（不经 Root LLM）
  - 跟空间：provider（可配覆盖）、VFS
  - 读：历史快照 + 现有 ws.md + updates + 按需扫盘
  - 写：`.coara/ws.md`（或判定跳过）+ 全局 `records/`（用户做事 / 空间变化，见 [本地记录.md](./本地记录.md)）
  - 每空间单飞 + 冷却防抖：窗口内触发只推迟不丢弃

| 概念 | 含义 |
|------|------|
| 载体 | `<workspace>/.coara/ws.md`（概况，不是契约） |
| 注入 | 新会话前缀模块：`工作空间概况：` + 全文或「生成中」 |
| 冻结 | 进 history 后本会话不改前缀；运行时也不回写磁盘概况 |
| 替换 | janitor 写盘后把概况消息换新（唯一例外，turn 边界，内容未变则跳过） |
| 维护 | 只在会话边界；写盘既服务下一次注入，也服务存活会话的替换 |
| 身份 | 系统维护管道；LLM 不可经 delegate 点名 |
| 频率 | 单飞 + 冷却（`session.janitor_min_interval_seconds`，默认 600s），窗口内最多一次 LLM |

**触发原因（信封字段 `trigger`）**

| 值 | 含义 | 派发后是否立刻新会话 |
|----|------|----------------------|
| `manual_new` | 用户主动 `/new` | 是（不等待 janitor） |
| `idle_timeout` | 空闲超时 | 否（janitor 跑完且 epoch 未变才 renew） |
| `startup_catchup` | 进程启动补扫 | 否（只刷盘；切入时磁盘恢复另开新会话） |

**任务类型**

| 值 | 条件 |
|----|------|
| `首次生成` | 磁盘无 `ws.md` |
| `会话间维护` | 已有 `ws.md` |

### 8.2 工作流

#### A. 新会话注入（所有开新会话路径共用）

- `start_new_session` → `build_environment_seed_messages` 构造一条环境种子 USER 消息，内含
  - `环境上下文：`（日期、地点、OS、工作目录）
  - `工作空间概况：` + 读盘 ws.md（≤32KB），缺失则为「生成中」占位
- 写入 message_history 最前（USER / `<系统消息>`）
- 之后本会话概况前缀冻结

#### B. 手动 `/new`

- 有真实对话？
  - 否 → 直接 `start_new_session`
  - 是 → `persist_session_to_disk` → `dispatch(trigger=manual_new)`（先拍快照，再按冷却决定立即或延迟派发）→ `start_new_session`（注入「当时磁盘」概况；可对话）→ 后台 janitor 写盘后替换进存活会话的种子（见 F）

#### C. 空闲超时（idle watcher，约每 60s）

- `startup_scan`（进程一次）：磁盘陈旧 + history 有真实对话 → `dispatch(startup_catchup)` 只刷盘，不 renew
- `finalize_pending`：在飞 idle 任务结束 → epoch 未变？→ `start_new_session`（前台发 `session_auto_new`）
- `scan_expired`：内存 session 空闲超时 + 有真实对话 + 该 epoch 未维护 → `dispatch(idle_timeout)` → 记 `_janitor_pending`（冷却期内 dispatch 返回 None，本 tick 不记 pending，下个 tick 重试）
- daily 零点整理：同 watcher 每 tick 调 `curator_tick`（与 `idle_timeout_seconds` 解耦；`src/records/daily_curator.py` + `daily` 系统调度；digest 写 `users/default/records/agent/digests/`；flight 30 分钟超时自愈，失败退避 1 小时后重试）

用户中途发消息 → activity epoch 变 → finalize **不 renew**，磁盘新 `ws.md` 保留。

#### D. janitor 内部维护流程（提示词强制）

- 读：主会话快照 + 现有 ws.md + `review(action=list|stats|read)` + 按需 glob/grep/read
- 评估：有无「影响下一会话认知或做事方式」的实质变化？
  - 否 → 不改文件，摘要「跳过：无实质变化」
  - 是 → 首次生成或会话间维护：重写用户行为块（目录有变才动）；临时文件 + 替换

短会话 / 一句话就 `/new`：无实质影响则跳过，避免空转改写。

#### E. 单飞 + 冷却防抖（/new 风暴）

派发判定：

- 该 workspace 已有 janitor 在跑？→ 只刷新 `session_history_janitor.json`，标 dirty，返回同一 task_id（不再开 LLM）
- 否则距上次真实派发 < `janitor_min_interval_seconds`？
  - 是 → 挂延迟定时器（同空间只一个，后到触发只刷新负载），返回 None
  - 否 → 立即派发
- 在飞任务结束且 dirty → 再派一轮（走同一 dispatch，冷却内自动并入定时器）
- 定时器到点 → 用最新快照派发（`snapshot_history=False`，不重拍）

时间线示例（冷却 10 分钟）：

- 0:00 `/new` → 立即派发 janitor A，拍快照
- 0:03 `/new` → 拍快照；冷却未到，挂 0:10 的定时器
- 0:05 `/new` → 拍快照；定时器已挂，只刷新负载
- 0:06 A 完成 → dirty 补跑请求并入 0:10 定时器；新概况替换进存活会话种子
- 0:10 定时器触发 → janitor B 带 0:05 那份最新快照开跑

三条保证：每个会话结束都拍了快照（历史不丢）；任意冷却窗口内最多一次 LLM 调用；运行永远用最新快照。中间会话的用户行为靠 ws.md 接力（后一轮先 read 现有概况）。

#### F. 概况替换（janitor 完成后）

- janitor 任务完成回调
- 该空间有存活会话？无 → 结束（ws.md 留给下次注入）
- 等 turn 边界（最长 180s，进行中 turn 不动）
- 会话消息数 > 40 → 跳过（前缀重建太贵）
- 读最新 ws.md，与种子里概况段比较：相同 → 跳过
- 只替换种子的「工作空间概况」段（env 上下文部分字节不动）
- 写回 `message_history[0]` + persist（事件对账）+ 发 trace（`workspace_overview_refreshed`）

替换不重新生成整条种子：日期、git 等 env 上下文保持原样，避免无谓的缓存失效。

### 8.3 数据流

会话进行中：

- 用户消息 / 工具结果 → `message_history`（内存）→ 每 turn 结束 persist（事件日志对账）
- 外部事件 → WorkspaceUpdatesStore（inbox），活跃会话同时注入对话流
- `ws.md` 不改

会话边界派发：

- 事件日志投影生成 `session_history_janitor.json`（临时文件 + 改名，防半截读取）
- 信封（trigger / task_type / 路径）→ `workspace_protocol.dispatch_janitor_background` → `janitor_maintenance.run_janitor_maintenance` → 临时 CoaraBase（不经 delegate）
  - 读：快照、ws.md、`updates_*`；模型：空间 last-run（最后一次正常对话运行的模型，不另配）
  - 写：`.coara/ws.md`
- 完成 → 不注入主会话（同aide）；同时触发概况替换（F）

下一次新会话：

- `.coara/ws.md` → 环境种子「工作空间概况：」→ message_history 前缀

| 路径 | 用途 |
|------|------|
| `<workspace>/.coara/ws.md` | 概况正文（注入源 / janitor 写入目标） |
| `…/session_events.jsonl` | 会话事件日志（**全端冷备/审计**；web 聊天区不读，见架构契约） |
| `…/web_views/` | web 端会话视图存储（08-31 起 web 聊天区唯一数据源） |
| `…/session_history_janitor.json` | janitor 专用快照（主会话上下文） |
| `…/session_state.json` | `last_updated`；启动补扫陈旧判定 |
| `<workspace>/.coara/inbox/` | 工作空间动态（外部变化；空间自治布局） |

### 8.5 失败与边界

| 情况 | 行为 |
|------|------|
| `/new` 时 janitor 未写完 | 新会话用旧/「生成中」；写盘后替换进存活会话种子 |
| 冷却窗口内触发 | 拍快照后挂延迟定时器（只推迟不丢弃），返回 None；idle 路径下个 tick 重试 |
| 派发失败 | 无 task_id；idle 本 tick 不 renew |
| 无 `ws.md` | 注入「生成中」；任务类型「首次生成」 |
| 歇着（仅环境种子） | 不派发 |
| Root 幻觉调用 janitor | 拒绝（非 system_dispatch） |
| 概况替换时会话过长 / turn 进行中超时 | 跳过替换，ws.md 留给下次边界 |
| 进程重启时有未触发的延迟定时器 | 定时器随进程丢失；启动补扫（startup_catchup）兜底 |

## 9. 核心结论

- 概况 = 内容（自上次更新以来的变化清单）+ 时机（注入一次、边界维护、完成后替换种子）。
- 主会话只**读**注入的概况；janitor 是**系统维护管道**，专写磁盘、不进对话、不对 LLM 暴露。
- `/new` 不等待；空闲是「维护完再 renew」；janitor 写盘后把新概况替换进存活会话的种子（前缀冻结的唯一例外）。
- 频率双保险：单飞合并在飞触发，冷却防抖推迟窗口内触发；历史快照每次触发都拍，永不丢。
- 维护输入必须全面：主会话快照 + 现有概况 + 外部动态；无实质变化则跳过。
- 省 token：正文只留变化、静态知识归空间文档、动态只在边界刷新、短会话可跳过、替换只换概况段。
