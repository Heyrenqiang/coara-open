# 归属载体收敛研究（草案）

> **本文是研究与判断，不是规范，也不构成动手计划**。事实依据为 2026-09-25 的只读摸底（逐点带 `文件:行`）。
> 相关：[架构契约.md](./架构契约.md) §端/通道状态载体职责表 · [消息渲染契约.md](./消息渲染契约.md) §六多端隔离 · [出站通道收敛设计.md](./出站通道收敛设计.md)

## 一、结论摘要（先给判断）

1. **四个载体不是同一件事的四份实现**，而是四个**生命周期不同**的事实：段（会易主，输出路由）· 回合来源（回合级快照）· 交互通道（协程上下文级）· 会话来源（会话级，回投兜底）。**因此"合并成一个对象"不是正确目标**——它们的清空时机互相矛盾（见 §四）。
2. 真正的问题是**读取侧**：`段.source or 回合来源` 这种"短接写法"散落在 6 处以上，语义靠读的人自己拼装；以及**缺一个统一的语义化查询**。
3. 其次是**生命周期缺口**：`session_origin` / `_last_user_input_source` / `_origin_remote_channel` **没有任何清空点**，跨回合永久残留（回投兜底需要它，但也可能一直指向已断的连接）。
4. 还有两处**零散的坏味道**：`_active_turn_source` 在 `base.py:361` 与 `:451` 重复声明；`EndChannel.foreground` / `view_workspace` 两个字段无任何读写者（疑死字段）。
5. **建议**：把批次三从"合并存储"改成"**收口读取 + 补齐生命周期 + 清坏味道**"三步，收益接近而风险低一个量级；每一步都能独立回归、独立回退。

## 二、四个载体是什么

| 载体 | 定义 | 语义 | 生命周期 | 清空点 |
|---|---|---|---|---|
| **SEG** `coara._segments` | `segment.py:8-54` | 输出帧路由权威：**谁最后注入，后续输出跟谁** | 会话级，随注入点推进 | 回合 finally 只清本回合段（`base.py:829`）；`_clear_session_state` 全清（`:1756`） |
| **CV** `EndChannel` | `turn_context.py:14-23` | 审批/交互通道：审批送哪端、send_file 旁路落点 | 协程上下文级（`turn()` 块） | 退出 `turn()` 块时 reset（`orchestrator.py:1290`） |
| **ATS** `_active_turn_source` | `base.py:361`（`:451` 重复声明） | 本回合的发起端快照（可观测/兜底） | 单回合 | 回合开始写（`:681`）、finally 清空（`:823`） |
| **SO** `session_origin` + `_origin_remote_channel` | `base.py:458-459` | 会话级最近真实输入端：唤醒/后台回投 | 会话级 | **无**（跨回合永久残留） |

伴生字段 `_last_user_input_source`（与 SO 成对更新，但更新点不同）：写入 `base.py:684`、`turn_orchestrator.py:367`；读取 `root.py:1203`、`janitor_maintenance.py:330`、`delegate.py:685`、`base_mixins/foreground_delegates.py:62`。

## 三、读取模式：短接写法是主形态

最常见的一行是 `段.source or 回合来源`（易主后按段、回合外按快照）：

`base.py:156-161,999` · `executor.py:526-527,559-560` · `commands/registry.py:232,361` · `web_server.py:2396-2397,2436-2437` · `cli/spinner.py:493` · `cli/root_shim.py:1090`

多级链出现在回投路径（`delegate.py:679-689`）：`段 → current_turn_source(ATS) → _last_user_input_source → SO.channel_id`；唤醒回投序是 `LAST > SO > origin`（`root.py:1198-1213`）。

**判断**：这些短接本身是对的（各自有明确语义），问题是**同一套拼装在三处以上各写一遍**——这正是过去几轮事故的同一结构（规则复制）。

## 四、五个时序窗口（合并的最大阻力）

1. **正常端回合结束**：`turn()` 块退出晚于回合 finally → 在 finally 期间 **CV 仍有效，而 ATS 与 SEG 已清空**（`ws.py:34-35` 明言依赖此时序，审批/事件回退要用它）。
2. **接续路径**：`orchestrator.py:1286-1292` 在 `run_turn_loop` 返回**之前** reset CV → 出现**反向窗口**（CV 已空、SEG 仍在）。
3. **夺权段跨回合存活**：`base.py:1344-1345` 开的段 `turn_id=""`，回合 finally 的判据（`:828` 只清 `turn_id==resolved_turn_id`）**不会清它**，它活到 `/new` 或被下一段覆盖。
4. **SO / LAST / `_origin_remote_channel` 永不清理**：回合外读取会拿到上一回合的端（`base.py:208/:960` 的两级兜底就可能拿到它）——回投兜底需要它，但**也可能指向已断的连接**。
5. **同名不同物**：CLI `cli/root_shim.py` 里的 `_active_turn_source` 是 attach 端本地镜像，与内核同名字段无关系；合并时极易误伤。

**判断**：窗口 1 与 2 方向相反、窗口 3 是有意设计（打断夺权后本回合收尾仍归新端）、窗口 4 是缺生命周期而不是缺载体。**一条"统一清空"规则会同时打破其中至少两处**——这就是"不能一刀切合并"的硬依据。

## 五、必须保持的不变量（12 条，逐条有据）

1. 段优先于回合来源（`base.py:156-161,999` 等 6 处；`test_session_config_confirm_gate.py:130`）
2. 回合结束时段与回合来源均须空（`base.py:823,829`；`test_segment_last_run.py:78`）
3. 夺权段跨回合存活（`base.py:1344`；`test_settle_b_class.py`）
4. 回合结束时交互通道仍持来源、不得随回合来源一起清（`ws.py:34-35`）
5. 审批通道独立于段（`approval_center.py:211`；`test_matrix_approval_turn_context.py`）
6. 唤醒回投端序 `LAST > SO > origin`，通道取 `SO.channel_id`（`root.py:1203`；`test_background_reply_routing.py:13`）
7. 段上通道过期不得静默丢帧（回退唯一连接/会话槽；`end_registry.py:95-111`；`test_end_registry.py:1093/1114`）
8. `_last_user_input_source` 只在"真正注入"时更新，入队不算（`orchestrator.py:366`）
9. 段只在用户端注入时开，系统回投不换段（`orchestrator.py:353`）
10. 非用户来源不推进空间 last-run（`base.py:1500`；`test_segment_last_run.py:50`）
11. 端族隔离：本端只收本端（`turn_source.py:40-93`；`test_turn_source.py`）
12. trace 事件必带 source（`trace.py:84`；`test_emit_trace_source.py`）

## 七、可合并度逐条评估

| 目标 | 可行性 | 理由 |
|---|---|---|
| 把四个载体**合成一个对象** | **不建议** | 清空时机互相矛盾（§四窗口 1/2/3），必须引入"按消费者分视图"才等价——那就是四个载体换个写法 |
| 把**读取短接**收口成语义化查询（`当前输出端` / `本回合发起端` / `回投端` / `交互通道`） | **可做，收益大** | 读点集中在一处，未来改判定只改一处；行为完全等价 |
| 补**生命周期缺口**（SO/LAST/远端通道的过期判定或清理） | **可做，但要先定语义** | 现无清空是有意的回投兜底；需要"什么时候该失效"的明确口径（例如连接断开即失效、或会话切换即清） |
| 清**死字段与重复声明**（`EndChannel.foreground`/`view_workspace`、`base.py` 重复的 ATS 声明） | **可做，零风险** | 无任何读写者；先确认测试替身未依赖 |
| 统一**同名不同物**（CLI 侧 `_active_turn_source` 改名） | **可做，低风险** | 纯改名，消除误导 |

## 八、若要推进，建议的三步

**第一步：收口读取（等价重构）**
新增一处查询模块（例如 `src/coara/turn_attribution.py`），提供四个语义化只读函数：`current_output_end()` / `turn_launch_end()` / `reply_end()` / `interaction_channel()`。把 §三列出的短接写法逐个换过去。
判据：行为零变化，12 条不变量对应用例全绿。

**第二步：补生命周期（先定口径再改）**
给 SO / LAST / 远端通道加"失效"判据（候选：连接断开、会话切换、来源端在册但通道已注销）；`_origin_remote_channel` 加清理点。
前置：先写用例钉住"何时该失效"，再改。风险集中在回投兜底（不变量 6）。

**第三步：清坏味道**
死字段、重复声明、CLI 同名镜像改名。

**明确不做**：不合并存储、不改清空时机、不动段的开段条件——这三件事都会触碰 §四的窗口与 §五的不变量，收益小于回归风险。

## 九、给决策的一句话

这一批的价值在"**读取收口 + 生命周期补齐**"，不在"合成一个对象"。前者两周内可以稳落地，后者即使做成也只是把四个载体换个箱子装。建议按 **第一步 → 第三步 → 第二步** 的顺序试水（先做零风险的等价重构，第二步要等"何时该失效"有了明确口径）。
