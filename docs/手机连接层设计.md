# 手机连接层设计

> 2026-09-15 定稿。回答一个问题 手机 App 如何在任何网络环境下稳定连上用户自己的电脑内核，不依赖 Cloudflare 作为唯一通道

## 目标与约束

- 服务对象是全部用户，不是开发者本人 方案必须开箱即用，用户操作收敛为两步 装 App、扫码配对
- 不依赖 Cloudflare 等第三方隧道作为唯一通道；允许其作为兜底层之一
- 用户对自己的数据有完全主权 任何中转层只见端到端加密的密文

## 分层择优模型

连接层按四级自动择优，上层失效静默回落，用户全程无感知，只看到「已连接」

```
同 WiFi   → 局域网直连（mDNS 发现）
否则      → IPv6 直连（高端口 + 设备寻址 + 自动证书）
不通      → Cloudflare 隧道（现状，降级为第三档）
再不通    → 自运营中转（E2E 加密，只见密文）
```

每一层只决定速度与成本，功能完全一致 对话消息、文件传输、审批、vault 解锁在所有层上行为相同

### 第 0 层 局域网直连

- 内核广播 mDNS 服务，App 用 Android NSD 扫到即直连内核局域网地址
- 价值最大、实现最独立、覆盖所有用户在家场景，流量不过任何外网
- 现有资产可直接复用 web server 已监听局域网、/api/upload 与 file-raw 已就绪、Matrix 客户端 API 一套代码两个地址

### 第 1 层 IPv6 直连（主路径）

- 内核监听双栈，使用非标高端口（如 8443，避开家宽普遍被封的 80/443）
- 设备寻址 内核自动上报当前 IPv6 地址到自运营服务（也可选 DDNS），App 经该服务查到地址后直连。地址只用于寻址，流量不过寻址服务
- 证书 ACME 自动申请与续期，内核后台维护
- Windows 防火墙放行由安装器 install.ps1 写入 netsh 规则
- 已知边界 光猫 IPv6 入站防火墙是软件够不着的物理卡点，型号杂、部分锁死。设计上一开始就把「IPv6 探测失败」当正常分支，静默回落，不追求该层 100% 覆盖

### 第 2 层 Cloudflare 隧道

- 现状原样保留，从唯一通道降级为回落档
- 免费、稳定可用，代价是国内访问质量波动
- 隐私上干净 隧道内是 TLS 加密流量

### 第 3 层 自运营中转（最终兜底）

- VPS 上跑纯转发 relay，只认设备对、转发加密帧、不落盘消息正文
- 端到端加密 手机与内核在扫码配对时交换会话密钥，服务器只见密文。这是自运营的底线设计，不经手明文
- 中转同时承担设备寻址职责（返回 IPv6 探测结果供择优）
- 成本 轻量 VPS 起步约 50-100 元/年；好消息是文件走局域网或分片直连，中转只承载消息小包，带宽压力小
- 国内 VPS 挂域名需 ICP 备案，一次性流程绕不开

## 用户操作清单（全量）

1. 装 coara，装手机 App
2. 扫码配对（手机连哪台内核必须告知一次，任何方案都省不掉）

其余全部自动化 检测 IPv6、选端口、注册寻址、申请续期证书、防火墙放行、择优与回落

## 文件传输配套（与连接层正交）

- 控制面与数据面分离已成立 对话走 /sync，文件走独立 HTTP，不共享发送队列
- 待补 分片上传与断点续传。现状 media upload 为整包 POST，断线全重来；CF 免费版还有约 100MB 单请求上限，4-8MB 分片顺带绕开。gomatrix 自建可加 /file/init、/chunk/{i}、/complete 三个端点
- 文件字节最终都落工作空间 uploads/，下游注入契约不变，内核侧零改动

## 落地顺序

1. 验证开发机 IPv6 入站可行性（本机前缀、光猫防火墙）——主路径地基
2. App 择优连接框架（地址簿 + 探测 + 回落）+ 局域网直连
3. IPv6 层（寻址服务先行，可先于中转服务器用轻量形式落地）
4. 自运营中转（依赖服务器采购与备案，最后做）
5. 文件分片续传可穿插任意阶段，独立增量
