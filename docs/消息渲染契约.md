# 消息渲染契约（Web 端）

> **一句话**：一条消息的**身份**（这是哪一条）与**位置**（排在哪里）是两个独立问题。
> 身份必须由**服务端键**唯一确定，位置必须由**线上序号（view_seq）**唯一确定；
> 端上只允许"到达得更快"，不允许"猜"，也不允许"留得更久"。
>
> **第二句话（2026-09-12 硬要求，I8）**：气泡一旦上屏，位置就固定——后续任何事件
> （实时帧 / 增量对账 / 重连回放 / 同文再发）只允许 ① 尾部追加新行、② 就地改某行内容；
> **不允许改变任何已显示行的相对顺序，也不允许整行重挂**。顺序的重建只允许发生在
> 「整条线重建」那一次（刷新全量重取 / 切空间 / epoch 变），且重建后必须等于 `view_seq` 升序。

本文是 web 端聊天区渲染的底层契约。改动渲染链路前先读这里；与代码不一致时以本文件为准并同步更新。

## 一、一条消息的完整生命（7 步）

| # | 环节 | 所在 | 关键点 |
|---|------|------|--------|
| 1 | 端上生成即时气泡 | `lib/store.ts` `addUserMessage` · `views/ChatView.tsx` `sendChat` | 生成 `clientMsgId`（身份）+ 乐观气泡（无 seq）；位置=列表尾部 |
| 2 | 发送 | `lib/ws.ts` `ClientMessage.chat` | 帧带 `text / attachments / workspace_dir / client_msg_id` |
| 3 | 内核受理 | `src/ui/web_server.py` `_handle_chat` → `_stream_chat_turn` | 绑定回合与空间；`emit("user_message", content, attachments, client_msg_id)` |
| 4 | 落带并分配序号 | `src/ui/turn_stream.py` `_record` → `src/ui/web_views.py` | **先落带后广播**：`persist` 分配 `view_seq` 并写回帧；序号同线永久单调 |
| 5 | 端上接收与裁量 | `store.ts` `handleServerMessage` | 边界守卫（workspace/session）→ 行存在性去重（序号已在屏上 ⇒ 整帧丢弃）→ 类型分派 |
| 6 | 落定（只有两条路） | `store.ts` `_appendRow` · `_mergeSnapshotRows` | ① 追加落定：尾部加一行（同序号幂等，已显示行不动）；② 对账落定：命中既有行只改内容、命不中追加尾部。**整表按 seq 重排只发生在整线重建那一次** |
| 7 | 渲染 | `features/chat/MessageList.tsx` · `ToolLineRow.tsx` | 一行一项，key 取服务端键（`store.ts::chatRowKey`）；类型按优先级分派；折叠区是该 item 的内部渲染 |

### 行存在性去重（第 5 步，`store.ts` `_hasRowWithSeq`）

- 内容帧带 `view_seq` 且**列表里已有同序号的行** ⇒ 这一帧已经上屏过（实时 / 重连回放 / 快照叠加三路都会送同一帧）→ 整帧丢弃，防双显
- 其它情况一律放行 → 由落定路径**追加在尾部**

判据只看「行在不在」，不依赖任何游标：因此既没有「假空洞」，也不需要补齐往返（旧的三走向序号闸门、空洞缓冲、退避重试、按文本判重已全部删除）。

### 渲染分派（第 7 步，`MessageList.tsx`）

优先级自上而下：分隔线 → 命令卡 → 工具行（隐藏则 `null`）→ diff 块 → 撤回行（`retracted`，不画）→ 空 assistant 行（`queued` 时画排队占位，否则 `null`）→ 普通气泡。
列表项只有一种：`ChatMessage`；"分组"是渲染期纯函数现算（`toolLineGroups` / `toolVisibility` / `diffPairing`）。
隐藏行（`toolVisibility` 命中的工具行、`retracted`、空 assistant 行）**只不画，仍在数组里占位**——删行会让它后面的行上移一格（跳）。

## 二、不变量（硬约束）

| # | 不变量 | 可执行判据 |
|---|--------|-----------|
| I1 | **身份唯一**：同一条消息在列表里最多一个 item | 合并优先级 `clientMsgId` → `seq` → 内容 key（`_mergeSnapshotRows` 一对一枚举）；认领链路见 `handleServerMessage` 的 `user_message` 分支 |
| I2 | **追加即冻结**：新内容只能追加在尾部；已显示行**永不被重排、跨位搬移或删除** | `_appendRow`（唯一追加入口）；`_mergeSnapshotRows` 命中既有行只改内容 |
| I3 | **两条落定通路**：① 追加（实时帧 / 回放帧 / 认领 / 命令输出）；② 对账（快照：命中即改内容、命不中追加尾部）。整表重排只在**整线重建**（`replace`） | `_sortBySeqAsc` 只被 `_mergeSnapshotRows(replace=true)` 调用 |
| I4 | **键稳定**：item key 与滚动锚键取服务端键（内容行 `s<view_seq>`、工具行 `t<tool_call_id>`、diff 行 `d<tool_call_id>`、带端上标识的用户行 `c<client_msg_id>`）；本地 uuid 只在"尚无服务端键"时兜底，拿到键的那一刻就地升级 | `store.ts::chatRowKey`；`MessageList` 的 `key` 与 `data-msg-key` 同源 |
| I5 | **隐藏即不存在**：可见性过滤必须先于间距 / 缩进 / 计数 / 邻接计算 | 插入任意条隐藏工具行，可见行的间距与折叠区计数逐字不变 |
| I6 | **端上零猜测**：不从正文文本推身份、位置或类型 | 渲染层不出现"按文本前缀判类型/判归属"的分支（认领的文本兜底只影响"配到哪一行"，不改变顺序） |
| I7 | **状态出口**：store 里写下的用户可见字段，必须既有渲染分支、又在 memo 比较器名单里 | 逐字段核对 `ChatMessage` ↔ `MessageBubble`（`sendFailed` / `retracted` 都已就位） |
| I8 | **已显示前缀不变式（硬要求）**：任一非重建落定后，已显示前缀的服务端键、内容与相对顺序**逐项不变**，新行只出现在末尾 | `store.selftest.ts`「已显示前缀不变式」块：迟到帧 / 回放帧 / 同文再发 / hydrate 对账 / `/new` 逐一断言；整线重建后顺序 = `view_seq` 升序 |

## 三、当前仍是"猜"的地方（收敛目标）

| 位置 | 猜法 | 证据 |
|------|------|------|
| 用户消息认领 | 三条启发式里的后两条（乐观标记会被重挂载净化、文本可能被改写） | `store.ts`；首选判据 `client_msg_id`。跟话与开局同走 `emit_user_message`（含 id/附件） |

## 四、薄弱点（按"会造成什么可见不适"排序）

1. **发送早失败无任何反馈**：`store.ts` 把尾部乐观泡标 `sendFailed` 并刻意不追加错误气泡，但渲染层从来没有 `sendFailed` 分支、memo 比较器也没列它 → 用户看到一条"正常已发送"的气泡。（已修）
2. **滚动锚点脆弱，三种可见跳位**：锚点是绝对像素；无快照回退的切空间路径分两次提交，第二次 `skeletonToContent` 直接判 bottom 覆盖锚点（靠 React 批处理"侥幸"正确，脆性耦合）；贴底补偿只到两帧，而图片 `loading="lazy"`、KaTeX/高亮都在之后到达。（键已改服务端键——对账不再换键，锚点因此不会因重挂而失配；像素补偿部分未动）
3. ~~无序号 hydrate 整表换 key~~（已修）：`chatRowKey` 让 key 与 id 脱钩，`_mergeSnapshotRows` 命中既有行时 id 与位置都不动 → 折叠面板与手风琴展开态不再因对账复位。
4. **隐藏行的间距没排除**（已修，见第六节）。
5. **过程组条目在"树行 → 落带帧"切换时文字跳变**：同一工具先从活动树进来（label 由 TS 拼、80 字截断），帧到后被服务端 label 替换，行内文案与标记（◌→✓+耗时）变一次（属"改内容"，不改行序）。
6. **渲染层自造条目类型**（文本判型）：命令输出前缀判分隔线、模块会话按 ✓/✗ 切正文。
7. **活动树父归属靠推断**：恰有一个活跃 delegate 就认父，缺父字段的工具行可能被挂进别人的折叠区。
8. **模块会话滚动与重绘**：每次 messages 变化都 smooth `scrollIntoView`，流式期间持续平滑滚动；列表无 memo。
9. **渲染窗口 200 / 内存 300 无提示**：长会话里最早的行在 store 里但不在 DOM 里，往上翻会"凭空消失"（尾部追加时 `_capMessages` 从头部丢最旧——只丢行、不动其余行序），没有"加载更早"入口；另有刷新 200、切空间 100 两个常量。
10. **折叠区两级嵌套滚动**（组 160 / 面板 240 嵌在主滚动容器内）：滚轮先吃内部滚动，到底才带动列表，手感粘滞。
11. **memo 白名单漏字段**：`dividerTime` / `queued` / `sendFailed` / `retracted` 渲染读取，比较器已补齐前四项（新增可见字段必须同时进渲染分支与比较器 —— I7）。
12. **分隔线时间回退到"落盘时刻"**：缺 `divider_time` 时用的是分隔帧写入时刻，深夜写帧会失真。
13. **每帧读一次计算样式**：`framelessPadding()` 渲染期 `getComputedStyle`，变量缺失静默退化为 8px。
14. **迟到 / 补齐的行只按到达序落尾部**（本次定案换来的代价，按用户硬要求）：序号比屏上小、或本地从没收到的行，一律追加在尾部——**它在历史里的正确位置暂时是错的**，直到下一次整线重建（刷新首屏 / 切空间 / epoch 变）按 `view_seq` 纠正。同一序号的帧永远不会重复上屏（行存在性去重）。
15. **同文重复的残余窗口**：对账不再删除已显示行 ⇒ 当权威行既没有 `client_msg_id`、内容 key 又对不上（服务端改写过文本）时，屏上会短暂出现两条同文行，直到权威帧到达就地认领（亚秒级自愈）。跟话已与开局同走 `emit_user_message`（含 id/附件）；残余多见于无标识的老带。
16. **同一件事在"实时路"与"落带路"上仍不同构**（服务端 P0-B 余项）：`divider` 只落带不广播；实时 `file` 帧不带 `view_seq`（且 kind 名 `file` vs `files`）；`command_result` 实时无序号而落带被投影成 `turn_start+chunk`。端上因此会把它们当"新行"追加（顺序不乱），但**形态/位置在刷新后会变一次**。
