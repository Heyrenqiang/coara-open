# 用户自建空间设计

> 状态：立项文档（2026-09-23），仅定方向与结构，具体实现后续推进
> 升级：《空间能力系统》（docs/空间能力系统.md，09-29）是本文的收束与升级——UI 改裁决为运行时插件化（推翻 §横切难点的 iframe 倾向）、引擎定性外部软件零槽位、主体装配泛化路径、空间级能力声明，均以新文档为准
> 依据：两路只读调研（aide）对 flow 空间装配链路的完整摸底，结论互证一致

## 愿景

用户能从零构建一个像「工作流」这样的空间：自己的 persona、自己的工具面、自己的业务引擎、自己的主页 UI。内核退到「抽象对话能力提供者」的位置——会话、消息、工具调度、事件通道、多端分发是通用底座；空间类型是用户可定义的。

对照目标：flow 空间（工作流创作者空间）是这套能力的第一个内置实例，证明骨架可行；本设计要把它从「内核特权产物」变成「用户可达的通用能力」。

## 核心理念（用户裁决）

- 内核只提供抽象的对话能力，不托管业务引擎
- persona、工具、UI 都是可配置的
- 业务引擎（如 WDL）是用户自己的软件，内核零 import、零托管——今天 WDL 已是独立软件，范式已成立
- 用户自己设计 UI 的显示方式

## 现状差距（调研结论摘要）

flow 空间的装配全部由内核写死，用户面入口没有一个能触达：

- 登记装配 `_CREATOR_WORKFLOW` 七元组是源码常量（`src/workspace/system_spaces.py`），内核启动无条件登记，同路径条目每次启动被强制矫正回出厂值
- 身份字段 `content_type/storefront/home_view/persona/view` 在 WorkspaceEntry 模型与持久化层都是通用字段，但 ws 工具、web 创建 API、CLI 全部不收——除手改 workspaces.yaml 外无任何用户入口
- persona 加载本身无白名单（文件齐备即得），但查找路径只含内置 `src/coara/prompts/agents/`，用户目录不在扫描路径
- 前端主页是编译期静态表：react-router 路由 + navRegistry 六路由白名单，home_view 指不到已注册路由一律退回对话页
- FlowRoot 全局单例 + WDL 草案系统级单库（`<coara_home>/users/default/workflows/drafts/`），无空间维度——多个工作流空间必然串

用户当前可自建约三成：空间壳（kind/name/目录/summary）、门面形态（space.yaml 三选一）、空间级模型绑定、在任意空间用 orchestrator 编排（无画布）。

## 结构：一个底座 + 四个并列能力面

能力面之间是并列关系——每个面对应一类用户可配置的东西，各自独立开放、独立生效，不存在先后依赖。底座是它们共同站立的地方。

### 底座：对话能力（内核，不动）

会话、消息、回合、工具调度、多端分发、录像带、审批、记录。这层已是通用的，用户自建空间免费获得。

### 能力面一：身份声明

让用户能声明「这是一个什么类型的空间」。

- `ensure_workspace` / web 创建与编辑 API / `coara ws add` 增加可选 `content_type/storefront/home_view/persona/view` 参数（模型与持久化已就绪，只缺入口）
- space.yaml 扩展为身份声明的磁盘真源之一（空间随目录搬迁时身份跟着走）
- flow 空间登记改为配置驱动：`config.yaml` 加开关（发布可不预置）；「强制矫正出厂字段」仅对出厂路径生效，尊重用户手改

### 能力面二：persona

- `AgentRegistry.scan` 查找路径追加 `<coara_home>/users/default/agents/` 与工作空间级 `.coara/agents/`（后者覆盖前者，与技能加载三层优先级同范式）
- 用户写一对 `{name}.yaml + {name}.md` 即注入自定义空间主体

### 能力面三：工具面（基本已就绪）

磁盘工具包机制（`.coara/tools/` + 用户级 `users/default/tools/`，TOOL.md + 入口 Python）已经是用户自定义工具的完整通道。缺口只在 persona yaml 的 `tools.include` 白名单如何与空间身份联动——随身份与 persona 两面开放后自然解决。

### 能力面四：业务引擎用户态（已是事实）

用户的引擎是独立进程/独立软件（WDL 范式）：内核不 import、不托管、不感知其内部。空间内会话通过工具调用与引擎交互（读写其文件、调其 CLI、或经事件源收其通知）。这一面不需要内核改动，只需要文档与示例（「怎么写一个自己的 WDL」）。

引擎用户态化之后，「数据按空间隔离」天然由用户的引擎自己负责；内核侧只剩它自己仍持有的东西（FlowRoot 类模块主体的单例化）需要处理。

## 唯一的横切难点：主页 UI

四个能力面之外，有一个不属于任何一面的横切问题——「用户自己设计 UI 怎么显示」。前端是编译期静态 SPA，用户页要进来只有三条路：

- iframe 承载 空间主页指向用户提供的 HTML/本地服务端口，内核主页壳内嵌 sandbox iframe。隔离天然成立（不透明源拿不到 dashboard token，与文件页 HTML 渲染同款裁决），代价是与主站视觉/交互割裂
- 远端组件 动态 import 用户 JS bundle。自由度最高但安全风险最大（与主站同域同 token 上下文），需要签名/白名单机制
- 声明式页面 内核定义一套页面描述（区块、数据绑定、动作），用户写 yaml/json 而非代码。安全可控但表达力受限，做不成画布这种重度交互

前置小步（先做）：home_view 白名单加安全降级——未注册的主页显示「暂无主页」而不是落回对话页，为后续开放留出语义空间。

终态倾向：iframe 承载为主线（安全边界清晰），声明式页面为轻量备选；远端组件不做，除非出现真实强需求。

## 推进建议

四个能力面各自独立，可按任意顺序做；建议先做改动最小、收益最直接的两个（身份声明、persona），引擎面写文档与示例即可，UI 横切难点单独立项。
