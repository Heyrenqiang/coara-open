# 空间性质模型（数据主权 · 投影 · 写入契约 · 接入分发）

> 状态：概念共识（2026-09-10 讨论产物，含三轮修订：门面三形态 → 正交维度 → 坐标系 → 种子与树 → 接入分发）。
> 本文修订 [`空间模型与内容注册表.md`](archive/空间模型与内容注册表.md) §3「门面三形态」：**三形态不是空间分类轴**，而是缺省模板。分类轴应换成下面这组正交维度。
>
> **实施范围（2026-09-10 决策）**：方向全部成立，但**落地聚焦单实例、单用户、可演示** —— 先把「一个人在 coara 上做空间、用空间、把空间做好用」做到足够强。§7「接入与分发」是**去中心化生态**，需要服务端支撑，**属远期，当前不实现**；等用户规模起来，再议空间之间如何连接。本文其余章节（§1–§6、§8–§9）为近期设计的依据。

## 0. 一句话

**空间 = 数据 + 投影 + 写入契约。** 界面 = `投影(数据, 视图参数)`。差异全部在"数据"这一项；"投影"对所有空间一律自由。这就是三种东西能被统一成"工作空间"的原因。

能力（工具 / 插件 / 技能）**同样以空间形态存在**并接入内核 —— 于是**内容生态与能力生态是同一种东西**（§8）。

再进一步（2026-09-14 共识）：**一个软件也是一个空间**。软件 = 数据 + 显示 + 逻辑；把逻辑层从写死的代码换成工作流，软件即 agentic 化 —— 空间是这三样的天然容器（§10）。

## 1. 为什么能统一，统一发生在哪里

旧世界的界面是**编译期写死**的：前端页面由程序员硬编码，所以"性质不同的数据"被迫做成不同的页面 —— 用量做一个看板页、配置做一个表单页、文件做一个浏览器页，互相不可通约，无法统一。

新世界的界面是**运行期可编程**的：投影参数（聚合方式、分组、版式、查看器）可以由对话生成与修改。于是：

- 数据性质的差异**下沉**到数据契约里（谁的内容、能否冻结、写入有何后果）
- 界面层（投影 + 渲染）得以**归一**：一套骨架、一套导航、一套令牌、一个对话入口

**统一发生在投影层，差异下沉到数据层。** 端只渲染投影，取各端能力交集（Web 全渲染、App 卡片、CLI 文本）。

## 2. 四个维度（正交，取代三形态）

> 维度一列出的三种主权是**当前已注册的实例**，不是闭集。空间的类型由 `(数据来源, 可变性边界)` 两个坐标决定，新增一种只是坐标系里多一个点 —— 详见 §7、§8。

### 维度一 · 数据主权 —— 决定「什么不能动」

| 主权 | 是什么 | 冻结边界 | 例 |
|---|---|---|---|
| **用户资产** | 内容属于用户 | 无冻结，全可动 | v8 / nx 的文件 |
| **系统观测** | 内容是"用户如何使用本软件"的事实 | 冻结为**事实**，只读 | 用量、记录 |
| **系统配置** | 内容是"本软件的行为参数" | 冻结为**契约/模式**，值在模式内可动 | config / providers |

冻结的从来不是"展示"，是**数据**：观测冻结为事实（改它等于伪造历史），配置冻结为契约（改错会毁掉系统）。

### 维度二 · 投影自由度 —— **对所有空间相同：完全自由**

投影 = 对数据的一次只读变换（聚合 / 分组 / 排序 / 图表 / 版式 / 查看器选择）。

- 关键性质：**改投影不触及数据**。所以"展示无限自由"与"数据被冻结"并不矛盾 —— 用量可以按天/按周/按模型随意换视图，而用量数据本身分毫不动。
- 因此：**展示不重要，随意修改都没问题**（用户原话）。真正要钉死的是"哪些东西不能动"，不是"长什么样"。
- 投影参数本身是空间里的一种内容类型（视图定义），于是"改变显示"折叠成"改变内容"，两个动作在同一循环里闭合；它可被对话修改。

### 维度三 · 写入契约与生效语义 —— 仅当写入被允许时存在

| 写入类型 | 契约 | 生效 | 回滚 |
|---|---|---|---|
| 用户资产写入 | 无契约 | 立即（文件即真相） | 无（靠版本控制/备份） |
| 配置写入 | 有模式 + 校验 | 分级：即时 / 热重载 / 需重启 | **必须有** |

**配置的真正特殊性不是"能改"，而是"改有契约、有副作用、有生效语义、可回滚"。** 这是它区别于"用户资产随便改"的唯一地方，也是它区别于"只读观测"的地方。

### 维度四 · 默认落点 —— 是缺省，不是性质

每个空间默认点进来落到**会话**还是**主页**，只是一个缺省值：v8 默认落会话（用户也可以给它设计一个主页来展示这个空间）；用量默认落主页。**用户随时可改，不写死。** 呼应原文档"缺省即正确"。

## 3. 「门面三形态」正名

仓库 / 展示 / 营业 三个词，描述的是「数据主权 + 默认落点 + 惯用介入方式」这三个正交量的**常见组合**：

- 仓库 ≈ 用户资产 + 默认落会话
- 展示 ≈ 系统观测 + 默认落主页
- 营业 ≈ 系统配置 + 默认落主页 + 写入有副作用

它们是好的**命名与缺省模板**（用于开箱默认、用于文档沟通），但不能当**分类轴** —— 一旦当分类轴，就等于宣称"这个空间天然只能对话/只能看/只能改"，而这三件事用户全都能变。保留三形态作预设，分类改用上面四个维度。

## 4. 配置：变更流水线

配置是唯一"写入有副作用"的类型，需要一条完整流水线（不是单点写入）：

```
① 声明   模式 + 约束（可改什么、怎么改、值域）
   ↓
② 校验   改前验证（模式校验 + 语义校验）
   ↓
③ 写入   落盘新版本（配置版本化）
   ↓
④ 生效   按项声明的生效级别：
            即时   —— 下次读取即生效
            热重载 —— 无需重启进程，重载即生效
            需重启 —— 必须重启（如端口、连接池）；评估能否改为热重载
   ↓
⑤ 回滚   失败或用户反悔 → 回到上一版本
```

要点：

- **生效级别是逐项元数据**，在模式里声明，不能全局一刀切。用户问的"要不要重启、不重启能不能生效"由该配置项的声明回答。
- **回滚是一等公民**：配置版本化（保留上一版），失败自动回滚，用户也可手动回。
- 保存有副作用这一条，是"营业"类比里唯一为真的部分，其余（能否改、主通道是谁）都是可变姿态。

## 5. 对 Web 架构的推论

**统一层（所有空间共用，与内容类型无关）**

- 页面骨架：`PageShell` 固定槽位（身份头部 / 工具条 / 内容区 / 可选检查器 / 常驻对话入口）
- 导航模型：注册表驱动，不再是硬编码的二元分组
- 设计令牌：单一真源，组件只引语义变量
- 常驻对话入口：所有空间同一入口

**差异层（由「内容类型注册表」逐类型声明）**

每个内容类型登记：`{ 数据主权, 冻结边界, 写入契约, 生效语义, 默认落点, 查看器 }`。查看器只负责"读数据 → 渲染投影"；数据主权与写入契约与查看器解耦。

**推论**：视图不再是空间的属性（原文档的判断依然成立），也不再是"形态"的属性 —— 视图是**投影参数**，对所有空间同构，随时可改。空间真正声明的是"数据侧的规则"，界面侧全统一。

## 6. 不是三个类型，而是一个坐标系

§2 的三种主权（用户资产 / 系统观测 / 系统配置）是**当前已注册的实例**，不是分类的闭集。空间类型由两个坐标决定：

```
类型 =（数据来源, 可变性边界）
```

- **数据来源**：内核内生（系统自身）/ 用户自建 / 外接空间（他人发布，接入内核即可用）
- **可变性边界**：无冻结 / 冻结为事实 / 冻结为契约 / 冻结为契约且有副作用

新增一种空间 = 坐标系里多一个点，**不需要新造"类型"概念**。可预见的补充（都在系统侧，由内核定义）：

| 来源 | 可变性 | 已存在 | 可预见 |
|---|---|---|---|
| 内核内生 | 冻结为事实 | 用量、记录 | trace、审计、健康、事件流 |
| 内核内生 | 冻结为契约 | 配置、providers | 技能清单、工具白名单、定时任务 |
| 用户自建 | 无冻结 | v8 / nx 文件 | 任意 |
| 外接空间 | 接入契约（见 §7） | —— | 他人发布的工具 / 插件 / 技能 / 查看器 |

**两侧的不对称（关键）**：

- **系统侧有限** —— 它是"系统关于自身的陈述"（内核照镜子）：用量/记录 = 系统做了什么，配置 = 系统该怎么行为。**谁写内核，谁定义这个集合**，所以规模由内核作者控制。
- **用户侧无限** —— 内核只提供**能力**（沙箱、LLM、存储、事件总线），不预设内容；内容由用户填，空间因此可无限。

## 7. 接入与分发：能力也以空间形态存在

> **对本节旧表述的更正**：此前写作"升格"（用户产物 → 成为厂家内置 / 出厂预设），**方向错了**。正确机制是**分发** —— 横向、去中心化、人人可发布。

工具、插件、技能 **都以空间的形态存在**，接入内核即可用：

- 你做出来 → 接入内核 → **别人也能接入内核、也就能使用**
- **人人都是开发者**；贡献值成为生态的度量（§7.4）

### 7.1 这是"一切皆空间"的收口

内核只需要**一种接入机制 —— 空间**。不必为工具 / 插件 / 技能各造一套接入方式。于是：

- 接入门槛 = "建一个空间"，而这本来就是用户会做的事
- **能力生态与内容生态合并成同一个东西**（都是空间）
- "人人都是开发者"不是愿景，而是**接入机制统一之后的必然结果**

### 7.2 内核职责因此收窄

内核不膨胀成"什么都内置"的巨兽。内核只持有：**执行体 + 接入契约**（挂载 / 声明 / 沙箱隔离）。能力生态在核之外、**空间之间**生长。

### 7.3 分发 ≠ 升格

| | 升格（旧，错） | 分发（正） |
|---|---|---|
| 方向 | 向上：成为厂家内置 | 横向：成为他人可接入的空间 |
| 中心 | 中心化，需厂家审核 | 去中心化，人人可发布 |
| 单位 | 出厂预设 | 空间 |

出厂默认预设仍可存在，但它是**起点共识**（§9.5），不是能力生态的主通道。

### 7.4 贡献值 = 生态的度量层

分发要成立，需要"发现与排序"：

- 度量：被接入次数 / 真实使用量 / 被依赖度
- 要点：贡献值必须基于**真实使用**，不能是点赞 —— 否则可刷，退化成游戏
- 贡献值是分发的基础设施（决定"别人怎么找到有用的空间"），不是装饰

### 7.5 分发引入的新约束

1. **信任** —— 接入别人的空间 = 执行别人的代码 → 沙箱是硬底线
2. **依赖与版本** —— 空间可依赖内核版本或其他空间 → 依赖图 + 版本约束
3. **发现** —— 人人可发布 → 海量 → 需要排序与推荐（§7.4）
4. **撤回** —— 作者删除 / 变更时，使用者钉住版本还是跟随？
5. **署名** —— 如何确认"这个空间"出自"那个人" → 签名 / 命名空间

**不变式（仍成立）**：接入他人的空间只获得**能力声明**，不获得对系统数据的任意写权；内核始终是唯一执行体。用户资产空间无限自由，但**以空间形态对外提供能力时，必须接受接入契约** —— 可变性边界不会因分发而消失，只会被重新声明。

## 8. 完整模型

- **静态坐标**：`(数据来源, 可变性边界, 默认落点)` —— 描述任一空间
- **动态路径**：接入与分发（空间之间横向流动），受接入契约约束（§7）
- **不变式**：
  - 内核是唯一执行体
  - 投影对所有空间一律自由
  - 差异只在数据侧（主权 / 冻结边界 / 写入契约 / 生效语义）
  - 对外提供能力 = 从「无契约」进入「有契约」

## 9. 交付即分化：种子与树

软件交付后不是"一个系统"，而是**每个用户各自的一个系统**。出厂形态是**种子**（能力 + 默认预设 + 约束），用户实例是**长成的树**（在种子上长出独一无二的形态）。§6 说的"系统侧有限"，指的是**出厂时**有限；出厂后每个实例各自演化，"系统侧"因此复制成 N 份。

### 9.1 定制压力全部泄到投影层

用户之间"每个都不一样"，差异几乎全发生在**投影层**（展示），而非数据层。这正是不变式"投影一律自由、差异只在数据侧"的价值：**N 种个性化的冲击落在不碰数据的一层上，数据侧安然无恙** —— 这才让"统一 + 无限定制"同时成立。

定制对象的风险梯度：

| 定制对象 | 副作用 | 治理 |
|---|---|---|
| 投影 / 展示 | 无（改投影不动数据） | 完全自由，改坏无代价 |
| 用户资产数据 | 无外部副作用 | 自由（用户自己的东西） |
| 系统侧（配置 / 接入能力） | 有（契约 + 生效 + 回滚） | 必须版本化、可回滚、可审计 |

### 9.2 定制必须可流动，否则只是碎片

N 个用户 = N 座孤岛，没有价值。定制要成为资产，必须可**存取 / 分享 / 分发 / 组合**：

- 投影预设是一种**内容类型**（可存进空间、可分享、可版本化）—— 呼应 §2 维度二
- 用户 A 做的空间（含工具 / 插件 / 技能 / 预设）→ **别人接入即可使用** —— 呼应 §7 **分发**

于是"每个用户都不一样"从碎片变成**生态**：默认预设是共同起点，个人定制是分化，**分发是横向流动**（不是向上回流到厂家）。

### 9.3 交付物是"可被改的东西"，不是"改好的东西"

传统交付：软件公司定义界面 → 用户使用。界面一旦由用户改写，这条路就断了：

- 产品团队无法靠"设计一个界面"交付价值 → 交付物必须是**底座 + 默认预设 + 约束 + 可组合积木**
- **设计的工作从"产出界面"变成"产出可被安全改写的界面"**：设计令牌、页面槽位、组件积木、默认预设、定制的边界

这正是 Web 设计体系（令牌单一真源 / PageShell 槽位 / 组件分层）的深层理由：**不是为了让界面更好看，而是为了让界面可被安全地改写。**

### 9.4 核心矛盾：升级 vs 定制

底座升级后，用户的投影定制可能引用已不存在的组件 / 字段而失效；若直接覆盖用户定制，等于背叛用户。需要：

- 投影定义**版本化 + 迁移**（底座变更 → 定制跟着迁移）
- 底座变更时**提示受影响的定制**，由用户决定，不悄悄改
- **一键回到出厂默认**，随时可退（也是排障兜底）

### 9.5 出厂默认 = 事实标准

绝大多数用户不会大改、或只改一点 → **默认预设成为 N 份实例的共同锚点**。「缺省即正确」在这里有了第二层含义：默认不只是省事，它是分化的**起点共识**。因此默认要极克制、极好用。

## 10. 空间即软件：agentic 软件 = 数据 + 门面 + 工作流逻辑

> 2026-09-14 共识。把「一切皆是空间」推到软件层：不只是一个对话目录是一个空间，**一个软件也是一个空间**，包括 agentic 的软件。

### 10.1 三层拆解

任何软件都可拆为三层，且三层恰好一一落到空间的三样东西上：

| 软件层 | 空间对应 | 说明 |
|--------|----------|------|
| 数据 | 空间的内容 | 文件、schema、投影源 |
| 显示 | 空间的门面 | 页面、用户交互 |
| 逻辑 | 空间的流程 | 由工作流实现 |

**agentic 化 = 逻辑工作流化。** 传统软件的逻辑是编译期写死的代码；agentic 软件把这一层换成 wdl 编排的图，节点是 LLM 驱动的 coaras。显示与用户交互照旧，但它们消费的逻辑由工作流产出。

注意区分入口与本体：**会话是逻辑的构建入口**（跟 FlowRoot 聊，把逻辑聊出来），**工作流图才是逻辑的本体**（wdl 图 + coaras 节点，经 wdl 引擎跑）。

### 10.2 各件归位

这套模型下每个部件的位置因此圆通：

- **coara**：以工作空间为核心的运行时。简单空间（一个对话目录）与复杂空间（一个 agentic 软件）是同一模型，不分两种东西。
- **wdl**：造 agentic 软件的引擎工具，与 coara 配套 —— 把逻辑层做成可编排、可固化、可独立运行的图。
- **flow 空间**：出厂自带的「已经是 agentic 软件」的样品。它没有任何特殊性，就是一个普通工作空间，无非门面带了画布显示、逻辑带了 FlowRoot 会话。此前把 flow 当「功能模块」塞进系统空间之所以拧巴，根源就是它本不是模块，是一个工作空间。

### 10.3 例证：agentic 笔记软件

- **门面**：笔记列表、编辑器、按钮 —— 传统 UI
- **数据**：笔记文件、分析结果、schema
- **逻辑**：一套工作流在底下支撑 —— cron 定时节点（到点触发分析）、界面按钮手动点火某节点、节点间 success/error 级联（干完交给下游汇总、回写）

触发的三态都在 wdl 里：cron 定时、界面手动点火、节点级联。界面只负责「按一下」和「看结果」，干活的编排在图里。

### 10.4 用户造空间的路径

复制 flow 的样子，换四样东西：自己的 schema、自己的 wdl 图、自己的工具、自己的页面。flow 空间作为出厂参考实现的全部意义在此。

### 10.5 已知缺口：门面与逻辑的投影契约

当前的工作流画布只是**图的生产视图**（给建图的人看的节点画布），还不是**软件的门面**（给用户用的业务界面）。agentic 笔记那种形态里，工作流藏在底下，用户看到的不是节点而是「分析中 / 已出结论」。缺的一层是：**把工作流运行状态投影成业务 UI 可消费的东西** —— 节点不是界面元素，是界面的后台工人。这层投影契约（门面如何订阅图状态、按钮如何点火节点、结果如何回写门面）未设计、未动工。

### 10.6 工程量级判断

这是一个超级巨大、且创新空间无上限的工程：门面投影契约、schema 自定义、空间打包分发、wdl 与门面的双向桥，每一层都是独立工程。当前只做地基第一铲 —— flow 归位成普通空间、模型先圆通，工程以后一步步来。天花板不在工具侧，在使用者的想象力侧：底座只负责把「数据 + 门面 + 工作流」三样的拼装成本压低，上面能长出多少种 agentic 软件是开放的。

## 11. 待决

- **投影 DSL 的形态**：投影参数是结构化配置（表单可控、可校验）还是自然语言模板（灵活、不可校验）？或两者分层（结构化内核 + 自然语言表层）？
- **配置热重载能力清单**：逐项标注当前能力（即时 / 热 / 需重启），并评估哪些"需重启"项可改造成热重载。
- **配置版本化粒度**：整文件版本 vs 逐项版本。
- **接入契约的准入模型**：私用与发布（供他人接入）的分界在哪？签名 / 署名与信任分级怎么落地？
- **外接空间的权限模型**：能力声明如何粒度化（读哪些数据、调哪些工具）？与现有工具白名单 / 沙箱策略如何对齐？
- **用户空间 → 系统侧数据**：用户是否可能产生"系统观测"（如用户自建工具的用量/日志）？若可，其主权与冻结边界归谁？
- **分发基础设施**：发现与排序（贡献值口径）、依赖图与版本约束、作者撤回时的语义（钉版本 vs 跟随）。
- **分发通道的形态**：空间如何在人与人之间流转（导出 / 链接 / 市场 / 订阅）？是否需要独立的"分发空间"？
- **定制漂移的排障**：每个用户界面不同 → 无法靠截图定位问题。定制快照 / 诊断包如何导出与复现？
- **底座升级与用户投影的兼容 / 迁移**：投影定义的版本与迁移机制如何设计（§9.4）？
