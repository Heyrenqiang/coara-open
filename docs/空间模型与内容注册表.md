# 空间模型与内容注册表（概念备忘）

> 状态：**概念共识（2026-09-08 讨论备忘）**，非实现方案。内容为「一切皆是空间」模型的统一表述、门面三形态模型与开源布局推论。
> 相关既有实现：`src/workspace/types.py`（WorkspaceKind/ViewCapability）、`src/ui/web/src/views/`（各查看器雏形）、`src/workflow/`（WDL 引擎）、`src/matrix_client/approval_bridge.py`（控制通道）。

## 1. 核心命题

一切皆是空间。空间 = 内容 + 展示；用户可以基于空间里的内容对话。空间之间没有本质区别，区别只在内容类型、查看器、门面形态，以及内容与系统是否联动。

程序不属于空间。WPS、Blender、WDL 引擎这类程序（工具/引擎）都是空间之外的存在，像 Office 之于 docx——它们被调用，不挂在任何空间下。

存在分类因此收齐四类：**内核**（执行体）、**空间**（内容与身份）、**端**（连接与渲染通道）、**独立软件**（引擎等外部能力，被内核调用，不归属前三者）。WDL 引擎是独立软件：独立于 coara 之外、可独立分发的软件，coara 是它的用户之一。二者唯一契约是内容格式兼容——coara 生成的 WDL 引擎必须能跑，但引擎不是内核、不是端、也不是空间内容。这让引擎有独立存在的理由（第三方也能生产 WDL），也让 coara 不被引擎绑死。

**每个空间都有主页**。主页 = 空间身份的呈现页，即空间的官网首页。对话不是「无主页空间的替代品」，而是主页的一种版式下主业务的入口。

## 2. 空间模型

一个空间是挂在内核上的、可对话的内容容器，声明四样东西：

- **内容**：空间装什么。目录只是文件形态的物理载体；内容可以是磁盘文件，也可以是虚拟文档（查询/聚合生成，如用量报表、消息流、记录时间线）
- **展示**：内容类型对应的查看器。文件空间=文件浏览+代码视图，用量空间=看板，配置空间=表单。对话框不是空间的展示，它是全空间共用的对话通道
- **persona**：空间里对话的主体是谁（默认 main，可绑专属 agent）。店员贯穿整个空间：会话的上下文与记忆是空间资产，不属于任何端，不随用户离开清空
- **空间身份**：这家店的完整身份，含名称/描述、门面形态、活跃内容预览。space.yaml 是空间身份的落盘形式（可缺省，见 §3 覆盖链）

空间类型的真实载体不是空间本身，而是**内容类型注册表**：文件/内容类型 → 查看器 + 编辑器 + 动作。像操作系统按扩展名关联程序：`.docx` 用 Word 开，`.wdl` 用引擎+图编辑器跑。视图不再是空间的属性，而是内容类型的属性。

动作是绑在内容类型上的工具：`.wdl` 的动作是提交给引擎执行，config 的动作是保存后生效（热重载），`.md` 的动作可能为空。查看器本质统一：读内容、渲染；特殊查看器多一个写回。

## 3. 门面三形态与主页版式

> **修订（2026-09-10）**：本章「三形态」不应作为**空间分类轴** —— 它把「能不能改」当成了空间的固有属性，而这是用户随时可变的姿态。分类改用 [`空间性质模型.md`](空间性质模型.md) 的四维（数据主权 / 投影自由度 / 写入契约与生效 / 默认落点）：**统一发生在投影层，差异下沉到数据层**；三形态降级为缺省模板。

空间类比店面：每个空间都有门面（主页），形态由**用户介入内容的方式**决定——内容是看的对象、直接改的对象、还是通过对话下令操作的对象。页面与对话谁当主通道，取决于哪种介入对用户最高效：

- **仓库**（闭门运作）：内容不需要摆出来，用户在对话里下令运作，店员干活。例：v8（几千个代码文件不值得直接看，点链接打开是最小外显；对话是主业务）
- **展示**（橱窗）：内容是结果，用户要瞄一眼。页面只读呈现，对话退到辅助位（可问「这个月哪个模型最贵」）。例：用量
- **营业**（柜台/操作台）：内容要被用户亲手改，页面经常动。例：配置（表单即编辑入口，保存有副作用）

**主页骨架统一**：空间身份头部 + 内容区 + 导航（对话入口恒在，深度可变）。形态只决定内容区版式与主入口位置。仓库形态的主页不是空白聊天框——它带空间身份（概况、最近动态、文件入口），对话是其主入口。

**判定覆盖链**（越往下越具体、越后生效）：

- 内容类型注册表给类型默认（代码工程→仓库，用量→展示，配置→营业）
- 空间清单 `space.yaml` 覆盖类型默认（可缺省；v8 不写也天然是仓库）
- 用户偏好再上层覆盖（极少用）
- 会话动作最上层，只影响本次姿态，不写死配置（对话里说「打开显示」「改成按周聚合」）

缺省即正确：配置文件的意义是偏离默认，不是必填表。

## 4. 显示与存储

- **打开显示**：把空间或条目的显示形态唤出来。仓库空间的文件链接打开是最小形态；用量打开是聚合页；配置打开是可编辑表单页
- **改变显示**：改的不是数据而是呈现（用量按周聚合、配置只显非默认项）。视图定义本身是空间里的一种内容类型，于是改变显示折叠成改变内容，两个动作在同一循环里闭合
- **显示是拉取不是推送**：默认什么都不弹，用户问/点/打开才呈现；唯一主动外显的是异常与待决（错误、审批、阈值、到期）
- **落盘物只有三类**：内容文件、会话档案（事件流 + 快照）、视图定义。主页**不落盘**，每次打开都是对当前内容的此刻渲染，空间因此点开永远新鲜
- **会话是流，主页是投影**：事件流 append-only 保历史不丢，快照保快速恢复。用量空间的 events.jsonl 是事件流、页面是投影；会话是另一种事件流、主页是另一种投影——存储模型在空间层合流

## 5. 端 = 渲染能力层

端不参与空间定义，只参与渲染。空间声明意图层（内容是什么、主页想给什么），端是能力层（能渲染出什么）：

- 全渲染端：Web、Electron（完整页面）
- 受限渲染端：手机 App（卡片、列表、摘要）
- 文本渲染端：CLI（表格、文本链接）

意图与能力取交集：CLI 无页面渲染器时，展示页降级为文本摘要加链接；降级规则跟端能力一起登记，不做全局兜底。

会话档案是空间级、跨端共享的单一事实，端只是接入点（Web 聊一半，手机点开同一空间恢复同一份会话）。因此决定显示什么的配置必须落在类型层和空间层，不能落端层——落了端层，同一空间在不同端就分裂。

## 6. 用户主体

用户是所有空间的主人，不是客户：店是用户的资产，店员服务的是主人，三种门面是主人与自家资产打交道的三种姿势。

用户本身也是跨店主体，需要一个不挂在任何店下的壳（用户主页、全局记录、最近动态），所有店员认得同一个客人。用户档案与空间会话档案分开存：一个在用户域，一个在各空间域。

客户（外部角色）是另一层概念，后续再议：届时店员需区分主人与客户的服务方式。

## 7. 系统页 = 普通空间

消息、记录、配置、用量与 v8、nx 并列，无本质区别。差异只在：

- **消息**：内容=会话流（活通道，非静态文件），查看器=对话视图，persona=main
- **记录**：内容=记录库，查看器=时间线，不需工具只需展示
- **用量**：内容=实时用量报表（虚拟文档，聚合查询生成），查看器=看板，刷新=重新查账
- **配置**：内容=config/providers，查看器=可编辑表单。唯一特殊处不是「可编辑」，而是保存有副作用（热重载/刷新连接）

实现推论：内容标识符（如 `usage:last7d`）+ content_type 决定查看器。注册表需区分取数方式：file 型走文件系统，report 型走内核 API；查看器不关心，拿到统一内容对象。

## 8. 工作流：WDL 是内容类型，coara 只是生产者与文件宿主

工作流空间不存在。WDL 是一种**内容类型**（文件），与 docx、图片、代码同级：任何空间加载了编排工具就能生成 .wdl 文件，它作为文件躺在空间里。

- **WDL 引擎 + 工作台画布页 = WDL 软件**（独立软件，见 §1 存在分类）：独立于 coara、独立分发、独立运行，像 Word 之于 docx。画布看进度、工作流执行都在 WDL 软件内部发生，与 coara 内核和三端无任何关系
- **彻底独立：WDL 软件有自己的 LLM provider 体系**（自己的 provider 配置、自己的模型接入），不复用 coara 的 provider/子智能体机制；节点执行的 LLM 与工具能力由 WDL 软件自带给定，coara 不提供任何运行时能力
- **coara 与 WDL 软件的唯一关系**：coara 是 WDL 的生产者（orchestrator 会话产图 = 写 .wdl 文件）与文件宿主。web 文件系统支持 .wdl 类型，双击唤起外部 WDL 软件（本地应用走协议唤起，web 服务跳 URL 带文件路径，按 WDL 软件实际形态定）
- **剥离动作（已完成 2026-09-08）**：内核 `src/workflow/` 执行层（engine/bridge/controller/persistence/scheduler/scanner）、画布前端（features/workflow 全树 + 三个视图）、REST/WS 接口、`coara workflow` 命令全部移除；orchestrator(run) 改为「校验投影 + 提示用 WDL 软件执行」，不再代跑
- **仓库格局（工具生态范式）**：WDL 软件留在 v8 仓库内作顶层兄弟子项目 `wdl/`（同 gomatrix/、android-app/），独立 pyproject/测试/pip 包，运行时与 coara 内核零 import 关系。coara 作为生产者可依赖 wdl 包的格式层（`wdl.core`：模型/校验/序列化）——格式真相由 WDL 软件持有，如同用 python-docx 产 docx。今后新独立工具同此格局
- **flow 现场模式归属**：FlowCoordinator 内存态编排是会话内能力（产 WDL 的一种方式），已留在 coara（改依赖 wdl.core）；持久化执行完全归 WDL 软件

## 9. 端与内核

三端现状：CLI、Web、Matrix/手机 App。另有内部通道（服务台 @空间、FlowRoot）不算用户端。

- 端 = 连接通道，负责输入送内核、输出推回；空间 = 数据与权限边界
- 所有端接入走同一契约：入站经调度器进 Root 会话，出站走端通道注册表路由，trace/工具活动经事件总线，审批回执走控制通道
- 端与内核之间至少两条通道：**内容通道**（对话消息）与**控制通道**（审批/保险柜等带外信令）。审批回执是控制信号不是聊天内容：需精确路由到等待中的 future、带超时/可中断/重启失效语义、绝不能进 LLM 上下文（防注入防污染）。聊天文字不触发审批
- 内核 = 唯一执行体：回合循环、LLM、工具沙箱、审批、持久化、审计。空间负责声明与调度，永远不拥有执行权。任何空间任何端只能把输入交给内核、从内核拿输出——控制面始终一根管子，可审计可设限
- 会话有引擎能力（agentic loop + 子智能体编排），工作流=确定性图 + 持久化 + 调度的工程化外壳。会话编排=现场指挥；工作流=把指挥图存档交专职引擎按图施工

## 10. 内核承载边界（讨论结论）

- 已支撑：多端并发（忙时去抖/续接/回合 detach）、每空间独立 WorkspaceSession、工作流独立子进程、EventBus 通知
- 边界：单进程内存态、本机一个内核、LLM 调用 IO 为主并发不吃力
- 结论：模式是「每个用户跑自己的内核、开发者给内核写端」则扛得住（现架构）；中心化 SaaS 多租户是另一套架构，非当前目标

## 11. 开源布局推论

能开源的：端（连接通道）、内容类型注册表与查看器、示例工具包/技能/agent 模板。开发者贡献新端或新内容类型（含查看器/编辑器/动作），空间模型与内核一行不改。

握住的：内核（对话引擎 + 工具沙箱 + 内容注册表核心协议）、更新速度、商标。

诚实边界：Python 内核防不了逆向，「闭源」是许可与发布层面控制（私有仓库、专有许可），不是技术壁垒。

## 12. 落地路径（讨论结论）

概念立柱后的推进顺序，前四步是一个闭环：

- **概念固化**：门面三形态、覆盖链、空间身份、端能力层钉进本文档（已完成）
- **内核最小件**：解析 `space.yaml`（可缺省，字段仅 `type`/`storefront`/`view`）；内容类型默认门面先手写静态 dict（不做动态可插拔）；`resolve_home_view` 判定函数先走类型默认 + space.yaml 两层，用户偏好与会话动作只留接口 → **已落地**：`src/workspace/identity.py`（Storefront 三形态 + SpaceIdentity + resolve_home_view）
- **伪空间登记成真空间**：空间条目携带身份三字段（`content_type`/`storefront`/`home_view`，`WorkspaceEntry`），internal 登记走 `ensure_internal_workspace` → **已落地（用量试点）**：`src/workspace/usage_space.py` 启动幂等登记「用量」internal 空间（kind=internal、view=web_only、content_type=usage、storefront=display、home_view=/usage），内容目录指向 coara_home/usage 槽位；`root_lifecycle.py` 启动钩子紧随 daily 登记之后
- **Web 端参考实现**：`/api/workspace/list` 带出 `kind`/`storefront`/`home_view`；侧边栏统一从注册表渲染全部空间——对话空间（无 home_view）在上、系统空间（有 home_view）在下、分隔线隔开；点对话空间真切换落 /chat，点系统空间落其主页；对话页 WorkspaceSwitcher 已删 → **已落地**：`src/ui/handlers/workspace.py`、`src/ui/web/src/components/AppLayout.tsx`、`ChatView.tsx`（删 WorkspaceSwitcher）
- **会话档案空间级缓后**：店员记忆归属空间（事件流+快照+跨端恢复）是大工程，前四步不依赖它

试点验证（2026-09-08）：覆盖链判定（无 space.yaml→warehouse / 有→display）通过；internal 登记幂等与身份字段落盘持久化通过；workspace+UI 测试 226 条全过；前端构建通过。

侧边栏统一（2026-09-08）：`src/workspace/system_spaces.py` 启动幂等登记 配置（营业/config）、消息（展示/review）、记录（展示/records）三个 internal 空间（report 型虚拟内容，占位目录 `.internal/<name>`）；「工作流」已是 managed 条目，用 `registry.patch_workspace_identity` 幂等补身份（workflow/营业//workflow），未登记不代建。切换失败时 `switchWorkspace` 解析响应体 `{"error": ...}` 原样透传（此前前端只抛 HTTP 状态码、吞掉后端真实原因）。**未闭环项**：系统空间登记在 root_lifecycle 钩子中，需重启内核才进注册表；仓库主页（v8 身份头+最近动态）未实现；ExperimentalBadge 组件已无引用但仍存磁盘。
