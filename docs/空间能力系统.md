# 空间能力系统

> 状态：立项文档（2026-09-29），定世界观、不变量与推进次序
> 上游文档：《用户自建空间设计》（09-23）——本文是它的升级与收束，UI 选型裁决、引擎定性、主体装配泛化、能力声明四处新结论以本文为准
> 依据：主线对 module_registry / flow_root / workspace_session / dsh 插件体系的代码核实（09-29）

## 愿景

一切皆工作空间。用户能从零构建出任意形态的空间——包括今天内核写死的工作流空间——不需要任何人把任何空间类型固化进代码。

四件事用户自己都能做：建空间（有会话）、写引擎（独立软件）、写工具（磁盘工具包）、设计 UI（插件页）。coara 的唯一职责是提供把这些组合在一起的槽位。内核是组合点的提供者，不是功能的提供者。

## 三条不变量（裁决判据）

后续所有设计裁决拿这三条当判据，违反任何一条的方案直接否掉。

### 空间 = 声明式组合根

空间的全部形态由声明决定：persona、工具面、技能集、主页 UI、引擎对接方式，全部落在磁盘声明上（注册表 per-workspace 段 / `.coara/` 目录 / 资产文件）。空间本身什么都不是，只是这些声明的组合点。做到了这条，「用户从零构建任意空间」自动成立——组合是自由的。

可变化性是核心判据：今天管这些、明天管那些，今天这个形态、明天那个形态，都只改声明不动代码。

### 管理是一种授权 scope，不是一种空间类型

不存在「系统工作空间」这个代码概念。管理其它空间（配置 / 用量 / 记录 / 技能工具资产）= 某个普通空间被授了系统域工具包 + 跨空间读写许可。它是普通空间加一组 grant。

推论：系统工作空间是涌现的角色，不是被授予的身份。用户建一个空间、挂上管理工具包，它就是系统工作空间；卸掉就回归普通。它管理别人的同时也管理自己（管自己就是读写自己的声明），零额外机制。代码里永不出现 `if 系统工作空间` 的分支。

### 内核不是工作空间

一切皆工作空间有一个不可递归的底：提供对话能力的运行时本身。day zero 它先于任何空间存在。这不是违背愿景，是愿景的边界。

内核里会残留一份「真正的铁律清单」——声明化过程会逐个顶出硬编码假设，每处要裁决「改成读取声明」还是「保留为不可变内核行为」。这份清单会越做越薄但永远不会是零（安全边界必在其中，见下）。

## 四个组合槽位

用户四件事对应四个槽位。现状与差距（09-29 代码核实）：

### 槽位一：工具 — 已有

磁盘工具包（`.coara/tools/` + 用户级 `users/default/tools/`，TOOL.md + 入口 Python）是完整通道：发现、审批、调用都通。零改动。

### 槽位二：引擎 — 不需要槽位

引擎是外部软件（Office 定性）：coara 经文件与命令跟它打交道，内核零 import、零托管、零 IPC 契约。WDL 已是这个范式的事实先例（`wdl/` 独立软件，`wdl run`）。此面只需文档与示例，无需内核改动。

### 槽位三：会话主体 — 装配泛化已落地（09-29）

改造前：`ModuleSpec` / `AgenticSpec` 已是声明壳（`src/coara/module_registry.py`），但五个内置模块是代码字面量注册，且装配动作写死——`_create_module_root` 里明文 `if spec.subject == "flow"` 走专属 `create_flow_root`。

已落地：

- 模块注册磁盘化：七个内置模块（chat/review/files/workflow/records/usage/config）原样搬为 `src/coara/prompts/modules/*.yaml` 声明文件（随包分发走既有 `prompts/**/*.yaml` 包数据规则）；用户级 `users/default/modules/` 同名 id 覆盖内置
- 装配泛化：`module_root.build_module_subject()` 抽出公共装配段（persona 加载、CoaraBase 创建、工具注册、ToolGatewayTool、subject trace sink），`create_module_root` 与 `create_flow_root` 共用；flow 只留专属段（orchestrator 常驻、录像带重解、草案会话恢复）
- persona 三层扫描：AgentRegistry.scan 追加 工作空间级 `.coara/agents/` → 用户级 `users/default/agents/` → 内置（同名先扫者占名，即高层覆盖低层，与技能三层同语义）

### 槽位四：UI — 裁决落定：运行时插件化（一期已落地）

现状改造前：纯单体。工作流画布（`features/workflow/`）、配置（`features/config/`）、用量（`views/PersonalView.tsx`）全部静态 import 进 bundle，运行时没有任何加载机制。

裁决（用户 09-29 拍板）：走 dsh 路线——运行时插件 + 槽位注册。目标天花板是「用户任意设计自己的工作空间 UI」，iframe 观感割裂、声明式拼不出画布，都不配此目标。此裁决推翻《用户自建空间设计》「iframe 为主线」的终态倾向。

dsh 参考架构（`deepseek-harness` 仓核实）：

- 双半插件：包声明 `dsh.client` 即成 UI 插件；宿主把 client bundle 经 `/plugins` 发给浏览器
- 浏览器懒加载模块表，按需拉取物化；插件可热启停
- 槽位系统（`ui-slots`）：具名类型化槽位，插件 `ctx.slots.register(...)` 挂入；声明即占领、冲突加载期抛错
- 冻结共享基线：壳冻结 React 与基础 UI 库，插件 bundle 对着基线解析，不自带 React
- dsh 自己的整个界面就是五十多个插件拼的，壳只是槽位渲染器

学它的架构，不学它的体量。dsh 是 cordis DI 内核 + 双 face 构建管线 + pnpm 包装安装与版本审批 + HMR 的完整体系；coara 只取两个核心思想——运行时加载浏览器 bundle、具名槽位注册。

一期已落地（09-29）：

- 空间声明入口：space.yaml 的 `home_view: plugin:<bundle.js>`（`src/workspace/identity.py::space_home_view` 下发）
- 后端服务口：`GET /api/space-ui/{空间名}/{相对路径}`（`src/ui/handlers/workspace.py::_handle_space_ui_asset`）——token 鉴权、限制该空间 `.coara/ui/` 子树、逃逸硬拒、JS 强制 `text/javascript` MIME
- 前端槽位：`views/SpacePluginView.tsx`——动态 import bundle，契约是 default export `mount(el, ctx)`（返回可选清理函数）；ctx 一期最小面 `{workspace, token, apiFetch}`；SpaceHomeView 就地渲染插件页，侧边栏对 plugin: 前缀落 /home
- 技术栈自由：bundle 是任意工具链打的 ESM，壳只给 DOM 挂载点，不冻结 React 基线（有真实需求再长）
- 明确不做：细粒度槽位（list/keyed/chain）、HMR、npm 包安装体系、版本审批。等真实需求顶出来再长

长期方向：现有内置页面（工作流 / 配置 / 用量 / 记录 / 消息）逐步迁成内置插件，壳变纯槽位渲染器。「砍掉工作流空间」届时才真正可能——它从代码变成可装可卸的插件包。迁移放在槽位跑通之后，不并进一期。

## 空间级能力声明（槽位一三的横切）

每个空间的工具集与技能集独立配置、跨空间零泄漏（09-29 已落地）：

- 存储（B 裁决）：space.yaml 单真源，不做双写。字段 `tools` / `skills`，None=不声明=全量默认；声明=白名单。目录拷走即带走全部声明，注册表不持这些字段（旧字段已退役，存量注册表里的残留键 pydantic 自动忽略）
- 技能生效点：SkillManager 挂起判定处——全局 skills.deferred ∪ 本空间白名单外；白名单外视同挂起（仍可 search/activate）
- 工具生效点：会话装配点（create_for_workspace）声明了才 `set_whitelist`；前台与切换空间共用此路径，子智能体经父可见集继承自动收窄
- 最小核心集保护：todo / delegate / plan / skill / ws / tool 恒在，白名单管不到（`src/coara/workspace_capabilities.py::CORE_TOOL_NAMES`）
- 一致性红利：external 空间的默认收敛也有了落点

## 创建空间：从零与复制

不要模板（用户 09-29 否决：模板是写死的出厂清单换了个存放位置）。创建只有两种：

- 从零：空声明，什么都没有，全靠自己往上加
- 复制某个现有空间：把源空间的 persona、工具技能声明、UI 声明整份深拷贝，之后各自独立演化

「出厂默认给什么」= 出厂自带的种子空间本身（一个普通空间），想用它做起点就复制它。用户的最佳实践天然成为后续起点，无需任何人固化模板。

## 代价与对策（提前认账）

- 可变化性的反面是漂移：一切可声明后，「这空间为什么行为变了」的排障变难。对策随声明化同步做：声明版本化、可 diff、变更留痕（接工作空间动态的处置轨迹）
- 组合自由度会顶出内核写死的假设：逐个裁决「读取声明」还是「保留铁律」，铁律清单越做越薄但不为零
- 插件化的安全边界：插件 bundle 与壳同域同 token 上下文（dsh 同此形态），external/untrusted 空间永不可被授管理 scope、其 UI 插件加载需单独裁决——此条属铁律清单，不交给配置
