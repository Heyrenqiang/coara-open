# 重启机制设计

supervisor 模式：`/restart` = 内核优雅收尾后以专用退出码结束，由外层托管进程拉起新实例。

## 一、为什么废掉旧协议

旧实现是「内核自己 spawn 替代者，然后 `os._exit(0)` 强退」（交棒协议：intent/ready/rollback 三文件 + 端口让位 + 健康轮询）。连环三次事故都长在这条结构上：

- 强退绕过优雅收尾：每条持久化链（sync 游标、用量、trace）都要靠调用点记得手工 flush，新增一条链就多一个丢数据的洞
- 交棒协议每步都是竞态窗口，失败靠 `_rollback` 往回捞（daemon.log 里真实触发过 6 次）
- 没有独立于内核生命周期的进程承担「先杀旧、后起新」

2026-09-25 的死循环是压垮它的最后一根：`/restart` 的处理器就是触发 `os._exit` 的任务，它永不「完成」，含 `/restart` 消息的 Matrix sync 世代游标永不落盘，新实例从旧游标重放这条消息，再触发重启，约每 22 秒一轮。在「进程自己替换自己」的模型上继续修补，永远会有下一条没 flush 的链。

## 二、新模型（顺序与职责收口）

进程分层：

- **supervisor**（`src/cli/supervisor.py`，极薄进程）：`coara tray` / `coara daemon` 的实际入口。职责只有三件——spawn 内核子进程、wait 退出码、按退出码分派。托盘图标挂在 supervisor（重启期间内核死一次，托盘不闪断）。不含 asyncio/LLM，越薄越稳。
- **内核**（`_kernel` 内部命令）：由 supervisor 拉起。`/restart` 不再是 spawn+强退，而是走正常优雅 shutdown 后以 `EXIT_RESTART`（42）退出码结束。sync 游标、用量、trace、实例锁、端口全部由既有 shutdown 路径自然收尾——没有需要单独记得 flush 的链。

重启流程：

1. `/restart` 到达 → 记录诊断（`restart_last.json`：谁/何时/为何）→ 唤醒 `stop_event` 走与信号退出完全相同的优雅收尾路径 → 进程 exit(42)
2. supervisor 看到 42 → respawn 内核（旧进程已死透，锁与端口已自然释放，零竞态）
3. 其他退出码：0 正常退出 → supervisor 跟着退；崩溃 → 退避 respawn（5s→10s→30s，封顶 5min，跑满 60s 的退出清零退避），防崩溃循环

## 三、实现落点

- `src/cli/supervisor.py`：`run_supervisor`（spawn-wait-分派主循环 + 托盘托管 + 崩溃退避）、`_kernel_argv`（内核命令固定为 `-m src.coara --workspace <ws> _kernel`）、`_terminate_kernel`（托盘退出：先 POST 优雅停机端点，无响应才 terminate，再不行强杀）、`EXIT_RESTART=42`
- `src/cli/main.py`：`tray`/`daemon` 改走 supervisor；`_kernel` 内部命令跑 `_run_frontends`（复用现成优雅收尾链：信号 → cancel tasks → 关 trace → `root.shutdown()`）；`_run_frontends` 尾部 `consume_restart_flag()` 为真则以 `SystemExit(EXIT_RESTART)` 结束
- `src/runtime/restart.py`：重启意图传递（`bind_restart_stop_event` / `request_restart` / `consume_restart_flag` / `wake_stop_event`）+ 诊断记录写入。不再是协议载体
- `src/coara/commands/restart.py`：`/restart` 仅 supervisor 托管下可用（`COARA_SUPERVISED=1` 由 supervisor spawn 时注入）；非托管形态明确拒绝（没有 supervisor 在外面 respawn，自杀就是真死）
- `src/ui/web_server.py`：`POST /api/v1/kernel/shutdown`（本机回环 + token 双闸）= supervisor 托盘退出的优雅停机通道；`yield_listening`/`resume_listening` 端口让位协议整体删除

## 四、边界

- 非托管形态（开发直跑 `python -m src.coara` 无 supervisor）：`/restart` 明确回复「未被托管，无法自重启」，不自杀
- 重启期间的在飞回合：不做特殊处理——重启是显式动作，发起者清楚代价；优雅收尾会把在飞回合按 shutdown 口径打断
- 并发保护：意图标志幂等（重复 `/restart` 只保留首个意图，stop_event 已 set 后重复 set 无副作用）
- 崩溃自愈只由 supervisor 的退出码分派承担，内核内不再有任何「拉起自己替代者」的代码
- 权限：owner only，与其它会改变内核生存状态的动作同级

## 五、验收

1. 正常路径：`/restart` → 端上只有「正在重启…断线几秒后自动重连」一句 → 内核优雅收尾（trace/游标落盘）→ exit(42) → supervisor respawn → 端自动重连 → `restart_last.json` 记下本次意图
2. Matrix 游标：重启后新实例 sync 游标越过 `/restart` 消息，不重放（本次死循环的直接修复点）
3. 托盘：重启期间托盘图标不闪断；托盘「退出」→ 内核优雅停 → supervisor 退
4. 崩溃自愈：人为让内核起来就挂 → supervisor 按退避 respawn，日志可追
5. 非托管：直接 `python -m src.coara _kernel` 跑的内核，`/restart` 明确拒绝
