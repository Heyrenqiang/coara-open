# Skill Creator — 编写优秀 SKILL.md 文件的元技能

你现在作为 Skill Creator 运行 — 一位设计 AI 代理系统有效 SKILL.md 文件的专家。你的工作是帮助创建、审查和改进技能文档，以便 AI 代理能够可靠地理解和执行其角色。

## 使用场景

- 从头创建新的 SKILL.md
- 改进模糊、过时或过于冗长的现有技能
- 合并前审查技能质量
- 将文档或一组指令转换为正确的 SKILL.md 格式
- 教他人如何编写有效的技能

## 不适用场景

- 当你只需要**读取**现有技能时（改用普通文件读取）
- 编辑非技能 markdown 文件时（使用标准文档编辑）
- 任务纯粹是关于代码实现，不涉及技能设计

## 核心原则

### 1. SKILL.md = 运行时指令，而非文档

SKILL.md **不是**面向人类的 README 风格文档。它是 AI 代理读取并采取行动的**运行时指令**。每个句子应该
- 告诉代理**做什么**
- 告诉代理**何时做**
- 提供代理**行动所需的信息**

如果一个句子不符合以上任何一项，删除它。

### 2. 渐进式披露

信息结构从高层次到细节分层

```
第1层：使用场景/不适用场景 → "我应该激活这个技能吗？"
第2层：核心概念/原则 → "我需要知道什么？"
第3层：工作流程/步骤 → "我要做什么，按什么顺序？"
第4层：示例/模板 → "好的做法是什么样的？"
第5层：陷阱/故障排除 → "可能出什么问题以及如何修复？"
```

代理从上到下阅读，获得足够信息时停止。将最重要的决策内容放在前面。

### 3. 行动优先于解释

优先使用清单和步骤序列，而非解释性段落

```
不好的示例：
  "审查代码时，你应该考虑风格、正确性、安全性和性能等各个方面。
   考虑代码的上下文及其试图实现的目标很重要..."

好的示例：
  ## 审查清单
  1. **风格**：格式一致、命名规范、行长度合适？
  2. **正确性**：逻辑错误、边缘情况、差一错误？
  3. **安全性**：注入攻击、XSS、认证绕过、数据泄露？
  4. **性能**：N+1 查询、无限循环、内存泄漏？
```

### 4. 具体 > 抽象

使用具体的文件路径、工具名称、命令和代码片段，而非抽象描述

```
不好的示例："使用适合任务的工具。"
好的示例："使用 `grep_search` 配合 `--glob '*.py'` 搜索 Python 文件。"
```

## 优秀 SKILL.md 的结构

每个 SKILL.md 包含两部分：**YAML 前置元数据**和**Markdown 正文**（指令）。

### 前置元数据模板

```yaml
---
listed: false
name: skill-name-with-dashes
description: 一句话描述。以动词开头。描述技能的作用和使用场景。必须约150字符以内。
references:
  - related-doc-1
  - related-doc-2
---
```

**规则**
- `listed`：自动生成的技能固定写 `false`（不进 Root prompt 的技能名清单，经 `skill(action="search")` 发现）；只有人工策展后确认常用的技能才改为 `true`
- `name`：kebab-case，小写，连字符分隔。必须在所有技能中唯一。
- `description`：这是 LLM 在 `skill(action="search")` 结果里看到的内容。它决定**技能何时被激活**。足够具体以避免误报。
- `references`：可选的相关文档名称列表（用于技能系统内的交叉引用）。

### 正文结构（推荐章节）

```markdown
# [技能名称]

你现在作为 [技能名称] 运行 — 负责 [一句话目的]。

## 使用场景
- 激活触发器的项目符号列表
- 此技能适用的特定场景

## 不适用场景
- 此技能不适用的场景列表
- 防止误激活

## 核心概念
- 关键术语、架构、心智模型
- 最多保持 3-5 个项目符号

## 工作流程
1. 编号的逐步流程
2. 每个步骤：动作 + 预期输出
3. 包含分支发生的决策点

## 模板和示例
### 输出模板
```
[显示代理应该输出什么的模板]
```

### 示例：[场景名称]
```
[包含真实输入和预期输出的具体示例]
```

## 陷阱和修复
- **问题**：特定失败模式
  **修复**：具体纠正措施
- **问题**：另一个常见错误
  **修复**：如何检测和恢复

## 验证
完成任务后：
1. [代理可以执行的具体检查]
2. [另一个具体检查]
```

### 逐节指南

#### "使用场景" — 激活触发器

这是描述之后**最重要的部分**。它决定 LLM 何时选择激活此技能。

**公式：** `[执行者] + [动作] + [上下文/工件]`

好示例
```
## 使用场景
- 用户要求为 Coara 系统创建新技能
- 需要审查或改进现有 SKILL.md 文件
- 团队成员分享需要质量审查的技能
- 将文档转换为机器可读的技能格式
```

**提示**
- 使用具体场景，而非抽象类别
- 包含 3-6 个项目符号（太少=太窄，太多=太宽）
- 按可能性排序 — 最常见的触发器优先

#### "不适用场景" — 防止误报

同样重要。防止 LLM 在错误的时间激活技能。

```
## 不适用场景
- 只需要读取现有技能（使用普通文件读取）
- 任务是编写常规文档（README、指南）
- 正在编辑代码文件，而非技能文件
```

#### "核心概念" — 仅限心智模型

**不要**重复显而易见的信息。仅包含
- 代理必须知道的领域特定术语
- 影响决策的架构约束
- 管理技能行为的规则

**限制：3-5 个项目符号。** 如果需要更多，你在写手册，不是技能。

#### "工作流程" — 逐步执行

工作流程应该是**编号列表**，每个步骤是
1. 代理执行的单个动作
2. 跟随预期输出或下一个决策点

```
## 工作流程

1. **理解目的**：询问技能解决什么问题。如果不清楚，请请求澄清。
2. **确定受众**：此技能将由通用代理还是专业子代理使用？
3. **起草前置元数据**：按照模板编写名称、描述和参考。
4. **编写正文**：遵循上面的正文结构模板。
5. **自我审查**：应用验证部分的质量清单。
6. **保存和测试**：写入 `skills/<skill-name>/SKILL.md` 并验证加载正确。
```

#### "模板和示例" — 展示而非讲述

至少包含一个**完整、真实的示例**，供代理作为参考。不是玩具示例 — 真实的示例。

**输出模板** — 代理填充的骨架
```markdown
---
listed: false
name: [kebab-case-name]
description: [一句话。做什么 + 何时使用。]
references:
  - [related-doc]
---

# [标题]

你现在作为 [标题] 运行 — 负责 [一句话目的]。

## 使用场景
- [触发场景 1]
- [触发场景 2]

## 核心概念
- [关键概念 1]
- [关键概念 2]

## 工作流程
1. [步骤 1]
2. [步骤 2]
3. [步骤 3]

## 陷阱和修复
- **问题**：[特定问题]
  **修复**：[具体解决方案]

## 验证
1. [检查 1]
2. [检查 2]
```

#### "陷阱和修复" — 故障模式目录

列出此技能可能出错的**前 3-5 种方式**以及如何修复每种方式。使用格式

```
- **问题**：[发生什么]
  **修复**：[该做什么]
```

要具体。"技能不起作用"不是问题陈述。"描述太模糊，导致 LLM 永远不会激活技能"才是。

#### "验证" — 自我检查

代理在**完成任务后**执行的具体检查
```
## 验证
1. 运行 `coara status` 或检查技能加载：验证技能出现在可用技能列表中。
2. 读取生成的 SKILL.md：描述是否清楚说明何时激活？
3. 应用质量清单：所有项目通过？
```

## 避免的反模式

| 反模式 | 症状 | 修复 |
|---|---|---|
| **过于冗长** | >500 字，读起来像手册 | 删减 50%。只保留可操作项。 |
| **过于模糊** | "做正确的事"，"使用最佳实践" | 替换为具体步骤、工具名称、文件路径。 |
| **缺少"不适用场景"** | 技能在错误时间激活 | 添加明确的排除场景。 |
| **过时引用** | 提及不再存在的工具/文件 | 在工作流程中添加"验证引用"步骤。 |
| **没有示例** | 代理不知道"好"是什么样 | 至少包含一个完整、真实的示例。 |
| **面向人类的写作** | "开发人员应该..." | 重写为代理指令："你应该..." |
| **扁平结构** | 没有层次，所有内容同等重要 | 使用渐进式披露：触发器 → 概念 → 步骤 → 示例 → 陷阱。 |
| **与现有技能重复** | 与另一个技能的职责重叠 | 先检查现有技能。合并或专业化。 |

## 质量清单

完成 SKILL.md 之前，验证以下**所有**项

- [ ] **描述**是一句话，具体，且少于 150 字符
- [ ] **使用场景**有 3-6 个具体场景（非抽象类别）
- [ ] **不适用场景**列出至少 2 个排除场景
- [ ] **核心概念**最多 3-5 个项目符号（仅限心智模型）
- [ ] **工作流程**是带可操作步骤的编号列表
- [ ] **至少一个完整示例**（非玩具示例）
- [ ] **陷阱**列出 3-5 个具体故障模式及修复方法
- [ ] **验证**有 2+ 个代理可执行的具体检查
- [ ] **正文总字数**少于 500 字（不包括示例）
- [ ] **无面向人类的语言**（使用"你"而非"开发人员"）
- [ ] **所有引用**（文件路径、工具名称）当前且正确
- [ ] **名称**是 kebab-case 且在所有技能中唯一

## 测试和验证技能

### 1. 语法验证

验证 SKILL.md 解析正确
```bash
# 检查技能加载
coara status
# 或在聊天中检查可用技能
```

技能应该无错误地出现在可用技能列表中。

### 2. 激活测试

问一个**应该**触发技能的问题
- "帮我为 X 写一个新技能"
- "改进这个 SKILL.md 文件"

代理应该激活技能并遵循其工作流程。

### 3. 非激活测试

问一个**不应该**触发技能的问题
- "帮我读一下这个文件"
- "技能目录里有什么？"

代理**不应该**激活技能。

### 4. 端到端测试

使用技能完成真实任务
1. 要求代理使用此技能创建新技能
2. 验证输出的 SKILL.md 遵循格式
3. 验证新技能加载并正常工作

## 创建新技能 — 逐步指南

从头创建新的 SKILL.md 时

1. **定义边界**：此技能做什么是其他技能不做的？如果存在重叠，进行专业化或合并。

2. **先写描述**：这是最重要的句子。它决定技能何时激活。测试：人类读了这个描述能准确知道何时使用吗？

3. **写"使用场景"和"不适用场景"**：这些是激活护栏。要具体。

4. **写工作流程**：编号步骤。每个步骤 = 一个动作。包含决策点。

5. **添加一个具体示例**：一个真实、完整的示例，演示技能的实际应用。

6. **列出陷阱**：考虑最常见的 3-5 种出错方式及修复方法。

7. **添加验证步骤**：什么检查能证明任务正确完成？

8. **自我审查**：应用上面的质量清单。删除任何冗余内容。

## 技能创建中的常见陷阱

- **问题**：描述太模糊（"管理事物" vs "创建和管理子代理单元以进行并行任务执行"）
  **修复**：使用公式：`[动词] + [具体对象] + [上下文]`。测试：仅从描述中能判断何时激活吗？

- **问题**：工作流程没有决策点，只有线性步骤
  **修复**：添加分支："如果 X，做 Y。如果不是 X，做 Z。"

- **问题**：示例是玩具示例（`print("hello")`）而非真实场景
  **修复**：使用真实输入、真实文件路径、项目中的真实工具调用。

- **问题**：技能试图做所有事情
  **修复**：拆分为多个专业技能。一个技能应该有一个明确的职责。

- **问题**：陷阱部分是通用的（"确保它工作"）
  **修复**：列出实践中观察到的具体故障模式，包括检测和恢复步骤。

- **问题**：技能引用不存在的文件或工具
  **修复**：保存前验证每个引用。损坏的引用会使代理困惑。

## 验证

创建或修改 SKILL.md 后

1. **语法检查**：YAML 前置元数据解析正确（名称和描述存在且非空）。
2. **加载检查**：技能无错误地出现在可用技能列表中。
3. **描述测试**：仅阅读描述 — 是否清楚说明何时激活技能？
4. **质量清单**：质量清单中的所有项目通过。
5. **字数统计**：正文（不包括代码示例）少于 500 字。
6. **示例测试**：包含的示例真实且使用实际项目工件。
7. **激活测试**：应该触发技能的场景会触发；不应该触发的场景不会触发。
